# Commit Skill

## Subject

### type

站在本仓库使用者的角度，判断本次变更带来的实质影响。

**判断原则**：以**使用者因此得到了什么**为优先，而非改了什么。

- `feat`：新增功能或内容。使用者因此获得了之前没有的能力或资源。
- `fix`：修复缺陷。使用者因此不再受该问题困扰。
- `refactor`：重构代码。使用者无感知，但代码的可维护性或可读性得到提升。
- `chore`：维护性工作。使用者无感知，如依赖更新、脚本调整、配置文件修改等。
- `docs`：文档或注释变更。使用者通过文档获得更准确的信息。
- `style`：格式调整。不涉及逻辑变更，如空格、换行、缩进等。
- `test`：测试代码的新增或修改。使用者无感知，但代码质量保障得到加强。
- `ci`：持续集成配置变更。使用者无感知，但自动化流程得到调整。

**场景示例**：

| 仓库类型 | 变更内容          | 判断       | 理由                   |
| -------- | ----------------- | ---------- | ---------------------- |
| dotfiles | 新增 `.gitconfig` | `feat`     | 使用者获得了新配置能力 |
| 业务应用 | 升级依赖版本      | `chore`    | 使用者无感知           |
| 工具库   | 重命名私有方法    | `refactor` | 使用者无感知           |

### description

- 使用祈使语气，说明本次提交做了什么
- 首字母小写（英文），末尾不加句号
- 不超过 72 字符

## 约束

1. 仅分析暂存区的变更内容
2. 提交信息仅包含 `<type>: <description>`，不添加 scope、body 或 footer
3. 优先使用最近一次提交所用的语言，无法确定时默认使用英文
4. 提交信息为英文时，须附中文释义，仅供阅读，不写入提交信息
5. 同时给出对应的提交命令（如 `git commit -m "<type>: <description>"`），但不代用户执行提交
6. 暂存区无变更时不生成提交信息，提示用户先暂存文件
7. 暂存区含多个逻辑独立变更时，按用户指定主题生成信息，不自行合并提交
