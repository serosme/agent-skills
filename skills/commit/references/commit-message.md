# 提交信息规范

## Subject 格式

提交信息仅包含一行：

```text
<type>: <description>
```

- `type` 与 `description` 之间使用英文冒号和一个空格。
- `type` 使用本规范定义的小写英文值。
- 不添加 scope、body 或 footer。

## Type 判断原则

站在本仓库使用者的角度，判断本次变更带来的实质影响。

判断优先级：以 **使用者因此得到了什么** 为优先，而非仅看 **改了什么文件**。

同一种文件变更，在不同仓库或不同目的下，可以对应不同 `type`。

例如：

- 配置文件是 dotfiles 仓库的交付内容，新增配置能力可以是 `feat`。
- 业务应用内部的常规配置维护，通常是 `chore`。
- 依赖更新用于修复明确的用户缺陷时，应按实际影响判断，不机械归为 `chore`。
- Skill 中的 Markdown 可能承载可执行的行为规范，不能仅因文件扩展名为 `.md` 就归为 `docs`。
- 只调整组织结构、不改变对外行为时，不因新增文件就判断为 `feat`。

## Type 定义

| type       | 含义               | 判断依据                                     |
| ---------- | ------------------ | -------------------------------------------- |
| `feat`     | 新增功能或内容     | 使用者获得了之前没有的能力或资源             |
| `fix`      | 修复缺陷           | 使用者不再受该问题困扰                       |
| `refactor` | 重构实现或组织结构 | 对外行为不变，但可维护性或可读性得到提升     |
| `chore`    | 维护性工作         | 内部维护，如常规依赖更新、脚本调整、配置维护 |
| `docs`     | 文档或注释变更     | 通过说明性内容提供更准确的信息               |
| `style`    | 格式调整           | 仅调整空格、换行、缩进等，不改变逻辑或含义   |
| `test`     | 测试代码新增或修改 | 加强测试保障，不改变对外功能                 |
| `ci`       | 持续集成配置变更   | 调整持续集成中的自动化流程                   |

## Type 场景示例

| 仓库类型    | 变更内容                             | 判断       | 理由                     |
| ----------- | ------------------------------------ | ---------- | ------------------------ |
| dotfiles    | 新增提供 Git 配置能力的 `.gitconfig` | `feat`     | 获得新的配置能力         |
| 业务应用    | 常规升级依赖，不改变用户行为         | `chore`    | 属于内部维护             |
| 工具库      | 重命名私有方法                       | `refactor` | 改善可读性，对外行为不变 |
| 业务应用    | 修复登录失败                         | `fix`      | 消除实际缺陷             |
| 工具库      | 修正 API 文档中的参数说明            | `docs`     | 提供更准确的信息         |
| 业务应用    | 统一代码缩进                         | `style`    | 仅改变格式               |
| 工具库      | 为现有解析函数补充测试               | `test`     | 加强测试保障             |
| 业务应用    | 调整 CI 的测试矩阵                   | `ci`       | 调整持续集成流程         |
| Skills 仓库 | 仅重新组织技能说明并提取参考文件     | `refactor` | 行为不变，改善维护性     |
| Skills 仓库 | 修复会生成错误提交命令的指令         | `fix`      | 修复技能的实际缺陷       |

## 删除与歧义处理

- 新增、修改、删除是操作形式，不直接决定 `type`。
- 删除不可达的内部代码且行为不变，可以是 `refactor`。
- 删除错误行为以修复缺陷，可以是 `fix`。
- 删除过时的说明性文档，可以是 `docs`。
- 删除对外能力或回滚变更时，仍应判断实际影响，不默认归为 `feat` 或 `chore`。
- 本技能只使用上述 8 种 `type`，不自行引入新类型。
- 无法在现有类型中可靠分类时，说明歧义并请求用户确认，不把 `chore` 当作无条件兜底。
- 用户指定的 `type` 与实际影响明显冲突时，说明冲突并请求确认，不直接套用。

## Description 规则

- 使用祈使语气，说明本次提交做了什么。
- 英文首字母小写。
- 末尾不加句号。
- `description` 本身不超过 72 字符，不含 `<type>:` 前缀。
- 在准确表达的前提下尽量简短，不堆砌内容。
- 优先描述具体行为，避免含义模糊的表述。
- 不声称差异中无法确认的效果。
- 不添加换行、控制字符或与主题无关的内容。

### 推荐示例

- `feat: add csv export`
- `fix: handle expired login credentials`
- `refactor: simplify configuration parsing`

### 避免示例

- `chore: update files`
- `fix: fix bugs`
- `feat: make things better`

## 语言规则

- 优先使用最近一次提交所用的语言。
- 判断语言时，主要参考描述部分，不仅依据 `feat`、`fix` 等类型前缀。
- 无历史提交，或无法可靠确定语言时，默认使用英文。
- 不自动改为按多条历史提交多数投票，也不推测历史作者的语言偏好。
- 英文提交信息须附中文释义。
- 中文释义不属于提交信息，不写入 `git commit` 的消息参数。
- 用户明确要求不同语言时，说明其与默认规则的差异，确认本次是否按用户指定语言处理。

## 多文件与多主题

- 多个文件不等于多个主题。
- 为同一功能配套修改实现、测试和文档，通常属于一个主题。
- 同一主题的 `type` 按主要实质影响判断，不因包含测试或文档就改为 `test` 或 `docs`。
- 多个逻辑独立主题不得擅自合并概括，应由用户指定主题。
- 用户尚未明确主题时，列出候选主题供选择，不生成最终提交信息。
- 选定消息主题不会改变实际提交范围；普通 `git commit -m` 仍会提交全部已暂存变更。
