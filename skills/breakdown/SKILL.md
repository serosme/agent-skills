# Breakdown

## 目标

输入可以是一个需求、一个 issue，甚至只是一个想法。先判断要不要拆，需要拆就切成能独立完成、独立验收的功能点，产出 `index.md`，写清有哪些功能点、它们之间谁依赖谁。

拆分的目的是降低开发人员的心智负担：一个功能点能独立做完、独立验收，比把整个需求一次交给开发人员更容易推进。

## 前置条件

- 必要输入：一个需求、一个 issue，或一个想法。
- 可读：需求点到的代码与文档，读够判断涉及哪几个部分即可。
- 输出位置：默认当前目录下 `docs/<需求名>/index.md`，目录名用小写短横线。
- 缺失处理：连涉及哪几个部分都判断不了，先问一句范围。

## 执行步骤

### 步骤 1：判断要不要拆

- 操作：读需求与它点到的地方，按 **判断标准** 得出结论，先告知开发人员。
- 完成标志：要不要拆已有结论并已告知。不用拆时也照常出草案，只是只有一行。

### 步骤 2：出草案

- 操作：
  - 按 **切分方式** 切分，一次给全，写清有哪些功能点、每块做完能看到什么、谁依赖谁，附一句为什么这么切。
  - 写完顺手确认依赖无环。
- 完成标志：每块都能独立交付、单独验收，粒度齐平。

### 步骤 3：与开发人员讨论

- 操作：
  - 开发人员砍、并、改、推翻都照办，按开发人员的切法重排依赖；开发人员确认草案即视为定下。
  - 有不同看法先给建议，采纳与否由开发人员定。开发人员只说不行、没说方向时，问一句想要的方向，不自行推演。
  - 合并或拆分后，「做完能看到什么」同步改写。
  - 要整体推翻重切时，回到步骤 2，不重新判断要不要拆。
- 完成标志：切法与顺序，或只有一块时的结论，由开发人员定下；各条的「做完能看到什么」已随讨论更新。

### 步骤 4：落盘

- 操作：按 **index.md 格式** 写文件。
- 完成标志：文件里的功能点、依赖与讨论结果一致。

### 步骤 5：验收并结束

- 操作：
  - 对照 **验收标准** 逐条核对，修正后重查。
  - 报告文件路径、要不要拆的结论，以及按依赖顺序第一个可开工的编号，然后停。
- 完成标志：验收项全过，路径与编号已报出。

## 约束

### 判断标准

- 一个功能点就是交付后开发人员能自己演示的一件事，不能是「设计完成」。
- 需求牵扯面广、本来就是两件不同的事时，就该拆；本来就小，就保持一块。
- 切开后要能形成更小、能独立完成与验收的功能点，并实际降低开发人员的心智负担。不以功能点数量或开发人员能否一次看完为准。
- 粒度齐平指各功能点体量相当，没有一块明显大于其余几块。

### 切分方式

- 按能独立完成的事切；同一件事要分几步才能用上时，按先能用、后补的顺序切。
- 不按层切，不按文件切，不按工期均分。
- 「做完能看到什么」里含「并且」就是两块，拆开后再写。

### 边界

- 只存在范围与切法这一层：在哪切、切几块、谁先谁后。进到列表里的功能点都是要做的，只是分先后。
- 功能点内部的具体边界，例如哪些行为做、哪些不做，不在这里定。
- 可以不拆，只有一块也算正常结果，同样要经开发人员确认。
- 讨论以开发人员为准，只给建议，不代开发人员定。
- 中途叫停时，已定下的切法留在对话里，不落盘；下次重新过一遍步骤 1。
- 不写计划、方案、技术选型、实现步骤、测试用例，不写代码。

## 输出与验收

### index.md 格式

```markdown
# <需求名>

<三五句话，概括需求本身：做什么、给谁用、有什么约束。可以精简、可以略去细节。不补需求里没有的内容，不写方案，也不写要不要拆的判断>

## 功能点

| #   | 功能点 | 做完能看到什么 | 依赖 |
| --- | ------ | -------------- | ---- |
| 01  |        |                | -    |
| 02  |        |                | 01   |
```

完整示例见 `assets/index-example.md`，落盘前对照一次。

「依赖」指必须先完成、后一块才能开始的那一块；只是复用产物而不挡路的，写 `-`。

### 交付内容

- 文件路径。
- 要不要拆的结论，在对话里说，不写进文件。
- 第一个可开工的编号，按依赖顺序。

### 验收标准

- 文件在 `docs/<需求名>/index.md`，目录名小写短横线。
- 每块都能独立交付、单独验收，粒度齐平。
- 每条的「做完能看到什么」能演示，且不含「并且」。
- 需求描述是概括需求本身，可以精简与省略，但没有补进需求里没有的内容，也没有写判断与结论。
- 依赖关系无环，且符合依赖的定义。
- 需求本来就小时，文件里只有一行功能点。
- 文件里没有计划、方案、技术选型、实现步骤、测试用例。
- 最终切法与顺序由开发人员认可；只有一块时也已确认。

## 示例

需求：「做一个和 AI 聊天的功能。Web 端用 Nuxt 加 Nuxt UI，单页，像传统聊天记录一样我发一句 AI 回一句，发出去不用等回复。后端把用户和 AI 的消息存进消息表，每次真调模型时带上最近 7 天的聊天记录，可以再附加一些提示词。手机上一个安卓壳加 WebView 加载这个网页。单用户，认证只要一个密码。」

结论：涉及页面、消息存储、模型调用、认证与安卓壳五个部分，要拆。给出五个功能点的草案。

开发人员只改了两条措辞，其余照原样，确认后落盘。落盘结果见 `assets/index-example.md`；报路径、结论与 01 的编号，然后停。
