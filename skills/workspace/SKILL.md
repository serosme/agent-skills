# Workspace

## 适用场景

### 目标

在工作区根目录生成两个文件：约束文件 `AGENTS.md` 与服务事实清单 `workspace.md`。
前者只写约束，后者只写事实，两边不重复。
让 Agent 不必猜端口，也不必逐仓库翻源码。
数据库与缓存的入口在初始化阶段一并对齐：按主机、端口、库名对上 dbx 里已有的连接，
记下 `connection_id`，初始化完就能直接拿它查库；
服务地址落成 browse MCP 可直接用作允许来源的完整地址。
技能只产出这两份文件，不接手业务开发；交付之后由 `AGENTS.md` 约束，Agent 再按它进入各服务子仓库干活。

### 适用

- 工作区已存在，根目录下有一个或几个 Git 仓库，首次接入 Agent。
- 服务端口或连接配置变化，需要重新初始化。
- 需要确认某个仓库的用途、端口与启动方式。

### 不适用

- 创建工作区、调整目录结构、初始化 Git。
- 启动、重启、停止服务。
- 编写业务代码或执行接口测试：这一步发生在交付之后，归属 `AGENTS.md` 管。

## 前置条件

### 必要输入

- 工作区根目录，即当前工作目录；仓库放在一层或几层子目录里都算。
- 本次是首次初始化还是重新初始化。

### 参考模板

- [服务清单模板](assets/workspace-template.md)：写 `workspace.md` 时套用。
- [服务清单样例](assets/workspace-example.md)：不确定拆分粒度时对照。
- [约束文件模板](assets/agents-template.md)：写 `AGENTS.md` 时套用，里面只有一份约束清单。

### 工具检查

开工前先跑一次例行检查，确认 browse 与 dbx 两个 MCP 可用。
只靠工具调用验证，不查 PATH、不装东西、不改 MCP 配置。

- dbx：调 `dbx_list_connections`，返回连接表即通过；报错或工具不存在即不可用。
- browse：调 `browse_status`，返回浏览器列表即通过；服务在但没浏览器连着，也算半可用。
- 两个各查一次，结果写进交付；中途再遇到不可用不重复探测。
- dbx 不可用时：`connection_id` 全写 `待建`，跳过匹配，不假装已连通。
- browse 不可用时：地址照记，在交付里说明后续页面验证不可用。
- 确认工具可用前不开始初始化，避免初始化完才发现拿不到 `connection_id`。

### 工具用法

- dbx 的元数据与查询工具大多用 `connection_id` 定位连接，清单里存的就是这个值，拿去就能用。
- dbx MCP 只用于只读盘点：拉现有连接，按主机、端口、库名对上就记下 `connection_id`。
- 不在 dbx 里建连接、改连接、删连接；缺什么提示用户自行处理。
- browse MCP 不用预先建会话：服务表里前端那一行即入口，到用时才塞进 `session_new` 的 `allowedOrigins`。

### 重复初始化

- 重复执行就是重新盘点一遍，不产生副作用：不建连接、不启动服务、不动仓库 Git。
  唯一的写操作还是根目录那两个文件。
- 先读现有的 `workspace.md` 与 `AGENTS.md` 当基线，按实际结果逐项比对。
- 只改有变化的字段；用户手加的内容保留，不整份覆盖。
- 清单里有、实际已找不到的条目列出来问，不擅自删。
- 新出现的仓库、服务、连接照常补进去。

### 信息缺失处理

- 某项信息找不到时留空，在交付里说明，不填默认值，不猜端口。
- 配置在 Nacos 等配置中心时标为未确认，在交付里说明，不推测实际值。

## 需要什么

不规定去哪找。按每个仓库自己的结构判断，配置可能分散在配置文件、环境变量、
启动脚本、容器编排或代码常量里。

### 仓库

- 工作区里有哪些独立仓库，各自目录与整体用途。
- 仓库级别的事实：语言、框架、单体还是微服务。
- 这条信息来自哪个文件，或来自用户口述。

### 服务

- 每个仓库里有哪些可独立启动的单元。微服务仓库要展开到网关、用户、管理等具体服务。
- 每个服务的用途与访问地址，前端仓库的页面地址也算一条服务。
- 前端那条是 browse 的入口，后续页面验证从它开始，其余服务地址供探测与接口联调。

### 基础设施

按类型收集，不同类型用得到的字段不同，只填该类型存在的项。
默认只收集关系型数据库与缓存两类；用户当场要求补其他类型时才加。
列的顺序与样例保持一致，不额外加名称列，身份靠类型、主机、端口与库名表达。

- 关系型数据库：类型、主机、端口、库名、账号、密码、`connection_id`。
  类型按 dbx 的驱动名写，如 `mysql`、`postgres`、`sqlserver`、`sqlite`。
- 缓存：类型、主机、端口、库号、密码、`connection_id`。
- 用户要求补充的其他类型，如消息队列、对象存储、配置中心，先问清要哪些字段再落表，不自作主张扩展。
- 主机写 IP 或域名，端口单独一列，不合并成 `主机:端口`。
- 类型、主机、端口、库名、账号、密码要凑齐，用户手工建连接时直接照抄这些字段。
- 主机、端口、库名三个字段要和 dbx 里已有连接对得上，才能拿到 `connection_id`。

### 判断原则

- 所有结论都要能指回一个文件或一次用户口述，指不回去的不写进文件，在交付里说明。
- 找不到就停，不猜端口、不套框架默认端口、不假设地址。
- 同一项在多个文件里不一致时，列出候选并交给用户裁决。

## 执行步骤

### 步骤 1：检查两个 MCP

- 操作：
  - 调 `dbx_list_connections` 与 `browse_status` 各一次，记下可用性。
  - 不可用的按 **工具检查** 的降级分支处理，不装东西、不改配置。
- 完成标志：
  - 两个 MCP 的状态已明确，可用就继续，不可用就带着降级方案继续。

### 步骤 2：识别仓库与拆分服务

- 操作：
  - 列出一级与二级子目录，识别独立仓库，非仓库目录也照常盘点。
  - 逐个判断仓库的用途与技术栈，参考依赖、包名、配置片段与 README；只有一个仓库也照这个流程走。
  - 微服务仓库继续展开到各服务模块，与仓库目录区分开。
- 完成标志：
  - 仓库与服务各有一份清单，无法判定的在汇总里标为未确认。

### 步骤 3：收集所需信息

- 操作：
  - 已有 `workspace.md` 与 `AGENTS.md` 时先读一遍当基线，只补差异，不整份重写。
  - 按 **需要什么** 逐项收集，允许跨文件交叉验证。
  - 每项填进模板对应的列；基础设施按类型填进对应小节，用不到的类型不回填，也不留空表。
    证据只记在步骤 4 的汇总表里，不写进 `workspace.md`。
  - 冲突与缺失不写进文件，留到交付时列出。
- 完成标志：
  - 该填的字段都填了，确实没有的留空，未坐实的不写进文件。

### 步骤 4：一次性确认

- 操作：
  - 输出汇总表，列为服务、仓库、用途、地址、证据、未确认项；证据是这一轮的核对凭据，不写进文件。
  - 仓库级的未确认项单独起一段，写明哪个仓库、卡在哪、需要用户确认什么，不塞进服务表。
  - 冲突项给出候选与推荐值，不自行裁决。
  - 服务表的未确认项与仓库层那一段一次问完，不逐条追问。
- 完成标志：
  - 用户已确认，或明确接受当前推断值。

### 步骤 5：对上 dbx 连接

这一步是初始化的一部分：先把 ID 对上再写文件，写完就能直接拿去查库。

- 操作：
  - 用 `dbx_list_connections` 拉现有连接，拿到每条的类型、主机、端口、库名与 ID。
  - 按主机、端口、库名与清单逐条对照，命中就把它的 `connection_id` 填进该列。
  - 库名对不上或清单里没写库名时，退到主机加端口匹配；仍有多条候选就列给用户选，不猜。
  - 没有命中就写 `待建`，同时把该条的类型、主机、端口、库名、账号整理成一段可照抄的信息，
    提一句可以用 `dbx_add_connection` 建，具体建不建、怎么建由用户定。
  - 不在初始化期建连接、不传密码、不改已有连接。
  - `connection_id` 从 `dbx_list_connections` 的 ID 列原样抄，不做任何改写。
- 完成标志：
  - 每条数据库与缓存连接要么是对得上的 `connection_id`，要么标 `待建`，没有空值。

### 步骤 6：写入并交付

- 操作：
  - 套用模板在根目录写 `workspace.md`，只放事实。
  - 套用模板在根目录写 `AGENTS.md`，只有约束清单，不写文件说明、工具用法与启动流程。
  - 交付按 **交付内容** 一节给全，写完再对照 **验收标准** 自查一遍。
- 完成标志：
  - 两个文件都在根目录，未落入任何仓库内部，技能到此结束。

## 约束

以下约束只管本次初始化：从开工到交付那一次为止。交付完后照常开发，仓库改动与提交按仓库自己的规矩来。

### 初始化边界

- 初始化期间只读，不修改仓库文件，不改动它们的 Git 状态。
- 只写工作区根目录的 `AGENTS.md` 与 `workspace.md`，别处一律不动。
- 不读 `node_modules`、`target`、`dist`、`.git` 内部。

### 服务与端口

- 不启动、不重启、不停止服务，不改端口，不结束进程。
- 地址只来自实际证据、用户口述或实测，不猜端口、不扫端口段、不遍历 `127.0.0.1`。
- 地址里的主机统一写 `127.0.0.1`，不写 `localhost`，避免解析与跨域判断不一致。

### 敏感信息

- 账号密码只写进 `workspace.md`，不写入任何仓库。
- 对话中展示时掩码为 `***`，需要原文时由用户自己打开文件。
- 密码不传给任何 MCP 工具，不进日志、不进提交。

### dbx 工具

- dbx 只做只读盘点：调 `dbx_list_connections`，不建、不改、不删连接，不调 `dbx_duplicate_connection`。
- 不在初始化期传密码给 `dbx_add_connection`，也不替用户配密钥提供者，建连接由用户自己做。
- 初始化期不跑插入、更新、删除与 DDL，只跑读取类查询。
- 一条清单对不上唯一连接时交给用户选，不按端口邻近或驱动相近去猜。
- 两个 MCP 都不可用时只产出两个文件，如实说明未做对齐，不报告成已完成。

### 异常处理

- 单个文件读取失败时跳过，在交付里说明，不中断整轮初始化。
- 用户对推断值提出异议时以用户为准，汇总与交付里的证据注明来源为用户口述。
- 部分完成时说明已初始化与未初始化范围，不报告全部成功。
- 重复初始化时，只改有变化的字段，用户手加的内容保留。

## 输出与验收

### 交付内容

- 工作区根目录的 `AGENTS.md` 与 `workspace.md`。
- 两个 MCP 的检查结果：dbx 可用与否、browse 可用与否。
- dbx 与 browse 都不可用时只交文件，并说明未做连接对齐，页面验证留给后续。
- 服务摘要表、仓库层未确认项与未确认项清单。
- 重新初始化时的差异摘要：新增、变更、待删候选、未变。
- `connection_id` 的对上结果：对上几条、几条标为 `待建`、哪条有多候选待用户选。

### 验收标准

- `workspace.md` 覆盖根目录下所有仓库，没有遗漏或多算。
- 开工前已确认过 dbx 与 browse 的可用性，工具不可用的降级执行了，没有当成已完成。
- 仓库一节只写仓库级事实，服务一节展开到每个可独立启动的单元，微服务不合并成一条。
- 每个对外服务都有访问地址；没有地址的服务在用途列写明它做什么。
- 服务地址缺失时在交付里列出，不写进文件。
- 基础设施按类型分节，默认只有关系型数据库与缓存，用户要求时才出现其他类型。
- 各节列名与顺序按模板约定，默认两节与样例一致，不加名称列，不合并主机与端口。
- 主机与端口分列书写，库名、库号与 `connection_id` 按类型落到对应列；用户要求补充的类型按当时约定的列写。
- 每条数据库与缓存连接都在 `connection_id` 列写着从 `dbx_list_connections` 取来的 ID 或 `待建`，没有空值，`待建` 项在交付里列出。
- 写下的 ID 能在 `dbx_list_connections` 里对回去，直接拿去调 `dbx_execute_query` 即可。
- 有多条候选且无法唯一定位的，已交用户确认，没有自行挑选。
- 仓库级未确认项单独成段，没有塞进服务行，也没有造伪行。
- 服务表地址含协议与端口，可直接用作 browse 允许来源；主机全部是 `127.0.0.1`，没有 `localhost`。
- 每一项在汇总或交付里都有证据位置，或标注为用户口述。
- 未使用的连接不填，未坐实的信息不写进文件，在交付里说明。
- `workspace.md` 只放事实，不设待确认一节。
- 密码在对话输出中已掩码。
- `AGENTS.md` 只有一个约束清单，不分节，不含文件说明、工具用法与启动流程，也不重复服务清单。
- 两个文件都在根目录，未落到任何仓库内部。
- 重复初始化时只改有变化的字段，用户手加内容被保留，清单里已消失的条目只在交付里列出，没有被静默删除。

## 示例

首次初始化一个含 `easy-cloud` 与 `easy-cloud-ui` 两个仓库的目录，`easy-cloud` 是微服务。

> 已生成 `AGENTS.md` 与 `workspace.md`。
> 仓库两条，服务四条，`easy-cloud` 已展开到网关、认证、对话三个服务，`easy-cloud-ui` 一条页面。
> 基础设施两类两条，分成数据库与缓存两节，都已对上 `connection_id`。
> 未确认一项：`easy-cloud-chat` 的端口配置与代码默认值不一致，待实测。
> 所有地址为代码声明值，尚未实测。

用户实测后回报 `easy-cloud-chat` 实际监听 8082，于是补上清单，并在汇总里把那条的证据注明为用户口述。
