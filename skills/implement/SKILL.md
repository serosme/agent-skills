# Implement

## 目标

在一个会话里完成实现：先把实现草案讨论清楚并经开发人员确认，再写代码与单元测试，跑通后报告改了什么。

输入形式不限：一段需求、一个功能点、一个 issue、一句想法、一份设计草案，或要改造的现有代码；有边界说明、时序草图、接口文档就一并看，没有也能做。

本技能只负责实现；接口与页面流程验证不在这里做。

## 前置条件

### 输入

至少一种：

- 需求、功能点描述、issue 或想法。
- 设计草案、接口说明或数据约定。
- 要改造的现有代码。

### 缺失处理

- 输入只有一句话、看不出范围时先问，不自行补全。
- 需求涉及多个可独立交付的部分、没说明这次做哪部分时先问，不替开发人员决定。
- 范围或业务规则有歧义时先问；问不出来就按最小合理解释写进草案并标明推断。
- 语言、测试框架或测试命令判断不了时先问，不猜。
- 仓库没有测试框架时先问是否引入；不引入就说明无法补可运行的单测，停下。
- 依赖装不上或测试命令跑不起来时报告并停，不换框架，不装全局工具。

## 执行步骤

### 步骤 1：读输入

- 读需求、文档、要改的代码与相邻测试，确认四件事：范围、入口与落点、仓库约定（语言、测试框架、目录、命名、断言与异常写法）、测试命令。
- 测试命令优先取 `AGENTS.md` 的命令表，没有就从构建声明文件里找。
- 说不清的先问，不带着猜测往下走。
- 完成标志：能说出做什么、改哪里、用什么框架、跑哪条命令。

### 步骤 2：出草案并等确认

- 在会话里给一份短草案。五项：
  - 范围：做什么、不做什么；推断的部分标明。
  - 方向：按需要讲清架构与分层、技术栈、设计模式及选择理由；有两条以上明显不同的方案时列 2 到 3 条，各用一句话说做法与代价，并标明推荐；只有一条就直接写。
  - 改动：改哪些文件，新增或修改哪些类与方法，各自做什么。
  - 单测：每个单元至少一正一反，反面写清非法输入、失败分支或边界值。
  - 取舍：本次不碰的相邻能力、暂缓的做法与原因。
- 草案控制在一屏以内，不贴整段代码；签名与数据结构可以贴几行。
- 写完自检：范围里的「做」都能兑现，「不做」一条不碰。
- 开发人员删减、合并、修改或推翻草案都照办；只否决、没给方向时问一句，不自行推演。
- 确认前不写代码。
- 完成标志：开发人员明确确认。

### 步骤 3：实现并补单测

- 按草案做，一个最小单元（一个方法或一个类）写完就按 **单测** 约束补它的测试，再进下一个。
- 单测用仓库既有框架、目录与命名；没有测试目录时按仓库惯例建一个。
- 依赖按 **单测** 约束替掉，保证单测能独立跑。
- 每完成一个单元就跑一次对应测试，未通过就先修，再往下做。
- 完成标志：草案里的单元都实现，单测全部通过。

### 步骤 4：跑全量并报告

- 按仓库的测试命令跑全量；命令表要求构建或 lint 时一并跑。
- 对照草案与验收标准逐条核对，修正后重查：多改的删掉或先确认，少做的补上；不一致的地方写进偏差。
- 核对工作区改动，确认范围外的源码与依赖未动，配置与部署脚本未被改动。
- 按 **交付** 清单报告，然后停。
- 完成标志：报告已给出，停在报告处。

## 约束

### 范围

- 只做草案确认过的范围；实现中发现要多改或范围变大时，先问，确认后改草案再动手。
- 草案里「不做」的行为一条都不做，顺手能做也不做。
- 不重构范围外的代码，不擅自升级或新增依赖，不格式化范围外的文件，不改配置与部署脚本，不提交。
- 业务规则由开发人员定；说不清的先问。

### 草案

- 草案不落盘；范围变了就改草案，不攒到最后。
- 先出完整草案再讨论，有多种方案时推荐必须给，采纳与否由开发人员定。
- 方向确认后不边写边改；确需调整时停下说清，先改草案再继续。

### 单测

- 最小单元是业务逻辑里能单独验证的一个方法或一个类，不是接口、页面或整条流程。
- 正面与反面都要有。只测正常路径、只测异常、只断言不抛异常都不算过。
- 每条被守住的业务规则都要有成立与不成立两种断言。正面断言返回值、状态变化或落库结果；反面断言拒绝方式，例如异常类型与消息、错误码、兜底值。
- 一个用例断言一件事；有分支的方法按分支拆用例，测试名写清场景与期待。
- 用例之间不依赖执行顺序，不共享可变状态，数据在用例里就地造。
- 不为让测试通过而改断言、放宽期待或跳过用例。实现错改实现，测试错改测试并在报告里说明。
- 含业务逻辑的方法都要有对应测试；getter、DTO、纯委托由上层用例覆盖，不为它们硬造用例，报告里说明。
- 依赖用仓库既有 mock 或 stub；没有就用手写 fake，仍不够时先问是否引入测试依赖。
- 外部依赖（时间、随机数、ID）要能替换，用仓库已有做法；没有就选最小的依赖注入，不引框架。
- 单测必须能独立跑：不连真实数据库、缓存、网络与第三方服务。

### 异常

- 已有测试因本次改动失败时先判断原因：本次改动导致的就修，与本次无关的报告并问，不顺手改无关测试。
- 草案做法走不通或单测修不过时，停下说明现状与可选做法，改草案再继续；不硬套，也不把未通过说成完成。
- 中途叫停时报告已完成的单元、已改的文件与未完成项，不把半成品说成完成。
- 测试结果里有跳过或未执行的用例时，报告条数与原因，不当成全绿。

## 输出与验收

### 交付

在会话里报告，不写报告文件。

- 改动文件清单。
- 新增或修改的测试文件与用例数。
- 测试命令与结果，含通过、未通过、跳过、未执行条数；跑了构建或 lint 时一并列出。
- 未单独测的样板方法及原因；没有就不写。
- 与草案的偏差；没有就说不存在。

### 验收标准

- 草案五项已在会话里给全，并经开发人员确认；推断部分已标明，确认前没有动代码。
- 改动与草案一致，多改的已删或已确认，少做的已补。
- 草案里「做」的范围全部兑现，「不做」一条没做。
- 每个新增或修改的最小单元都有对应测试，其中含业务逻辑的方法都被用例覆盖；有分支的方法每个分支都有用例；getter、DTO、纯委托这类样板方法未测时报告里已说明。
- 每个单元至少一条正面与一条反面断言，每条被守住的业务规则都有成立与不成立两种断言；断言落在返回值、状态变化、落库结果或拒绝方式上。
- 用例按分支拆开、互不依赖，一个用例只断言一件事，测试名能看出场景与期待。
- 测试放在仓库惯例的测试目录，用既有框架与命名；引入新框架或全局工具时已确认。
- 单测能独立跑，不依赖外部服务。
- 仓库测试命令通过；命令表要求的构建或 lint 也通过；有跳过或未执行用例时已报告条数与原因。
- 没有为让测试通过而改断言、放宽期待、跳过用例，或用改实现掩盖问题。
- 配置与部署脚本保持改动前状态；范围外的源码也保持改动前状态；依赖变更都在草案里确认过；没有提交。
- 报告在会话里给出，与实际一致，未验证的部分已标明。

## 示例

输入：「聊天页接真模型，带最近 7 天记录，单次最多 200 条」，另有现有聊天模块代码，没有其他文档。

草案在会话里给五项：范围做「调模型、提示词取最近 7 天且最多 200 条、失败时保留用户消息并给出提示」，不做「流式、重试、多模型切换」；方向按现有分层拆出 `PromptBuilder` 与 `ModelClient`，沿用仓库的 Spring、JUnit 5 与 Mockito，不引新依赖；改动为新增两个类并调整 `ChatService`，单测为三个类各列正反用例；取舍是提示词与超时先写成常量，暂不做配置化，等有需求再开。开发人员把「给出提示」改成「允许重发」，其余照办，确认。

实现时先做 `PromptBuilder.build`：正面断言按时间升序带出 7 天内的消息、250 条只留最近 200 条；反面断言没有消息时返回空提示词、8 天前的消息被排除。再按序做 `ModelClient.send` 与 `ChatService`，每个单元补齐正反用例并跑通。最后跑仓库测试命令，按交付清单报告改动文件、用例数、测试结果与「无偏差」，然后停。

边界案例：输入只有「做个登录」一句。先问清登录方式、账号来源与失败表现，再出草案；问不出来就按最小解释写进草案并标明推断，不自己补成一套完整方案。
