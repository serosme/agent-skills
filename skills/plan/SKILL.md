# Plan

## 目标

把一个需求拆成功能块，逐块定边界，产出一批可据此执行的文档：

- `index.md`：功能块、每块做完能看到什么、依赖、文档链接。
- `<编号>.md`：这一块的做与不做。

拆分让一块能独立做完、独立验收，不必整个需求一次交付；所有块合起来覆盖需求，一个能力只归一块。

做与不做用来约束后续实现：`做` 的才做，`不做` 的不得多做，没写到的先问。文档只写范围，不写方案、技术选型、实现步骤、测试用例与代码，也不记录流向与进度。

本技能只用自己和需求就能跑完：输入一个需求或一份已有的范围文档，产出 `index.md` 与 `<编号>.md`，不需要任何其他技能、模板或外部产物做前置。流程图、时序图、方案与实现步骤都不在本技能产出。

有四个停顿点：拿到确认前不写文件、不往下走；拿不到确认就停在原地等回复，不替开发人员做决定。`index.md` 的链接回填与复位、改编号或需求名带出的标题与一句话校正属校正，不单独设停顿点：

1. 拆分草案只给在对话里，确认后立刻写 `index.md`，不把确认稿留到下一轮。
2. 写完 `index.md` 先问做哪一块，没点名、没确认就不动。
3. 做与不做一次给全草案，确认后写入文档。
4. 一块结束后问是否继续下一块；覆盖核对时并入、拆分、新增也要再确认。

## 前置条件

### 必要输入

- 需求、issue 或一个想法。
- 继续写某块时，给出 `docs/<需求名>/`、`index.md` 或需求名，并指明编号或名称；只给需求名时按 **输出位置** 找默认目录，产物放在指定位置时必须给出路径或 `index.md`。

### 判断从哪里开始

动手前先找一次已有产物：用户给了路径或目录就只查该处，没给就查 `docs/` 下有没有同名目录。判据是需求名相同，或目录里 `index.md` 的标题与需求名相同。

- 没找到：先看是不是「上一轮拆分已确认、`index.md` 还没写入」——是就重展确认稿，确认后直接进步骤 3；跨会话确认不了这段经历、或本来就不在这个状态，就当新需求，走下面「没有 `index.md` 也没有文档」这一支。
- 找到了：按下面的已有分支走，不另建目录。
- 名字只是相近、并不相同的（例如已有「AI 聊天」，新需求是「AI 聊天导出」）：先问一句是同一个需求加块，还是新需求另开目录，问清再选分支。

按产物现状选一条走：

- 没有 `index.md` 也没有文档：步骤 1。
- 有文档没 `index.md`：按步骤 1 到 3 补 `index.md`，已有文档不重写（已定结论不改，标题与一句话不合模板时按步骤 3 修正后再回填）；既有文件名里的编号就是拆分骨架，草案必须包含这些编号，覆盖不到的需求另给新编号；名称与「做完能看到什么」按文档里的一句话重建，先给草案确认，再按 `<编号>.md` 回填链接。
- 有 `index.md`、链接与目录一致：跳步骤 4，先问做哪块。
- 有 `index.md`、目录里有 `<编号>.md` 但「文档」列填着 `-`：先按文件名回填链接，再跳步骤 4，先问做哪块。
- 有 `index.md`、「文档」列有链接但对应文件不存在：按这块还没有文档处理，先把「文档」列复位成 `-`，再跳步骤 4。
- 有 `index.md`、目录里缺 `<编号>.md` 且「文档」列为 `-`：正常未写状态，跳步骤 4，先问做哪块。
- 目录里有 `index.md` 没列出的 `<编号>.md`：先问是加块还是删文件，不自行加块。
- 要重新拆分、加块或调整方案：回步骤 1；没要求就保持原方案。
- 已有某块文档：在原文件上改，已定结论不再问。

### 输出位置

- 默认 `docs/<需求名>/`，目录名原样取需求名：中文照写，不转拼音、不缩成短横线，ASCII 照原样；开发人员指定位置时按指定。需求名含 `/` 等文件系统不允许的字符时先问怎么处理，不自行替换。
- `index.md` 与 `<编号>.md` 同目录；文件名只写编号；文档标题写 `<需求名> / <编号>`，让单份文档脱离目录也认得出归属；功能块名称只写在 `index.md` 的表格里，不进文件名与文档标题。

### 参考文件

- [模板](assets/templates.md)：写入前读一次。
- 示例：`assets/ai-chat/`，对照用，不必通读。

### 缺失处理

- 判断不了涉及哪些部分，或一块只有一句话看不出要改什么：先问范围。
- 接口名与表名：查不到先问一句；定了就写进去，不标未实现。
- 编号在 `index.md` 里找不到：先问，不自行加块。
- 一块确实没有用户可见的结果：先问是否还算一块，不硬塞一个凑数的。
- 覆盖核对时没有需求原文：先要一份，或按口述范围核，不凭记忆。
- 补的功能点超出「做完能看到什么」：先问是加进这块还是另开一块。

## 执行步骤

### 步骤 1：拆分功能块

用于首次拆分与调整拆分。

- 读需求与相关代码、文档，够判断涉及哪些部分即可。
- 可拆可不拆时先给结论：需求牵扯面广、本来就是两件不同的事就拆；本来就小就只保留一块，一块也算正常结果。
- 按能独立完成、独立验收的事拆；同一件事要分几步才能用上时，按先能用、后补的顺序切。
- 每块一句话写「做完能看到什么」，必须能演示；带「并且」就拆成两块。
- 定依赖：只有必须先完成、后一块才能开始的才写编号，否则写 `-`；确认无环。
- 补建或调整时，既有 `<编号>.md` 的编号就是骨架：草案必须包含这些编号，覆盖不到的需求另给新编号，已确认的块不重排。
- 对话里给草案表：编号、功能块、做完能看到什么、依赖，附一句拆分理由与要不要拆的结论；调整时把受影响块与依赖变动一起列出。
- 草案不写文件。
- 完成标志：每块能独立交付、粒度相当；首次拆分覆盖需求全部能力，调整只覆盖变动部分；既有编号未经确认不改，经确认的删块与合并不算丢失。

### 步骤 2：确认拆分方案

- 删、并、改、推翻都照办；合并或拆分后同步改「做完能看到什么」并重排依赖。
- 受影响块的文档「一句话」与标题里的需求名跟着同步改写，别只改 `index.md`。
- 有不同意见先给建议，采纳与否由开发人员定；只说不行、没说方向时问一句，不自行推演。
- 推翻就回步骤 1。
- 完成标志：拆分与顺序已确认，受影响块要改的字段已列清。

### 步骤 3：写入 `index.md`

- 按模板写；已有 `index.md` 就增改，不重写已确认的行；没写文档的块「文档」列填 `-`，已有文档保住链接。
- 回填链接前先核对既有文档：标题是 `<需求名> / <编号>`、一句话与表格该行一致；不一致先改文档再回填。
- 报路径，问继续写哪一块还是先停止。
- 停止时报告 `index.md` 路径、块列表、下一个可开工的编号与文件树，然后停。
- 完成标志：文件与确认稿一致、依赖无环、已问是否继续。

### 步骤 4：选定功能块

- 已点名就用；没点名就问，只有一块也要报编号与名称确认。不默认从 01 开始。编号或名称在 `index.md` 里找不到就按缺失处理先问，不自行加块。前序块还没写完文档时提醒一句，开发人员坚持先做这块就照做。
- 看这块已有文档：没文档或做与不做没确认 → 步骤 5；已确认没落盘 → 步骤 5 重展同一张表、确认后写入；已确认且已落盘 → 步骤 6。
- 开发人员要求给已确认的块补行，或步骤 6 覆盖核对要补行时走步骤 5：整表重出并重编序号，已定结论的行不再逐条追问，只请开发人员看新增与改判的行。
- 没有待写的块（每块都已有 `<编号>.md`）→ 步骤 6 做覆盖核对。
- 一次只做一块。
- 完成标志：编号与「做完能看到什么」明确，待补部分明确；没有待写块时已确认。

### 步骤 5：起草、确认并写入做与不做

- 读这块的代码与文档，够判断入口、行为与相邻能力即可；上下游没写明的不自行补。
- 先自己把 **边界清单** 的七个角度过一遍，能定的都定下来，再把整张表一次给全：不拆成多轮提问，不报进度、不写文件；边界取舍拿不准的按推荐填，表外按序号点出哪几行是推断的，交给开发人员改；只有接口名、表名这类查得到的事实不确定时，才先问一句。
- 行数明显偏多时（例如超过 20 行），再在表外按序号补一句哪几行请重点看。
- 请开发人员补漏、改判、删行；他按序号指认的那几行照办，其余按草案保留。
- 只说不行、没说怎么改时问方向；与现有行为冲突或成本明显不划算时当场指出。
- 改完再整表展示一次；确认后写文件：新文档写标题、一句话、这张表与需要时的备注；已有文档改写这张表，保留已确认的行，只增改受影响的行并按新表重编序号，同时同步改写标题与一句话。
- 完成标志：表已确认并写入，每行有序号；七个角度都过了一遍，确实不适用的已在备注里写明原因；每条 `做` 都追问过紧挨着它外面的能力；每条 `做` 能判断是否完成，合起来能兑现「做完能看到什么」；`不做` 至少 3 条，不够时理由写在备注里。

### 步骤 6：收尾并问是否继续

- 把这块链接填进 `index.md`；没处理新块时跳过。
- 还有未写的块（目录里缺 `<编号>.md`）：报当前文档路径与编号、剩余块、下一个可开工的编号与文件树，问继续还是停；要继续就回步骤 4，说停就停，不主动提议实现、不自动写下一块。
- 全部写完（每块都有 `<编号>.md`）：对照需求原文核一遍（没有就先要一份，按口述范围核），每项能力都在某块的 `做` 或 `不做` 里。遗漏能并入就并入，先确认放哪块、做还是不做，按步骤 5 更新并再确认，只补 `不做` 也走步骤 5；重复的确认留在哪块并同步改；删掉的行让某项需求失去归属的，按遗漏处理；要新增块就回步骤 1 重新拆分确认，再按步骤 3 到 6 补齐。改完重核，无遗漏后报结果与文件树，停。
- 报告前：还有剩余块只报进度、不做验收；全写完则对照 **验收标准** 逐条核对。任一条不过就按类型回退：`index.md` 的摘要、块列表、链接与文件树类回步骤 3；文档表格、序号与备注类回步骤 5；拆分、粒度、依赖类回步骤 1；多余的块与文件按删块、删文件处理，漏掉的确认重新走一遍；改完重核，全过再报。
- 完成标志：链接就位；有剩余块时已定继续或停；全写完时验收全过、覆盖核对通过并已报告。

## 约束

### 名词

- 功能块：`index.md` 一行，对应一份文档。
- 功能点：做与不做表的一行，值只有 `做`、`不做`。
- 序号：做与不做表首列的行号，一行一个，从 `01` 起。
- 编号：功能块的号，从 `01` 起顺序编，删块后不重排。
- 可开工的编号：依赖列里的块都已有 `<编号>.md`、本块还没有 `<编号>.md` 的那些块编号。可能不止一个；报的时候先报编号最小的，其余一并列出。

### 拆分

- 一块是开发人员能独立演示的一件事，不能只是「设计完成」。
- 不按层、不按文件、不按工期均分。
- 拆分只定范围与先后；块内做与不做留到步骤 5。
- 一个能力只归一块。
- 依赖指必须先完成、后一块才能开始的那一块；只复用产物不挡路的写 `-`。
- 粒度齐平指各块体量相当，没有一块明显大于其余几块。
- 块改名只改 `index.md` 表格；改号要同时改文件名、文档标题与链接。需求改名要同时改目录名、`index.md` 标题与全部块文档标题，改完按验收的一致性条目核对。
- 删块：删表格行与文档，其他块指向它的依赖改 `-` 或经确认改指。

### 边界清单

列草案时按这些角度一次过完；七个角度是下限，不是可选项，不逐项追问。

- 闭环：输入从哪来、经过什么、到哪去、谁收到、之后怎么变。
- 数据：写哪张表、一笔写几行、怎么核对。
- 状态：是否持久化、留多久、刷新或换端是否还在。
- 异常：空、满、重复、失败、无权限、并发，至少三种有结论。
- 反馈：等待时看到什么、失败提示、能否重试、等待期间能否继续操作。
- 外围：相邻能力、上下游、常见外围功能，逐条给做或不做。
- 成本与更简单的替代：可能改变范围时列出，不展开。

某个角度对这块确实不适用时，在文末备注里写一句为什么；没写原因的按漏问处理，回步骤 5 补。

### 做与不做

- 一张表，三列：序号、功能点、做与不做；`做` 行在上，一行一个功能点。
- 序号按当前表行序从 `01` 起连续编，`做` 行在前、`不做` 行在后；每轮改完整表重出时按新表重编，不留空号。
- 一行只写一个功能点：可以带「…时」这类限定，但不得在一行里混写做与不做，不得用「与」把两件独立的事并列，不写进度与方案。
- 只写短句，不写段落与背景。
- `做` 要能判断是否完成；`不做` 要是真有人会顺手做的能力。
- 只写这块，不越界到其他块。
- 补「不做」行必走一遍：每条 `做` 都追问「紧挨着它外面的是什么，我们做不做」，一串问到的写成 `不做` 行，没问到的不记。

### 草案格式

一次给整张表，不拆成多轮、不逐行问。

```markdown
| #   | 功能点       | 做与不做 |
| --- | ------------ | -------- |
| 01  | <具体功能点> | 做       |
| 02  | <具体功能点> | 不做     |
```

- 表外只写三类，各一句：哪几条是推断的、哪几行请重点看、定不下来的点；都写序号，必要时在序号后带一句名称，不让开发人员自己数行。
- 推断与重点看只用于对话，确认后不留在文件里；需要落进文件的只限备注允许的两类，见 **边界**。
- 没把握按推荐填，不留空、不标待定。
- 定不下来的点一次列全，由开发人员一起定；表外点名以最近一次展示的表为准，改过表再点名先对一遍序号。

### 边界

- 不写设计、方案、选型、实现步骤与测试用例，不写代码。
- 不画时序图与流程图，不写流向；流向与验证不归本技能。
- 代码里缺的上下游按开发人员说明补，对话里逐条指出。
- 代码与描述不一致，或代码本身有绕行、跳过、重试时，按实际写进表里并标出问一句，不自判对错。
- 表里写「要不要做这件事」和做完怎么判断，不写怎么改；代码现状只点出影响范围的地方，不写修法。
- 范围由开发人员定；表里新增行先点出来，由开发人员定去留。
- 中途停止：已写入的保留，下次从步骤 4 继续，已写入的不再问；拆分已确认但 `index.md` 没写入的，重展确认稿直接进步骤 3；表草案没确认就重出；确认了没落盘就重展一遍再写。
- 文档只记录范围：标题、一句话、做与不做表，需要时加一段备注（最多两行）。备注只写两类：某一角度不适用的原因、`不做` 不足 3 条的理由；几个角度都不适用时合并成一句写；不写过程、背景与方案。没有完成状态，没有流向。
- 没得到继续指令，不写下一块，也不主动提议开始实现。

## 输出与验收

### 模板

见 `assets/templates.md`，写入前读一次；文件名与位置按 **输出位置**。

### 交付内容

- `index.md` 路径。
- 本轮写入的文档路径与编号。
- 下一个可开工的编号：取可开工编号里最小的那个，其余可开工编号一并列出。
- 文件树，至少含 `index.md` 与本轮文档。
- 只要求拆分时，报路径、块列表、可开工的编号与文件树，然后停。

### 验收标准

- `index.md` 在 `docs/<需求名>/` 或指定位置；目录名原样取需求名，中文照写，不转写、不缩成短横线；需求名含文件系统不允许的字符时，按开发人员确认的写法。
- 每块能独立交付、粒度相当；「做完能看到什么」能演示，不含「并且」。
- 依赖无环且符合定义；需求小时只有一块，且已确认。
- `index.md` 的需求摘要只概括需求本身：没有补需求里没有的内容，也没有方案与拆分判断。
- 一块一份 `<编号>.md`，与「文档」列对得上；文档里只有标题 `<需求名> / <编号>`、一句话、`## 做与不做` 小节与其中的一张表，需要时一段备注（最多两行，只写角度不适用的原因或 `不做` 不足 3 条的理由，不写过程、背景与方案），没有完成状态与流向。
- 文档标题里的需求名与 `index.md` 的文件标题一致；标题里的编号与文档的一句话，与 `index.md` 对应行一致。改过号的块，标题、文件名与链接三处都是新编号。
- 表首列是序号，从 `01` 起按行连续编，与最近一次展示并确认的表逐行一致。
- 每条 `做` 能判断是否完成，合起来兑现「做完能看到什么」；`不做` 至少 3 条，不足时备注里写了理由。
- 边界清单七个角度都过过；确实不适用的角度，备注里写了原因。每条 `做` 行紧挨着的外围能力，要么有对应的 `不做` 行，要么备注里说明为什么没有。
- 全部写完后，需求里每项能力都在某块的 `做` 或 `不做` 里，无遗漏、无重复归属。
- 没有字段清单、索引、建表语句、接口签名、SQL、测试代码与用例，也没有方案、选型、实现步骤与图；接口名与表名按缺失处理照写，不算接口签名。
- 拆分与顺序由开发人员认可；只写了 `index.md` 与确认过的 `<编号>.md`，没有额外文件。
- 每次内容写入前都经过对应停顿点的确认；`index.md` 的链接回填与复位、改编号或需求名带出的标题与一句话校正属校正，不单独设停顿点。

## 示例

需求是 AI 聊天：单页一问一答、发出去不必等回复，消息存表，调模型带最近 7 天记录并可附提示词，手机端安卓壳加 WebView，单用户只用一个密码。

拆分：页面与消息存储合并为一块，模型调用、单密码登录、安卓壳各一块，共四块；结论是要拆。草案给在对话里，开发人员改了两处措辞后确认，写入 `docs/AI 聊天/index.md`，「文档」列先填 `-`。

写完后问先做哪块，开发人员选 01。自己先把七个角度过了一遍，整表二十来条一次给全、逐行带序号，表外按序号点出哪几条是推断的、哪几行请重点看。他把「失败提示」留在不做，补了「消息编辑」「消息删除」两条不做，其余保留。确认后写入 `01.md`。

其余块照此处理。全部写完后对照需求核一遍：页面、存表、7 天窗口、提示词、单密码、安卓壳，每项都落在某块的 `做` 或 `不做` 里。

示例见 `assets/ai-chat/`：`index.md` 与 `01.md`；资产目录名沿用 `ai-chat`，示例里的产物路径是 `docs/AI 聊天/`。示例只写 01 一块，实际按依赖顺序逐块写。

```text
docs/
└── AI 聊天/
    ├── index.md
    └── 01.md
```
