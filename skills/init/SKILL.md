# Init

## 目标

在工作区根目录生成一份 `AGENTS.md`，写两部分：

- 现状：仓库名与目录、可独立启动的服务及地址与端口、中间件连接位置、各仓库的常用命令。
- 约束：几条工作约束，供 Agent 在本工作区干活时遵守。

只做盘点和记录，产出这一份文件。写进去的是「Agent 行动前必须知道、且不翻多个仓库就难以确认」的运行期事实与入口：地址、端口、连接位置、启动与校验命令、工作约束。读一次代码就能稳定得到的结构事实不写。

### 适用

- 工作区已存在，根目录本身是 Git 仓库，或根目录的一级子目录里有一个或几个 Git 仓库，首次接入 Agent。
- 服务地址或端口变化，用户要求重新扫描并刷新说明。

## 前置条件

### 必要输入

- 工作区根目录。用户指明路径时以用户为准；未指明时按步骤 1 的定位规则确定，不默认「当前目录就是根」。
- 本次是首次初始化还是重新初始化：按 **来源判定** 的规则判定，用户另有说明时以用户的说明为准。
- 仓库范围固定为工作区根与它的一级子目录；更深的仓库不扫描，写进交付的未覆盖范围。

### 参考模板

- [AGENTS 模板](assets/agents-template.md)：落盘前必读，现状、约束与命令的格式以它为准；以 `> 填写说明：` 开头的行不写入。
- [AGENTS 样例](assets/agents-example.md)：不确定拆分粒度或约束写法时对照。

### 需收集的信息

#### 仓库

- 工作区里有哪些独立仓库，记下仓库名与目录；根目录本身是仓库时目录记作 `.`，仓库名写根目录名。
- 目录位置来自实际扫描或用户口述。
- 扫描范围固定为工作区根与一级子目录；更深的目录不算漏项，但要写进交付的未覆盖范围。

#### 服务

- 每个仓库里有哪些可独立启动的单元，有多个就逐个展开，每个单元各记一行。
- 可独立启动的单元指有独立启动入口的单元，例如独立启动脚本、容器编排里的一个服务定义、`package.json` 的 start 脚本、独立 main 入口或独立进程；一个仓库里同时有多个独立启动入口时按每个单元各记一行，容器编排里每个服务定义算一个单元；只有一个启动入口的仓库记一行。
- 用途写一个短语（不超过约 10 字）概括它负责什么，只用于索引，不写整句、不写说明。
- 每个服务的地址与端口；前端仓库的页面地址也算一条服务。

#### 基础设施

- 记实际存在的中间件与存储：关系型数据库、缓存、消息队列、注册/配置中心、对象存储等；只列实际存在的类型。
- 只记类型、主机、端口、库名或库号；关系型数据库写库名，缓存写库号，其余写主题、命名空间、桶名等最小区分标识，没有就留空；多个 topic 只写主 topic，其余写进交付。
- 主机写实际使用的 IP 或域名，本机部署写 `localhost`，端口单独一列。
- 集群或多节点只写调用方可达的入口（多个入口用逗号分隔）；其余节点、broker 与非主 topic 写进交付，不塞进同一格。
- 配置只在 Nacos 等外部配置中心、本地读不到时，配置项记为未确认；配置中心自身的地址与端口按基础设施记录。

#### 命令

- 每个仓库的安装、构建、测试、lint 与启动入口，按仓库各记一行。
- 命令取自构建或任务框架的声明文件，例如 Node 的 `package.json` scripts、JVM 的 `pom.xml`、`build.gradle.kts`、Python 的 `pyproject.toml`、通用的是 `Makefile` 与 `justfile`，也可以是容器编排、CI 配置或用户口述。
- 仓库自带 wrapper 时记 wrapper，如 `./mvnw`、`./gradlew`，不写依赖本机全局安装的 `mvn`、`gradle`。
- README 或注释里的命令只用于交叉核对；与声明文件不一致时以声明文件为准，并在汇总里说明差异。
- 每条只记命令与一句话用途，不解释参数。
- 项目若有「改完必须跑什么」的约定，整理成约束里的一条。

### 信息缺失处理

- 地址、端口这类关键信息找不到时不要猜，记为未确认，留到步骤 3 一次问完；用户也确认不了就留空，在交付里列出。
- 留空就是不写内容，不放 `待填` 或其他占位符；缺失项统一写进交付。
- 非关键信息找不到时留空，在交付里说明。
- 配置只在 Nacos 等外部配置中心、本地读不到时记为未确认，在交付里说明。
- 命令找不到或与仓库对不上时，记为未确认并列出已查过的位置，不写推测的命令。
- 同一环境内同一项在多个文件里不一致时，列出候选与推荐值，由用户裁决；裁决前不把候选值当结论写进 `AGENTS.md`。不同环境各有一份合法值时按 **服务与地址** 的多环境规则处理。

## 执行步骤

### 步骤 1：定位工作区根并识别仓库

- 操作：
  - 确认工作区根：用户给了路径就用用户给的；没给时按顺序判断——当前目录含 `.git`（目录或文件），或当前目录的直接子目录含 `.git`（目录或文件）（多仓库工作区），则当前目录就是根；否则向上找最近的满足「自己或直接子目录含 `.git`」的祖先目录；仍找不到就请用户给出路径，不猜。判断出的根与用户预期不符时先向用户确认。把确认后的绝对路径记为工作区根。
  - 读根目录现有 `AGENTS.md`，按 **来源判定** 得出「首次初始化 / 重新初始化 / 非本技能生成」三种结论之一，记下来留到步骤 3。
  - 根目录本身含 `.git` 时也记作一个仓库；只列一级子目录，含 `.git` 目录或 `.git` 文件的目录按独立仓库处理；更深层不扫描。
  - 扫描范围内没有任何含 `.git` 目录或 `.git` 文件的目录时中止：说明已查范围与扫描边界，请用户确认路径或补充仓库位置，不产出只剩约束的 `AGENTS.md`；用户给出路径后从步骤 1 重新开始。
  - 按 **需收集的信息** 记录仓库名与目录。
- 完成标志：工作区根已确认并记录绝对路径；来源判定结论已记录，基线全文（或现状四节逐行值与来源、扫描元数据）与基线哈希已记录供步骤 4 比对；仓库清单在根与一级子目录内已齐，扫描范围与未覆盖范围已记录。

### 步骤 2：记录服务、基础设施与命令

- 操作：
  - 按 **服务** 一节的判据展开服务，每个单元各记一行，用途写短语，再记地址与端口。
  - 地址与端口按 **服务与地址** 取，允许跨文件核对；取不到按 **信息缺失处理** 处理。
  - 基础设施按 **基础设施** 一节记录。
  - 按 **命令** 一节收集各仓库的构建与校验入口，写入命令表。
  - 跳过 `node_modules`、`target`、`dist`、`.venv`、`vendor` 等依赖与构建产物目录，不读 `.git` 内部；跳过的目录写进汇总。
  - 单个文件读取失败按 **异常处理** 跳过。
  - 全程只读，不启动、重启、停止任何服务，不改端口。
- 完成标志：每个服务都有地址与端口，或已标为缺失；基础设施只列实际找到的类型；命令表有内容或已标为缺失；跳过的目录已记录。

### 步骤 3：一次性确认

- 操作：
  - 输出汇总，含六部分：
    1. 定位与来源：工作区根绝对路径、扫描范围与实际覆盖边界、来源判定结论、是否纳入版本控制与是否需要脱敏。
    2. 仓库清单（仓库、目录、证据、未确认项）。
    3. 服务表（服务、仓库、用途、地址、证据、未确认项）。
    4. 基础设施表（类型、主机、端口、库名或库号、证据、未确认项）。
    5. 命令表（命令、仓库、用途、证据、未确认项）。
    6. 约束清单（模板自带、用户口述、待确认）。
  - 来源判定结论为「非本技能生成」时，在本次确认里一并让用户选：备份后整份替换 / 合并并保留用户内容 / 中止；用户不选就按中止处理。
  - 首次初始化时固定问一次：有哪些必须、禁止或「先确认再做」的工作习惯要写进约束；用户不补充就只放模板约束。
  - 重新初始化时再加一部分：相对基线的差异（新增、变更、待删候选、未变）。
  - 冲突项、所有未确认项与待删候选一次问完，处理规则见 **信息缺失处理** 与 **重新初始化**。
  - 用户提出异议时按 **异常处理** 处理。
- 完成标志：用户已确认，或明确接受当前结果与缺失项。
- 用户部分确认时：按已确认项写入，未确认项留空并在交付里列出，不整轮中止。
- 追问一轮后用户仍未回应或明确拒绝：按未确认处理，不写 `AGENTS.md`，交付汇总、未确认项与未落盘原因，结束本次初始化。

### 步骤 4：写入 AGENTS.md

- 操作：按步骤 3 的结论选择路径，不重新提问。
  - `首次初始化`（文件不存在）：按模板整份写入，行来源默认 `扫描`，用户口述或裁决的取值为 `用户`。
  - `重新初始化`（文件开头 20 行内含维护条款首句）：按基线逐字段增量改写，只改「来源=扫描」且有变化的字段，用户行保留，不整份重写；覆盖前备份为 `AGENTS.md.bak-<时间戳>`。
  - `非本技能生成`（无维护条款首句）：按用户在步骤 3 选的子路径执行——`备份后整份替换`（先备份为 `AGENTS.md.bak-<时间戳>`，再按模板整份写入）、`合并并保留用户内容`（先备份；把模板标题 `# 工作区`、维护条款与扫描元数据写在文件最前面，用户原有内容（含其标题）整体顺延保留、不删不改；原文件现状四节内的行按 `用户` 保留，没有 `来源` 列时补列并全填 `用户`；`约束` 节按同义去重、用户措辞优先、模板独有项追加；模板四节按模板顺序排列，模板外的自定义章节追加在 `## 约束` 之后、原样保留，不参与比对与待删候选；扫描结果只做新增，同一项冲突以用户值为准并写进交付）、`中止`（不写文件，交付汇总、原因与已扫描范围，结束）。
  - 写入内容：保留首段维护条款、扫描元数据、各节表格与约束条目；删除以 `> 填写说明：` 开头的说明行，替换全部 `待填`。
  - 写入扫描元数据：扫描时间（ISO 8601，带时区，如 `2026-11-16T21:00+08:00`）与各仓库短 HEAD（7 位；根目录仓库以 `.` 为键；无提交写 `无提交`）。
  - 模板里的约束逐条放入；用户已给出或临时补充的约束一并放入。
  - 整类都不存在的章节删掉，不留占位表；有条目但全部未确认时保留该节，把缺失写进交付。
  - 不随意改章节名；确需改名时先搜 `AGENTS.md` 与章节名的引用处，同一次改动内同步更新。
  - 内容字段与基线一致时不改写现状与约束，只更新扫描元数据，并说明内容无变化。
  - 写入前重读 `AGENTS.md` 并与步骤 1 记录的基线哈希比对；不一致就先输出差异请用户确认，不直接覆盖；首次初始化没有基线，跳过本步。
- 完成标志：已按步骤 3 的结论写入并更新元数据，或只更新元数据并说明内容无变化，或已中止并交付；写入失败时按 **异常处理** 降级交付。

### 步骤 5：验收并结束

- 操作：
  - 对照 **验收标准** 逐条核对，修正一轮后重查；仍不通过就交付未通过项、原因与已完成范围，结束，不把未通过说成通过。
  - 按 **交付内容** 报告，附未确认项、缺失项、扫描边界与未覆盖范围。
- 完成标志：验收通过并已交付，或已交付未通过项清单并结束；写入失败按 **异常处理** 降级交付。

## 约束

### 初始化边界

- 初始化期间只读，唯一写入的是工作区根目录的 `AGENTS.md`（覆盖前写带时间戳的 `AGENTS.md.bak-<时间戳>`）。
- 除本技能被显式触发期间，任何时刻都不改根目录的 `AGENTS.md`；发现信息过时时按 **过期处理** 执行。
- 跳过 `node_modules`、`target`、`dist`、`.venv`、`vendor` 等目录，不读 `.git` 内部，并在汇总与交付里说明跳过范围。
- `AGENTS.md` 可能含内网地址与库名；是否提交进版本控制、是否需要脱敏，写入前提示用户决定；用户未回答时，默认不提交进版本控制、不脱敏写入，并在交付显著标注。

### 服务与地址

- 不代为启动、重启、停止服务，不改端口，不结束进程；只读扫描。
- 地址与端口只从配置文件、环境变量、启动脚本、容器编排、代码常量或用户口述里取，不用推测值；框架默认端口不算来源，找不到时按未确认处理。
- 服务主机：本机直连写 `localhost`；监听 `0.0.0.0`、空主机或 `${HOST}` 占位时，调用方在本机写 `localhost`，跨机或容器互访写实际可达的 IP 或域名并在交付说明；具体网卡 IP 或域名原样写。
- 端口取调用方可达的端口：容器端口映射写宿主侧映射端口；容器化但无宿主映射时地址列留空或只写网关入口，并在交付说明；非容器化且没有映射时写服务自身监听端口；不写容器内端口，也不写框架默认端口。
- 服务被网关统一前置时，网关单独一行写对外入口；被前置的服务仍写自身监听地址（容器场景写映射后的宿主端口，无映射时按上一条处理），并在交付里注明经哪个网关访问。
- 同一项在多个环境配置里各有一份合法值时，取本地或开发环境的值，其余环境在交付里列出，地址列不写多值；本地或开发环境没有该值时不拿其它环境的值顶替，地址列留空并在交付里列出其它环境的值与来源。
- 基础设施主机写实际使用的 IP 或域名，本机部署写 `localhost`。
- 默认端口（如 https 的 443）可以不写端口；Unix socket 入口写路径，不写协议与端口。

### 事实与证据

- 只写能指回一个文件、一次实际扫描或一次用户口述的结论。
- 证据统一写 `路径:行号`、`命令` 或 `用户口述`，多条用 `；` 分隔，指不回时写 `未确认`。
- 证据只进汇总与交付，`AGENTS.md` 只写结论；表格里的「来源」列只区分 `扫描` 与 `用户`，不写证据。
- 取值来自用户口述、用户裁决或用户确认保留的，行来源记 `用户`；后来被用户在步骤 3 改过的行也记 `用户`。

### 内容边界

- 写：服务地址与端口、中间件连接位置、启动/构建/校验命令、仓库位置、工作约束。
- 不写：目录职责逐项、接口逐条说明、表结构、与连接位置无关的组件/版本/部署拓扑清单、功能清单——这些读一次代码就能得到，写进文档只会过期。
- 判据：写进去的每一条，都应是 Agent 行动前必须知道、且不翻多个仓库就难以确认的运行期事实或入口。
- 例外：命令虽在仓库声明文件里，但跨仓库分散、是 Agent 的行动入口，仍要写；地址与端口同理。
- 约束写成必须、禁止或先确认，一条一件事，能判断是否被违反，并附原因或后果。
- 校验命令、安全边界、提交与部署约定若已在模板或用户口述中出现，必须保留，不因篇幅删掉。
- 同一规则只写一处，其他位置不重复。

### 来源判定

- 文件开头 20 行内出现维护条款首句「本文件由工作区初始化技能扫描生成」：按重新初始化处理。
- 不含该首句且文件存在：视为用户手写或他工具生成，在步骤 3 让用户选「备份后整份替换 / 合并并保留用户内容 / 中止」，用户不选按中止处理。
- 文件不存在：按首次初始化处理。

### 重新初始化

- 按步骤 1 读到的基线逐项比对；文件不存在就按首次初始化处理。
- 只改有变化的字段；用户手加的内容与约束保留。
- 只对「来源=扫描」的行做比对；实际已找不到的列为待删候选，在步骤 3 问过再处理。「来源=用户」或来源为空的行永不列为待删候选。
- 待删候选按用户裁决写回：删行；或保留并把来源改为 `用户`；或按用户给的实测值改。
- 新出现的仓库、服务、基础设施与命令照常补进去。
- 覆盖前先写带时间戳的备份；不整份重写；内容无变化时只更新扫描元数据。

### 过期处理

- 使用 `AGENTS.md` 前，以运行环境当前时间与各仓库当前 HEAD 对照文件记录；扫描超过 7 天，或任一仓库 HEAD 与文件记录不一致（记录为 `无提交` 但仓库已有提交也算不一致），视为可能过期。
- 视为可能过期时按三级处理：
  1. 在回复或交付里标注「本文件可能过期」，本次以实测或配置为准；
  2. 输出差异摘要（哪一项、本文件值、实际值）；
  3. 提示用户重新运行本技能。
- 这里说的「实测」限于只读：读配置文件、环境变量、`git log`/`git rev-parse`、端口连通性探测；不启动、不重启、不停止服务；探测失败按配置为准并在回复标注。
- 不直接改 `AGENTS.md`，也不把过期标注写进文件。

### 异常处理

- 单个文件读取失败时跳过，在交付里说明。
- 写入 `AGENTS.md` 失败（根目录只读、文件被占用、空间不足）时中止，不留部分文件，把汇总全文作为降级交付并说明失败原因。
- 用户对推断值提出异议时以用户为准，该行来源改为 `用户`，汇总与交付里的证据注明来源为用户口述。
- 部分完成时说明已初始化与未初始化范围。

## 输出与验收

### 交付内容

- 工作区根的绝对路径、扫描范围与未覆盖范围。
- 工作区根目录的 `AGENTS.md`；未落盘（写入失败、中止、步骤 3 未回应）时为汇总全文。
- 仓库、服务、基础设施与命令的汇总表及未确认项清单。
- 被网关前置的服务及其网关关系（若有）。
- 集群或多节点的其余节点、broker 与非主 topic 清单（若基础设施是集群）。
- 扫描时间与各仓库 HEAD。
- 缺失的地址、端口与命令清单。
- 其它环境各有一份不同值时的地址清单。
- 重新初始化时的差异摘要：新增、变更、待删候选、未变。
- 备份文件路径（若有），以及是否纳入版本控制、是否需要脱敏的结论。

### 验收标准

- 写入路径只有工作区根目录的 `AGENTS.md`（覆盖前写带时间戳的备份），落盘路径等于步骤 1 确认的工作区根；未落盘时（写入失败、中止、步骤 3 未回应、扫描范围无仓库）本组文件类验收项豁免，只核对汇总是否完整。
- 文件开头 20 行内有维护条款与扫描元数据（扫描时间、各仓库 HEAD）；维护条款含首句指纹「本文件由工作区初始化技能扫描生成」、手工修改规则、只在用户显式触发时更新、内容无变化时只更新元数据并说明、使用前对照扫描时间与 HEAD、与实测冲突时以实测为准。
- 现状覆盖根目录与一级子目录内的全部仓库，没有遗漏或多算；扫描范围与未覆盖范围已在交付里写明，更深层仓库已声明为未覆盖。
- 现状下存在的每一节都有「来源」列，取值为 `扫描` 或 `用户`；`AGENTS.md` 里没有证据列。
- 用户口述、用户裁决或用户确认保留的行，来源为 `用户`；重新扫描后这些行没有被覆盖或列为待删候选。
- 合并分支写入后，原文件现状四节内的行来源为 `用户`，`约束` 已按同义去重合并，自定义章节原样保留，维护条款与扫描元数据已写在文件开头 20 行内，原内容已保留，写入前已备份。
- 服务一节展开到每个可独立启动的单元，每个单元各一行，用途均为不超过约 10 字的短语（只用于索引），不写整句或说明；前端页面地址也算一条。
- 已确认的 TCP 服务地址含协议与主机，端口非默认时必写，用尖括号包成链接；Unix socket 入口直接写路径，不加尖括号；地址取调用方可达视角：本机直连写 `localhost`，跨机或容器互访写实际可达地址，容器映射写宿主端口；被网关前置的服务写自身监听地址（容器场景写映射后的宿主端口），网关关系写进交付。
- 确实找不到的地址留空并在交付里列出，该格不保留 `待填`。
- 基础设施只出现实际存在的中间件与存储类型（关系型数据库、缓存、消息队列、注册/配置中心、对象存储等），只写类型、主机、端口、库名或库号；主机与端口单独成列；集群或多节点只写调用方可达入口，其余节点写进交付。
- 各节列名与顺序按模板约定，`待填` 占位符已全部替换，`> 填写说明：` 说明行已删除；整类不存在的章节已删除，未留空表，全部未确认的节已保留并在交付里列出缺失。
- 命令表每条命令都取自声明文件、编排配置或用户口述，并附一句话用途；仓库有 wrapper 时用的是 wrapper。
- 文件里没有目录职责逐项、接口逐条说明、表结构，或与连接位置无关的组件/版本/部署拓扑清单；有争议的条目能用 **内容边界** 的判据判定。
- 每项在汇总或交付里都有证据位置（`路径:行号`、`命令`、`用户口述`），或标注为 `未确认`。
- 配置中心等未确认项与冲突候选都在交付里列出，且冲突候选没有被写进 `AGENTS.md`。
- 约束按模板逐条列出，模板里的约束都在（合并分支按同义合并计，不重复），用户已给出与临时补充的约束也已放入；每条可判断是否被违反并附原因或后果，没有写成建议。
- 交付里说明了跳过的依赖与构建产物目录、未读取的 `.git` 内部，以及全程未启动、未重启、未停止任何服务。
- 部分完成时交付里写明已初始化与未初始化范围。
- 重新初始化时只改「来源=扫描」且有变化的字段，用户手加内容保留，新增条目已补入，待删候选按用户裁决写回并在交付里列出；内容无变化时只更新元数据并已说明。

## 示例

见 [AGENTS 样例](assets/agents-example.md)：首次初始化一个含 `easy-cloud` 与 `easy-cloud-ui` 两个仓库的目录，生成根目录 `AGENTS.md`，现状记录两条仓库、四条服务、三条基础设施（含消息队列）与五条命令，约束按模板写入并追加项目约定一条。

边界：某个服务找不到端口，或配置文件里的端口互相不一致。核对不到唯一值时该行地址留空，交付时列出服务名、已查过的文件与候选值，请用户补一个实测值；用户也确认不了就保持留空，不把候选值写进 `AGENTS.md`。重新初始化时只改「来源=扫描」的行；实际已找不到的列为待删候选，用户手补的行不动。
