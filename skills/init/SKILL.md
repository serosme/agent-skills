# Init

## 目标

在工作区根目录生成一份 `AGENTS.md`，写两部分：

- 现状：仓库名与目录、可独立启动的服务及地址与端口、基础设施位置、各仓库的常用命令。
- 约束：几条工作约束，供 Agent 在本工作区干活时遵守。

只做盘点和记录，产出这一份文件。不写读代码就能得到的实现细节。

### 适用

- 工作区已存在，根目录本身是 Git 仓库，或根目录下有一个或几个 Git 仓库，首次接入 Agent。
- 服务地址或端口变化，用户要求重新扫描并刷新说明。

## 前置条件

### 必要输入

- 工作区根目录，即当前工作目录；仓库可能在根目录本身，也可能放在一层或两层子目录里。
- 本次是首次初始化还是重新初始化：默认按根目录是否已有 `AGENTS.md` 判定，用户另有说明时以用户的说明为准。

### 参考模板

- [AGENTS 模板](assets/agents-template.md)：落盘前必读，现状、约束与命令的格式以它为准。
- [AGENTS 样例](assets/agents-example.md)：不确定拆分粒度或约束写法时对照。

### 需收集的信息

#### 仓库

- 工作区里有哪些独立仓库，记下仓库名与目录。
- 根目录本身是仓库时，目录记作 `.`。
- 目录位置来自实际扫描或用户口述。

#### 服务

- 每个仓库里有哪些可独立启动的单元，有多个就逐个展开，每个单元各记一行。
- 可独立启动的单元指有独立启动入口的单元，例如独立启动脚本、容器编排里的一个服务定义、`package.json` 的 start 脚本、独立 main 入口或独立进程；只有一个启动入口的仓库记一行。
- 每个服务的用途用一句话说明它负责的功能。
- 每个服务的地址与端口；前端仓库的页面地址也算一条服务。

#### 基础设施

- 只记关系型数据库与缓存两类，只列实际存在的类型。
- 只记类型、主机、端口、库名或库号；关系型数据库写库名，缓存写库号。
- 主机写实际使用的 IP 或域名，端口单独一列。

#### 命令

- 每个仓库的安装、构建、测试、lint 与启动入口，按仓库各记一行。
- 命令取自构建或任务框架的声明文件，例如 Node 的 `package.json` scripts、JVM 的 `pom.xml`、`build.gradle.kts`、Python 的 `pyproject.toml`、通用的是 `Makefile` 与 `justfile`，也可以是容器编排、CI 配置或用户口述。
- 仓库自带 wrapper 时记 wrapper，如 `./mvnw`、`./gradlew`，不写依赖本机全局安装的 `mvn`、`gradle`。
- README 或注释里的命令只用于交叉核对；与声明文件不一致时以声明文件为准，并在汇总里说明差异。
- 每条只记命令与一句话用途，不展开参数。
- 项目若有「改完必须跑什么」的约定，整理成约束里的一条。

### 信息缺失处理

- 地址、端口这类关键信息找不到时不要猜，记为未确认，留到步骤 3 一次问完；用户也确认不了就留空，在交付里列出。
- 非关键信息找不到时留空，在交付里说明。
- 配置只在 Nacos 等外部配置中心、本地读不到时记为未确认，在交付里说明。
- 命令找不到或与仓库对不上时，记为未确认并列出已查过的位置，不写推测的命令。
- 同一项在多个文件里不一致时，列出候选与推荐值，由用户裁决；裁决前不把候选值当结论写进 `AGENTS.md`。

## 执行步骤

### 步骤 1：识别仓库

- 操作：
  - 重新初始化时先读根目录现有的 `AGENTS.md` 作为基线，后续按它逐项比对。
  - 根目录本身含 `.git` 时也记作一个仓库；再列出一级与二级子目录，含 `.git` 的目录按独立仓库处理。
  - 按 **需收集的信息** 记录仓库名与目录。
- 完成标志：仓库清单已齐，无法判定的在汇总里标为未确认。

### 步骤 2：记录服务、基础设施与命令

- 操作：
  - 按 **服务** 一节的判据展开服务，每个单元各记一行，用途写一句话功能描述，再记地址与端口。
  - 地址与端口按 **服务与地址** 取，允许跨文件核对；取不到按 **信息缺失处理** 处理。
  - 基础设施按 **基础设施** 一节记录。
  - 按 **命令** 一节收集各仓库的构建与校验入口，写入命令表。
  - 单个文件读取失败按 **异常处理** 跳过。
- 完成标志：每个服务都有地址与端口，或已标为缺失；基础设施只列实际找到的项；命令表有内容或已标为缺失。

### 步骤 3：一次性确认

- 操作：
  - 输出汇总，含四部分：仓库清单（仓库、目录、证据、未确认项）、服务表（服务、仓库、用途、地址、证据、未确认项）、基础设施表（类型、主机、端口、库名或库号、证据、未确认项）、命令表（仓库、命令、用途、证据、未确认项）。
  - 重新初始化时再加一部分：相对基线的差异（新增、变更、待删候选、未变）。
  - 冲突项、所有未确认项与待删候选一次问完，处理规则见 **信息缺失处理** 与 **重新初始化**。
  - 用户提出异议时按 **异常处理** 处理。
- 完成标志：用户已确认，或明确接受当前结果与缺失项。

### 步骤 4：写入 AGENTS.md

- 操作：
  - 首次初始化时套用模板写入；重新初始化时在现有文件上按字段改，不整份重写。
  - 首段维护条款照模板原样写入，写明本文件只在用户显式触发本技能时更新。
  - 模板里的约束原样放入；用户已给出其他约束时一并放入，用户临时补充就追加。
  - 整类都不存在的章节删掉，不留占位表；有条目但全部未确认时保留该节，把缺失写进交付。
  - 不随意改章节名；确需改名时先搜 `AGENTS.md` 与章节名的引用处，同一次改动内同步更新。
  - 按 **重新初始化** 只改有变化的字段，并输出差异摘要。
  - 各字段与基线一致时不写入，按首段说法说明未改本文件。
- 完成标志：`AGENTS.md` 已按步骤 3 确认的结果写入，或无变化时已说明未改本文件。

### 步骤 5：验收并结束

- 操作：
  - 对照 **验收标准** 逐条核对，修正后重查。
  - 按 **交付内容** 报告，附未确认项与缺失项。
- 完成标志：验收项全过，交付已完成。

## 约束

### 初始化边界

- 初始化期间只读，唯一写入的是根目录的 `AGENTS.md`。
- 除本技能被显式触发期间，任何时刻都不改根目录的 `AGENTS.md`；发现信息过时时只报告差异，并提示用户重新运行本技能。
- 跳过 `node_modules`、`target`、`dist`，不读 `.git` 内部。

### 服务与地址

- 不代为启动、重启、停止服务，不改端口，不结束进程。
- 地址与端口只从配置文件、环境变量、启动脚本、容器编排、代码常量或用户口述里取，不用推测值。
- 地址写完整入口，含协议、主机与端口；服务一节的主机写 `localhost`，服务配置里主机本来不是 `localhost` 时写实际值，并在汇总与交付里说明原因。

### 事实与证据

- 只写能指回一个文件、一次实际扫描或一次用户口述的结论。
- 证据只进汇总与交付，`AGENTS.md` 只写结论，不加证据列。

### 内容边界

- 不写读代码就能得到的实现细节：功能清单、目录职责逐项、表结构、接口逐条说明、组件清单。
- 约束写成必须、禁止或先确认，一条一件事，能判断是否被违反，并附原因或后果。
- 校验命令、安全边界、提交与部署约定若已在模板或用户口述中出现，必须保留，不因篇幅删掉。
- 同一规则只写一处，其他位置不重复。

### 重新初始化

- 按步骤 1 读到的基线逐项比对；文件不存在就按首次初始化处理。
- 只改有变化的字段；用户手加的内容与约束保留。
- 实际已找不到的条目列为待删候选，在步骤 3 问过再处理，不直接删除。
- 新出现的仓库、服务、基础设施与命令照常补进去。

### 异常处理

- 单个文件读取失败时跳过，在交付里说明。
- 用户对推断值提出异议时以用户为准，汇总与交付里的证据注明来源为用户口述。
- 部分完成时说明已初始化与未初始化范围。

## 输出与验收

### 交付内容

- 工作区根目录的 `AGENTS.md`。
- 仓库、服务、基础设施与命令的汇总表及未确认项清单。
- 缺失的地址、端口与命令清单。
- 重新初始化时的差异摘要：新增、变更、待删候选、未变。

### 验收标准

- 初始化期间只写根目录的 `AGENTS.md`，其中同时包含现状与约束。
- 开头有维护条款，写明本文件只在用户显式触发本技能时更新，重新扫描后无变化时不改文件并说明。
- 现状覆盖根目录本身及子目录里的所有仓库，没有遗漏或多算；仓库一节只写仓库名与目录。
- 服务一节展开到每个可独立启动的单元，每个单元各一行，用途均为一句话功能描述，前端页面地址也算一条。
- 服务地址含协议、主机与端口，用尖括号包成链接，主机为 `localhost`；例外按实际值写并在交付里说明。
- 确实找不到的地址留空并在交付里列出，该格不保留 `待填`。
- 基础设施只出现关系型数据库与缓存两类，只写类型、主机、端口、库名或库号，主机与端口单独成列。
- 各节列名与顺序按模板约定，`待填` 占位符已全部替换；整类不存在的章节已删除，未留空表，全部未确认的节已保留并在交付里列出缺失。
- 命令表每条命令都取自声明文件、编排配置或用户口述，并附一句话用途；仓库有 wrapper 时用的是 wrapper。
- 文件里没有功能清单、目录职责逐项、表结构或接口逐条说明，也没有跨节重复的规则。
- 确实找不到的非关键字段留空并在交付里说明；每一项在汇总或交付里都有证据位置，或标注为用户口述。
- `AGENTS.md` 里没有证据列，证据只在汇总与交付里出现。
- 配置中心等未确认项与冲突候选都在交付里列出，且冲突候选没有被写进 `AGENTS.md`。
- 约束按模板列出，模板里的约束都在，用户已给出与临时补充的约束也已放入；每条可判断是否被违反并附原因或后果，没有写成建议。
- 部分完成时交付里写明已初始化与未初始化范围。
- 重新初始化时只改有变化的字段，用户手加内容保留，新增条目已补入，待删候选在交付里列出；无变化时未改文件并已说明。

## 示例

见 [AGENTS 样例](assets/agents-example.md)：首次初始化一个含 `easy-cloud` 与 `easy-cloud-ui` 两个仓库的目录，生成根目录 `AGENTS.md`，现状记录两条仓库、四条服务、两条基础设施与五条命令，约束按模板写入。

边界：某个服务找不到端口，或配置文件里的端口互相不一致。核对不到唯一值时该行地址留空，交付时列出服务名、已查过的文件与候选值，请用户补一个实测值；用户也确认不了就保持留空，不把候选值写进 `AGENTS.md`。
