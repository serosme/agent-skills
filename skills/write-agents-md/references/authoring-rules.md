# 内容分类与写法规则

本文件是 `AGENTS.md` 内容取舍与句式的详细定义。
判定原则、约束与决策点的关系以 `SKILL.md` 为准，本文件只展开怎么写。

## 三类内容

逐条对现有内容提问，按第一命中处理：

| 提问                             | 归属           | 处理                         |
| -------------------------------- | -------------- | ---------------------------- |
| 违反了会不会出问题？             | 约束           | 保留，写成必须、禁止或需确认 |
| 这里有过备选方案吗，为什么没用？ | 决策点         | 保留，写成选择、原因、代价   |
| Agent 需要照抄执行的命令或环境？ | 命令与环境事实 | 保留在「命令」「部署」等章节 |
| 两分钟内能从代码读出来吗？       | 代码可读内容   | 删除                         |
| 别处已经有同样内容吗？           | 重复           | 合并到一处，保留更具体的那个 |

删除是默认动作；保留需要能说出属于前两类或第三类。

## 推荐章节骨架

- 开头一段：项目是什么、给谁用、一行技术栈。
- 紧随其后的一句定位说明：本文件只写约束与决策，以及**更新时机与维护责任**
  （谁在什么时候判断、什么时候才写入）。
- `## 核心约束`：全部约束集中一处，不再按功能拆分。
- `## 决策点`：按领域分三级小节，例如渲染与取数、认证、数据模型、外部服务、UI。
- `## 命令`：可用命令表加工程事实（包管理器、有无测试与 CI、配置文件约定）。
- `## 部署`：部署链路、密钥、平台限额。
- `## 项目技能`：项目内可用的技能及其触发场景；没有就删掉本节。

章节名不必与本骨架完全一致，但「约束」「决策点」「命令」三类要有明确去处。

## 约束的写法

- 一条一件事，动词开头：必须、不要、只能、禁止、先确认。
- 附原因或后果，让读者知道违反的代价。
- 可判断：给出可观察的判据，例如命令、文件、字段名、允许值。
- 常用位置标注：把最容易踩的实现位置写在括号里。

反例与改法：

| 反例             | 改法                                                                                    |
| ---------------- | --------------------------------------------------------------------------------------- |
| 注意性能         | 重编号只走 `renumberGroupQuery`，语句数与分组大小无关（平台有每批语句数与绑定参数上限） |
| 尽量使用统一风格 | 所有界面文案用英文，代码注释用中文                                                      |
| 不要随便改配置   | 不擅自改已有 API、配置字段或模块边界                                                    |
| 修改后记得验证   | 任何代码修改后必须执行 `pnpm lint` 与 `pnpm typecheck`，并在回复中说明结果              |

## 决策点的写法

统一句式：

```text
**选择 {A}**：不用 {B}，因为 {原因}；代价是 {代价或前提}。证据：{报错文本 / 实测数字 / 平台限制}。
```

要求：

- 必须写出备选方案；只有一句「我们用了 A」是现状描述，不是决策点。
- 必须写代价或前提。代价常出现在调用方义务、兼容性、性能上限上。
- 证据要可核对：报错文本、实测数字、平台文档限制、报错码。
- 理由来源优先级：代码中的防御与注释 → `git log -S` 查相关提交 → 平台或库的限制 → 用户说明。
- 四处都查不到理由时，只保留约束事实，或询问用户；不写「为了更优雅」「更符合最佳实践」这类无法核对的理由。

反例与改法：

| 反例                    | 改法                                                                                                         |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ |
| 使用 json_each 做重编号 | 重编号走 `json_each` 单语句，不用逐行 UPDATE（撞每批语句数上限）或单条 CASE（撞每查询绑定参数上限）          |
| 流式不做服务端加工      | 不给流式加服务端逐 chunk 加工：每个 chunk 有固定 CPU 开销，中文会被切上千个 chunk，实测撞 CPU 上限并中断对话 |
| 金额存分                | 金额存整数「分」：避开浮点误差，小计累加可靠；出入经 `formatAmount` / `parseAmount` 换算                     |

## 踩坑的写法

一条坑按四段写，缺一段就会在下一次重复踩：

1. 症状：可检索的报错文本或现象（白屏、超限、无响应）。
2. 成因：为什么会出现。
3. 规则：应遵循的做法。
4. 位置：涉及的文件或组件。

示例：

> **模板只能引用 `script` 里出现过的标识符**：只写在模板里的自动导入工具函数会被 vue-tsc 当成组件属性，报 `Property 'formatAmount' does not exist on type 'ComponentPublicInstance<...>'`（typecheck 失败但运行时不报错，因为构建期仍会注入）。所以模板专用逻辑要在 `script` 里收口。

保留报错原文的价值在于：以后直接搜报错就能命中这条约束。

## 压缩手法

| 手法                     | 做法                                                 |
| ------------------------ | ---------------------------------------------------- |
| 段落压成一行理由         | 保留结论与原因，删掉推导过程与举例                   |
| 删清单类章节             | 功能清单、目录职责、表结构、组件清单、API 逐路由要点 |
| 合并重复                 | 同一规则在多处出现时只保留最具体的一处               |
| 实现描述改写成约束或决策 | 「X 在 Y 里做了 Z」→「X 必须走 Y，因为 Z」           |
| 删除历史痕迹             | 已完成的迁移、临时兼容、版本历史；防回归的坑要保留   |
| 表格瘦身                 | 列、行只保留影响判断的部分                           |
| 交叉引用代替复述         | 同一主题只写一处，其他位置指向它                     |

删掉的应是「读代码就知道」的内容，不是「出过错所以写下来」的内容。

## 更新时机与维护责任

- 开头必须把「触发」与「条件」分开写：**每次改动后都要判断，只有新增或改变约束、
  决策点、命令与环境事实时才写入**。
- 只写「改了代码就更新本文件」会把实现细节重新引回文件，必须改写；
  只写「本文件不随代码更新」也不行，那会让后续 Agent 不再主动维护。
- 维护责任条款要落在文件本身：本技能按需加载，只有文件里的条款能约束每一次改动。
- 原文件若要求「改代码后同步更新功能、目录职责、API 要点」，与只写约束与决策的定位
  直接冲突，必须按下例改写，不能两条并存：

改写前：

```text
代码修改后必须同步更新本文件：新增、修改或删除文件时，立即更新功能、目录职责、API 要点等章节。
```

改写后：

```text
本文件只保留约束与决策：实现细节以代码为准。
每次改动后都要判断本次是否产生新的约束、取舍或踩坑：有则在同一次改动内更新本文件并说明；
没有则在回复中说明「无新约束，未改本文件」。不要为了同步现状而更新，也不要留成待办。
```

理由：前半句要求同步的章节已被删除，留着会让后续 Agent 试图重建那些章节；
补上维护责任条款，判断才会发生在每次改动之后，而不是等用户提醒。

## 锚点与引用维护

- 盘点时分别搜索文件名（`AGENTS.md`、`@AGENTS.md`）和章节标题文本，包括引号内的中文小节名。
- 被引用的章节名要具体、稳定，例如「CPU 限制」「菜单分节统一约定」。
- 重命名章节时，同一次改动内同步更新所有引用处；引用在代码注释里也要一起改。
- 删除章节前先确认没有引用；有引用则保留措辞，或先改引用再删。
- 交付时必须报告核验结果，否则悬空引用会长期留在注释里。

## 必须保留的内容

以下内容即使读代码能推测出来，也应留在文件中：

- 校验命令，以及「什么改动之后必须跑什么」。
- 安全边界：认证方式、CSRF 依赖的配置、密钥的存放位置、权限范围。
- 明确的禁止项，例如禁止某个危险命令、禁止把密钥放入客户端可见配置。
- 提交与部署链路、参数顺序、平台限额与已知报错码。
- 工具链例外，尤其是会导致编译或类型检查失败的约定。
- 维护责任条款（触发时机、判定标准、「无变化时不写」）：主动维护唯一能常驻的载体。

## 常见反例

- 把约束写成建议：「建议」「最好」「尽量」——无法判断是否违反。
- 理由靠猜：为现状补一个听起来合理的原因，掩盖真实取舍。
- 保留已失效的命令、路径或字段名。
- 把 README 的内容搬进来：安装步骤、使用示例、截图说明。
- 穷举代码现状：逐文件职责、组件 props 清单、每个接口的请求体。
- 文件内部互相矛盾，却不修正冲突，只加一句「以某处为准」。
- 占位符用尖括号写法（如 `<主题>`、`<A>`）：字母开头的会被 markdownlint 判为行内 HTML（MD033/no-inline-html），统一改用 `{主题}`、`{A}`。
- 只写「本文件不随代码更新」，把主动维护一并取消；触发时机与写入条件必须分开写。
