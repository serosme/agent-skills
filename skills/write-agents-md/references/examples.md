# 精简与反馈示例

示例用于说明写法与反馈形式，其中的项目规则不要直接套用到其他仓库。

## 精简：从代码导读改为约束与决策

用户请求：

> 精简一下 AGENTS.md。很大一部分内容都能通过读取代码获得，主要是约束相关的保留。

现状：

- 文件 191 行 / 43.4 KB。
- 章节为：功能清单（F1–F17）、目录职责、命令、API 要点、数据库（含三张表结构）、
  前端架构约定、Nuxt UI 组件清单、项目技能、部署、约束。

预期行为：

- 盘点外部引用：代码注释里出现「见 AGENTS.md 的『CPU 限制』」和「菜单分节统一约定」。
- 删除功能清单、目录职责、三张表结构、API 逐路由要点、组件清单。
- 保留并重写核心约束；把决策段落压成「选择、备选的原因、代价、证据」。
- 补两条约束：任何代码修改后必须执行校验命令；模板只能引用 `script` 中出现的标识符。
- 在定位说明里补上维护责任：每次改动后判断，只在约束或取舍变化时写入。
- 保留并核验上述两个被引用的锚点。

前后对照：

| 项目     | 精简前       | 精简后     |
| -------- | ------------ | ---------- |
| 行数     | 191          | 103        |
| 体量     | 43.4 KB      | 9.5 KB     |
| 章节     | 10 个        | 8 个       |
| 内容类型 | 代码导读为主 | 约束与决策 |

预期反馈：

> 精简完成：191 行 / 43.4 KB → 103 行 / 9.5 KB。
> 删除的是功能清单、目录职责、表结构、API 要点、组件清单；
> 保留并重写了核心约束，新增两条约束，并在开头补上维护责任条款。
> 核验结果：代码注释引用的「CPU 限制」「菜单分节统一约定」两个锚点仍然存在。

## 追加约束：把口头要求写成硬约束

用户请求：

> 添加一点约束：任何代码修改过后都要执行 lint 以及 typecheck 命令。

预期行为：

- 把「记得验证」升级为硬约束，并写明「没跑就不算改完」与「在回复中说明结果」，
  否则约束无法判断是否被违反。
- 拆成两条：一条是校验要求，一条是原本混在一起的禁止项（禁止使用带自动修复的命令）。
- 不写成建议，不与其他约束合并成一句。

改写结果：

```text
**任何代码修改之后都必须执行 `pnpm lint` 与 `pnpm typecheck`**，哪怕只改一行、只改一个字符串；
不得新增错误，并在回复里说明两条命令的结果。没跑就不算改完。
```

## 追加约束：把踩到的坑固化成约束

场景：

- 页面模板里直接调用自动导入的格式化函数。
- `nuxt typecheck` 报 `Property 'formatAmount' does not exist on type 'ComponentPublicInstance<...>'`。
- 运行时不报错，因此长期无人发现。

预期输出：

```text
**模板只能引用 `script` 里出现过的标识符**：只写在模板里的自动导入工具函数会被 vue-tsc 当成组件属性，
报 `Property 'formatAmount' does not exist on type 'ComponentPublicInstance<...>'`
（typecheck 失败但运行时不报错，因为构建期的模板自动导入仍会注入）。
所以模板专用逻辑要在 `script` 里收口，例如 `const money = (cents: number) => \`¥${formatAmount(cents)}\``。
```

要点：保留报错原文与「运行时正常」这一反直觉现象，否则后来者会认为约束没有依据。

## 改动后主动维护：判定为需要

场景：

- Agent 修完取数 bug，顺便在代码里加了防御：重试必须走 `retryFetch`。
- 用户全程没提 `AGENTS.md`。

预期行为：

- 先判断：本次产生了新约束（重试路径），需要写入。
- 在同一次改动内更新 `AGENTS.md`，保留可检索的症状与实现位置。
- 回复中说明写了哪条、放在哪一节，不等用户提醒。

预期反馈：

> 本次产生了新约束，已在同一次改动内写入 `AGENTS.md` 的「决策点 · 取数」：
> 重试必须走 `retryFetch`，不用裸 `fetch`（撞平台重试上限，附报错文本）。
> 同批的命名调整与日志改动未影响约束，未写入。

## 改动后主动维护：判定为不需要

场景：

- Agent 只做了一次重构：合并两个内部函数、改名，外部行为与约束都没变。
- 用户全程没提 `AGENTS.md`。

预期行为：

- 同样做一次判断，结论是不需要更新，不改文件。
- 在回复中给出结论，而不是沉默跳过；也不为了显得有产出而追加条目。

预期反馈：

> 本次是纯重构，未新增或改变约束、取舍与环境事实，`AGENTS.md` 未改动。

## 与文件定位冲突的请求

用户请求：

> 把 AGENTS.md 补全成完整的项目文档，把每个页面的实现细节都写进去。

预期反馈：

> 这与 `AGENTS.md` 的定位冲突：它只保留约束与决策，实现细节读代码即可，
> 补进去会在下次代码改动时立刻过时。
>
> 请选择：
>
> - 保持约束文件，只补约束与决策点；
> - 另建面向人的项目文档（README 或 `docs/`），把实现细节写在那里。
>
> 明确后再动手。

## 决策理由无法确认

场景：

- 代码中有一处看起来多余的额外校验，用户要求写进决策点。
- 提交记录与注释都查不到原因。

预期反馈：

> 这条可以写成约束（「服务端必须再校验一次 X」），
> 但没法从代码、提交记录或你的说明里确认当初为什么这么做。
> 请补充原因，或先按只有约束、不写理由的形式记录。

## 锚点悬空

场景：

- 精简时删掉了「CPU 限制」小节。
- `app/utils/chat-smooth.ts` 的注释写着「见 AGENTS.md 的『CPU 限制』」。

预期行为：

- 交付前 grep 到该引用，保留小节措辞或同步修改注释，二者选其一。
- 交付说明中报告核验结果，而不是只在文件内部改完就算结束。

预期反馈：

> 核验发现 `chat-smooth.ts` 的注释引用了「CPU 限制」。
> 已把该小节改名为「CPU 限制（踩过一次）」保留原措辞，代码注释无需改动。
