# 提交信息规范

## 格式

提交信息只有一行：`<type>: <description>`。

- `type` 与 `description` 之间是一个英文冒号加一个空格。
- `type` 用小写英文，取本规范的 8 个值之一。
- 不加 scope、body 或 footer。

## Type 判断

站在仓库使用者的角度判断本次变更带来的实质影响，看使用者因此得到了什么，而不是改了什么文件。同一种文件变更在不同仓库可以对应不同 `type`：

- dotfiles 仓库新增提供 Git 别名的 `.gitconfig` 是 `feat`；业务应用内的常规配置维护是 `chore`。
- 依赖升级修复了明确的用户缺陷时按实际影响判断，不机械归为 `chore`。
- Skill 或规则类 Markdown 承载可执行的行为规范，不因扩展名是 `.md` 就归为 `docs`。
- 只调整组织结构、对外行为不变时，不因新增文件判为 `feat`。

| type       | 判断依据                                   |
| ---------- | ------------------------------------------ |
| `feat`     | 使用者获得了之前没有的能力或内容           |
| `fix`      | 使用者不再受该问题困扰                     |
| `refactor` | 对外行为不变，可维护性或可读性提升         |
| `chore`    | 内部维护，如常规依赖更新、脚本与配置维护   |
| `docs`     | 说明性内容提供更准确的信息，不改变程序行为 |
| `style`    | 只改空格、换行、缩进，不改变逻辑           |
| `test`     | 加强测试保障，不改变对外功能               |
| `ci`       | 调整持续集成中的自动化流程                 |

## 边界情况

- 新增、修改、删除是操作形式，不决定 `type`。删除不可达代码且行为不变是 `refactor`；删除错误行为以修复缺陷是 `fix`。
- 只使用上述 8 个 `type`，不引入新值。
- 无法可靠分类时说明歧义并询问，不把 `chore` 当无条件兜底。
- 用户指定的 `type` 与实际影响明显冲突时说明冲突，不直接套用。

## Description

- 祈使语气，说明这次提交做了什么。
- 英文首字母小写，末尾不加句号。
- 不超过 72 字符，不含 `<type>:` 前缀。
- 写具体行为，不写 `update files`、`fix bugs` 这类空话。
- 不写差异里无法确认的效果，不加换行或控制字符。

## 语言

- 跟随最近一次提交描述部分所用语言，可用 `git log -1 --format=%s` 判断。
- 无历史提交或无法判断时用英文；不按多条历史投票，也不推测作者偏好。
- 英文消息附中文释义，释义不写入提交信息。
- 用户指定语言时按用户要求执行，并说明与默认规则的差异。
