## 目标

打扫暂存区并生成提交信息：

- 属于当前会话业务主题的改动留在或进入暂存区；本地调试配置、临时调试代码、日志等非业务改动从暂存区移出，改动仍留在工作区。
- 默认只输出提交信息，不提交、不推送；用户明确要求才提交。
- 没有业务上下文时不猜取舍，改为分析改动主题；多主题时询问用户：拆分（多条信息、分批提交）、合并（一条）、或只保留部分主题。
- 只做这一件事，不做其他 Git 操作。

## 术语

- **业务改动**：服务当前对话任务、要进入本次提交的改动。
- **非业务改动**：本地调试开关、临时日志、断点、个人配置、为本地测试临时改的配置，以及与本任务无关的改动。
- **移出暂存区**：用 `git restore --staged`（首次提交仓库用 `git rm --cached -f`）把路径从索引撤下；工作区内容不丢弃、不还原。
- **无法判断**：不能可靠归类的改动；保持原状、单独列出并询问。
- **主题**：同一目的的一组改动；多个文件服务同一目的算一个主题。
- **首次提交仓库**：`git rev-parse --verify HEAD` 失败的仓库。
- **文件级路径**：来自 `git status --porcelain -uall` 的单个文件路径；业务路径不得使用目录。

## 步骤

### 1. 预检

以下命令都在仓库根执行（统一 `git -C <仓库根>`；取 git 内部路径时用 `--path-format=absolute`）。

- 在仓库内：`git rev-parse --show-toplevel`；否 → 停止，报告。
- 分支：`git branch --show-current`；为空（detached HEAD）→ 停止，报告，不自行切换。
- 首次提交仓库：`git rev-parse --verify HEAD` 失败 → 记下，后续移出暂存区改用 `git rm --cached -f -- <路径>`（`-f` 只影响索引，工作区文件保留；`AM` 等「已暂存但工作区有差异」状态必须加 `-f`，否则命令失败）。
- 进行中操作：分别执行 `git rev-parse --path-format=absolute --git-path rebase-merge` 与 `... --git-path rebase-apply`，检查输出路径是否存在；再分别执行 `git rev-parse --verify --quiet MERGE_HEAD`、`CHERRY_PICK_HEAD`、`REVERT_HEAD`，成功即命中；或 `git ls-files -u` 有输出 → 停止，报告（用 `git status` 长格式复核「still merging」等提示）。
- 状态盘点：`git status --porcelain -uall --ignored`（ignored 只用于风险提示）、`git diff --name-status -M`、`git diff --cached --name-status -M`。
- 出现 `AD` 状态（已暂存新增但工作区文件已删除）→ 停下询问，不直接移出（内容可能只存在于暂存对象）。
- 工作区与暂存区都干净 → 报告「无改动可提交」，结束。

### 2. 判断上下文

- 有明确任务（改了什么功能、修了什么缺陷、为什么改）→ 进入 **3. 有上下文**。
- 无（对话为空，或只有「收尾、生成提交信息、打扫暂存区」这类指令）→ 进入 **4. 无上下文**。
- 用户要求只读（只看信息、不动暂存区）→ 仍做 3.1–3.2 或 4.1–4.3 的范围判定，跳过所有暂存区写操作，直接走 5–7：安全检查只进汇报、不打断；步骤 6 的 C 分支只报告可移出清单，不执行，需用户解除只读后才能移出。
- 判断不了 → 按无上下文处理，并在汇报说明「未识别到业务上下文」。

### 3. 有上下文：划定业务范围并整理暂存区

1. 从对话提取任务目标与涉及的文件、模块，对应到步骤 1 的 **文件级路径**；完全对应不上 → 报告「未找到与任务对应的改动」并列出清单询问，不猜。
2. 逐项分类「业务、非业务、无法判断」；同一文件同时含业务与非业务改动（例如业务文件里加了一行本地调试日志）→ 标为「混合文件」；同一路径既有已暂存内容、工作区又有未暂存改动（同时出现在 `git diff --cached --name-status` 与 `git diff --name-status` 中）→ 标为「部分暂存文件」。两者都单独处理，不直接归业务。
3. 安全检查（见 **5. 安全检查**）在暂存前执行：命中且属业务范围 → 停下询问；用户确认继续 → 记录风险后继续；用户拒绝或无法确认 → 停止报告。
4. 处理混合文件与部分暂存文件（不自动改文件、不逐 hunk 拆分）：
   - 混合文件：若已暂存，先移出暂存区；① 整文件按业务暂存并在汇报标注风险（调试行会一并进提交，需用户确认）；② 用户用 `git add -p` 手工分块后重跑（未跟踪新文件需先 `git add -N`）；③ 整文件跳过、留在工作区。
   - 部分暂存文件：保持现状，不预先移出；① 只提交已暂存部分（不动索引，汇报标注该文件仍有未暂存改动，核对时允许该路径的未暂存剩余）；② 补齐暂存（`git add -- <路径>`，工作区剩余一并提交）；③ 移出暂存区、仅保留工作区改动。
   选择后回填分类并继续。
5. 处理无法判断项：列出并询问。已暂存且未获答复 → 停下等待（索引不干净，不能当作已闭环）；未暂存且未获答复 → 保持原状、不计入业务范围，汇报标注待确认。得到答复后回填分类并继续。
6. 整理暂存区（首次提交仓库把「移出暂存区」换成 `git rm --cached -f -- <路径>`）：
   - 业务改动：未暂存 → `git add -- <文件路径>`；已暂存 → 不重复 add（避免失败或抹平已有部分暂存）。重命名按旧、新两个路径处理；删除按路径处理。
   - 非业务改动：已暂存 → 移出暂存区；未暂存 → 不动。
7. 业务改动集合为空 → 不生成提交信息，报告「未找到本次任务的业务改动」，列出非业务与无法判断清单后结束。
8. 核对：`git diff --cached --name-status -M` 的路径集合与业务集合 **全等**（重命名记录 `R100 old new` 按旧、新两个路径计入集合）；`git diff --name-status -M` 只含未暂存的非业务、无法判断、范围外路径，以及选择「只提交已暂存部分」的业务路径；两者之外不应有差异；不通过 → 停止并报告，不继续改索引。

### 4. 无上下文：分析主题

1. 确定范围：暂存区非空 → 以暂存区为范围（工作区未暂存改动列为范围外）；暂存区为空 → 以全部改动为范围。
2. 读差异：`git diff --no-ext-diff --no-textconv`、`git diff --cached --no-ext-diff --no-textconv`；未跟踪文件单独列出并 **读取文件内容**（它们不在 diff 中）；ignored 不属改动范围，只提示。
3. 按「同一目的」归组，判断单主题还是多主题。
4. 单主题 → 进入步骤 6 生成一条提交信息。
5. 多主题 → 列出每个主题的路径、改动要点与候选提交信息，进入步骤 6 的多主题分支询问。
6. 无法归组或信息不足 → 说明缺口并询问。
7. 默认不调整暂存区；用户选定拆分、合并、保留部分后按步骤 6 的对应分支执行。
8. 完成标志：给出主题结论（单主题或多主题）与对应提交信息，或明确列出待确认项。

### 5. 安全检查

- 范围：拟纳入提交范围的改动（有上下文时为业务集合；无上下文时为步骤 4 的分析范围；只读时为 3.1–3.2 或 4.1–4.3 判定的范围）。
- 检查项：凭据文件（`*.pem`、`*.key`、`*.env*` 等）、明文 token、冲突标记 `<<<<<<<`、构建产物与依赖目录（`dist/`、`node_modules/`）、单个超过 5 MB 的二进制。
- 命令：已暂存内容用 `git diff --cached --stat`（大二进制显示 `Bin N bytes`）与 `git diff --cached --name-status`；未暂存与未跟踪内容按路径读取文件、用文件系统大小；ignored 从 `git status --porcelain -uall --ignored` 识别并只提示（ignored 不会被暂存）；仓库较大时 ignored 只检查与构建产物、依赖目录相关的路径，不逐条列出。
- 命中且在提交范围 → 停下询问：确认 → 记录风险后继续；拒绝或无法确认 → 停止报告。命中但不在提交范围 → 汇报提示。

### 6. 生成提交信息

1. 判定提交范围的主题数：
   - 单主题 → 生成一条提交信息。
   - 多主题 → 询问用户一次：A：按主题拆分；B：合并为一条；C：只保留部分主题。
2. C 分支：用户指定保留哪些主题；对其余主题的路径执行「移出暂存区」（已暂存路径用 `git restore --staged`，首次提交仓库用 `git rm --cached -f`；未暂存路径不动）；只读模式下只报告可移出清单、不执行。执行后核对索引集合等于保留主题路径集合，不通过 → 停止报告。对保留部分重新判定主题数——单主题 → 一条；仍多主题 → 再询问 A 或 B（不再提供 C）。
3. 按选择生成：A 每个主题一条、`type` 按该主题的实质影响；B 一条、`type` 覆盖整体影响；C 按保留后的结果。不把互相独立的主题硬说成一个功能。
4. 读 [提交信息规范](references/commit-message.md)，按其规则写；语言跟随最近一次提交（`git log -1 --format=%s`；空仓库用英文并附中文释义）；依据必须是实际差异，范围与提交范围一致。
5. 记录用户选择，供步骤 7 汇报与步骤 8 提交使用。

### 7. 汇报（默认）

- 提交信息（拆分时每个主题一条）。
- 已暂存：本次纳入的路径清单；只读或未整理时写「未调整」。
- 未纳入：非业务、无法判断、范围外（含未暂存）改动，或「无」。
- 风险提示：安全检查命中项、ignored 提示，或「无」。
- 多主题选择状态（未选择、拆分、合并、只保留部分）与对应信息。
- 分支名。
- 说明本次未提交；若用户可能要提交但当前无法直接提交（暂存区为空、范围未确认），写明下一步需要什么。

### 8. 提交（仅用户明确要求时）

- 前置：若当前无可提交内容（暂存区为空或范围未确认）→ 先询问是否按分析范围整理后提交；用户确认后整理再提交，不自行扩大范围。
- 单主题或合并：先用 `git diff --cached --name-only` 列出索引路径并确认目标集合；若索引含目标集合之外路径（非业务、无法判断）→ 先说明并等用户决定（移出后提交，或确认一并提交）；处理完核对索引集合与目标集合全等，再 `git commit -m '<提交信息>'`。无上下文模式下把索引路径清单交用户确认范围后再提交。
- 按主题拆分：逐个主题提交——先确认当前主题内没有「部分暂存」路径（有 → 停下说明，按 3.4 的选项处理）；用 `git diff --cached --name-only` 取索引全集合；对不在当前主题的路径（**含非业务、无法判断**）移出暂存区；对当前主题中未暂存的路径 `git add -- <路径>`（已暂存路径不重复 add）；核对索引集合与主题路径全等（重命名按旧、新两个路径）；`git commit -m '<该主题信息>'`；用 `git show --name-only --format= HEAD` 核对；再处理下一个主题。
- 钩子失败 → 报告输出与残留改动，不绕过（不用 `--no-verify`）。
- 本技能不推送；用户要求推送时说明需另行操作，不自行执行。

## 边界

- 只做打扫暂存区与生成提交信息；默认不提交、不推送；不 amend、不 rebase、不 squash、不用 force。
- 不修改工作区文件内容；只用索引命令（`git add`、`git restore --staged`、`git rm --cached`）整理；行级拆分由用户用 `git add -p` 完成（未跟踪新文件需先 `git add -N`）。
- 不用 `git add -A`、`git add .`、`git commit -a`；按文件级显式路径暂存，路径前加 `--`，不得传目录。
- 不做 `reset --hard`、`checkout -- .`、`clean`、删 stash、删分支。
- 无法判断的改动不猜测，保持原状并列入待确认。
- 任一实际执行类 git 命令（`add`、`restore`、`rm`、`commit`、`diff` 等）非 0 → 停止并报告，不继续改索引（钩子失败同此）；仅用于判定的探测命令（`rev-parse --verify`、`--verify --quiet`、`git log -1` 等）以退出码为判断信号，非 0 属预期结果，不算失败。
- ignored 文件不纳入暂存，只提示。
- 不改 CHANGELOG、README、版本号，除非用户要求。
- 已有进行中的 Git 操作时不动手，只报告。
- 用户要求与提交信息规范冲突时说明冲突，不静默选一套。

## 交付

- 默认产物：提交信息，以及已暂存、未纳入、风险、多主题选择与分支清单；除暂存区整理外不改仓库。
- 未纳入项写明原因（非业务、无法判断、范围外）。
- 提交时给出提交 hash 与消息；失败时只报失败步骤、原因与残留。

## 示例

场景一（有上下文）：对话中用户在修登录重试，`src/auth.ts` 已修改，`local/debug.ts` 是本地调试代码，`README.md` 与本任务无关；用户说「收尾」。

- 分类：`src/auth.ts` 业务；`local/debug.ts`、`README.md` 非业务。
- 整理：`git add -- src/auth.ts`；若 `local/debug.ts` 已在暂存区，`git restore --staged -- local/debug.ts`。
- 信息：`fix: resolve login retry loop`。
- 汇报：已暂存 `src/auth.ts`；未纳入 `local/debug.ts`、`README.md`；未提交。

场景二（无上下文、多主题）：用户只说「收尾」，暂存区有两个无关主题。

- 分析：主题一（`src/auth.ts`）候选 `fix: resolve login retry loop`；主题二（`src/export.ts`）候选 `feat: add export endpoint`。
- 询问：拆分还是合并？未确认前不生成合并信息、不调整暂存区。
- 用户选拆分：给出两条信息；若用户随后说「提交」，按主题逐个收敛暂存区、`git add`、`git commit`，每次核对只含该主题文件。

场景三（混合文件）：`src/auth.ts` 同时含业务改动和一行本地调试日志；不自动改文件、不做 hunk 拆分，停下给出「整文件按业务暂存并标注、用户 `git add -p` 手工分块、跳过该文件」三个选项。

场景四（首次提交仓库）：`git rev-parse --verify HEAD` 失败；仍可整理，但移出暂存区用 `git rm --cached -f -- <路径>`（已暂存且工作区又改过的文件也必须加 `-f`），其余流程不变。
