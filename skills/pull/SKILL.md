# Pull

## 目标

把当前位置对应的仓库更新到远端最新，且不丢本地提交与本地改动。

范围只取一种：当前目录在仓库内时，只处理该仓库根；当前目录不在仓库内时，只处理当前目录直接子目录中的仓库。两种情况不合并，也不向更深层递归。

「不丢」的边界：保护已跟踪文件的改动与未跟踪文件；被 `.gitignore` 忽略的文件不在保护范围；本地提交的内容保留，merge 拓扑不保证（见 **边界**）。

## 术语

- **停止**：该仓库立即终止后续步骤，保留现场，结果记「已停止」。
- **跳过**：该仓库不进入修改，结果记「已跳过」，并记录原因。
- **回退**：仅在用户要求放弃时发生，结果记「已回退」。
- **结束**：单个仓库流程走完；已更新、已回退、已是最新、已跳过、已停止都算结束。
- 停止、跳过、回退都只作用于当前仓库，其余仓库继续；整轮在所有仓库结束后统一报告。

## 步骤

### 1. 确定待处理清单

- 当前目录在仓库内：`git rev-parse --show-toplevel` 的输出作为唯一目标。
- 当前目录不在仓库内：列出直接子目录，对每个子目录执行 `git -C <子目录> rev-parse --show-prefix`。输出为空（仅换行）表示该子目录自身就是仓库根，加入清单；命令失败（不是仓库）或输出非空（是更深层仓库的子目录）都不加入。
- 用 `--show-prefix` 判断可避开 `realpath` 在路径分隔符、大小写与符号链接上的差异；需要比较路径时按平台规则归一化。
- 清单为空：报告「没有可拉取的仓库」，流程结束。

### 2. 采集现状

以下命令都在仓库根执行（统一加 `git -C <仓库根>` 或先切换到仓库根）；否则 `git ls-files` 只覆盖子目录。

先只读记录基线，供核对与交付使用：分支名（`git branch --show-current`；为空表示 detached，记「detached @ <短 SHA>」，若 `git rev-parse --git-path rebase-merge/head-name` 指向的文件存在，可从中补出被 rebase 的分支名）、拉取前 HEAD（`git rev-parse HEAD`）、`git stash list --format='%H %gd'`、`git status --porcelain --untracked-files=all`、ignored 清单（`git ls-files -o -i --exclude-standard`，仅用于交付提示）。

随后按顺序执行；除用作条件判断的命令外，任一命令失败都按 **冲突与异常处理** 停止该仓库。

1. **进行中操作检查**：用 `git rev-parse --git-path` 取得 `rebase-merge`、`rebase-apply`、`MERGE_HEAD`、`CHERRY_PICK_HEAD`、`REVERT_HEAD` 的路径并检查存在性；任一存在，或 `git ls-files -u` 有输出 → 停止，残留项写「进行中的 rebase/merge/cherry-pick/revert」或「未合并索引」。
2. **上游配置检查**：分支名为空（detached）→ 跳过，原因「detached HEAD」。读 `git config branch.<分支名>.remote` 与 `git config branch.<分支名>.merge`；未配置时 `git config` 以 exit 1 结束，属预期结果，按「无上游」跳过；remote 为 `.` → 跳过，原因「上游是本地分支」。
3. **拉取前取证**：若 `@{u}` 可解析，记录 `git rev-parse @{u}`（拉取前上游 tip）与当时的 `git rev-list '@{u}..HEAD'`（拉取前领先清单），对领先清单逐个执行 `git for-each-ref refs/remotes --contains <SHA>`，有输出并入「已发布集合」。必须在 fetch 前做：`fetch --prune` 会更新或删除远端跟踪引用，事后无法取证。
4. **拉取远端**：非交互执行 `git fetch --prune <上游 remote>`（例如设置 `GIT_TERMINAL_PROMPT=0`；不等待交互式凭据，失败不自动重试）。失败 → 停止，贴原始报错。
5. **复解析上游并检测远端改写**：重新解析 `@{u}`；失败 → 停止，原因「上游已被删除或无法解析」。若拉取前上游 tip 与新上游 tip 不同，用 `git merge-base --is-ancestor <拉取前 tip> <新 tip>` 判断：拉取前 tip 不是新 tip 的祖先 → 停止，原因「远端历史被改写」，等人工确认。squash/rebase 型上游更新可能被保守停止（安全方向，可接受）。
6. **计算落后/领先并补充已发布集合**：`git rev-list --left-right --count '@{u}...HEAD'`；记录 `git rev-list '@{u}..HEAD'`（待重放的领先清单）与 `git log --format='%H|%an|%ae|%at|%s' --no-merges '@{u}..HEAD'`（非 merge 领先提交的元数据，供核对是否被重放）；对领先提交再执行一次 `for-each-ref refs/remotes --contains`，结果并入「已发布集合」（补充证据，用于发现本次 fetch 才出现的已发布提交）。

### 3. 判定是否允许拉取

按顺序匹配，先命中者生效：

- 落后数为 0：结果「已是最新」；用「已发布集合」为交付补充说明；不修改本地分支与工作区。
- 落后数大于 0、领先数为 0：进入步骤 4。
- 落后数大于 0、领先数大于 0：若「已发布集合」非空 → 停止，原因「本地存在已发布提交，rebase 会改写已发布历史」；否则进入步骤 4。

### 4. 先处理工作区

- 工作区干净（`git status --porcelain --untracked-files=all` 无输出；ignored 文件不计入）：不创建 stash，记录「未创建本次 stash」。
- 存在已跟踪改动或未跟踪文件/目录：`git stash push -u -m pull-<YYYYmmddHHMM>`。执行后用 `git stash list` 与基线比较：出现新条目则 `git rev-parse 'stash@{0}'` 记录本次条目 SHA；未出现新条目（例如只有无法收纳的嵌套仓库）则记录「未创建本次 stash」，再按下一行复查工作区。不逐个挑选未跟踪文件，整目录收纳（嵌套仓库除外）；不收纳 ignored 文件。
- stash 后复查 `git status --porcelain --untracked-files=all`：仍有输出（如未跟踪目录内含嵌套仓库，git 会打印 `Ignoring path ...` 而无法收纳）→ 停止，原因「存在无法 stash 的未跟踪路径」，路径列入残留，本次 stash 保留。
- stash 创建失败 → 停止，贴原始报错。

### 5. 执行拉取

已在 2.4 fetch，以下命令不再访问网络。命令中的 `@{u}` 使用 2.5 复解析后的上游。

- 领先数为 0：`git merge --ff-only '@{u}'`。
- 领先数大于 0（且步骤 3 已确认无已发布提交）：执行前先确认提交身份可用（`git var GIT_COMMITTER_IDENT` 成功），否则停止并报告，避免留下半完成的 rebase；然后 `git rebase --no-fork-point '@{u}'`。显式禁用 fork-point，避免远端改写后按旧上游 tip 静默丢弃提交；不用 `git pull`，避免二次 fetch 造成判定与执行之间的竞态。若领先提交全部会被跳过（补丁已在上游），rebase 不会新建提交，此预检可能保守停止，属可接受的安全侧偏差。
- 在 PowerShell 等 shell 中，`@{u}`、`stash@{n}` 必须加引号，否则会被解析或截断。
- 执行时保存命令输出（stdout/stderr），供核对与交付使用。

失败处理：

- `merge --ff-only` 失败：贴原始报错并停止；报错涉及未跟踪文件将被覆盖时，列出冲突路径（防御性分支：正常流程已收纳全部未跟踪文件，此情况少见）；本次 stash 保留，列入残留。
- `rebase` 因冲突停下：停止；若本次创建了 stash，保留条目，不做任何恢复动作；不修改代码，不自行 `git rebase --abort`；报告冲突文件清单与双方改动要点后等指示。
- `rebase` 因其他原因失败（如提交身份缺失、钩子拒绝）：停止，贴原始报错；若 rebase 已经开始，按「rebase 冲突中」的现场处理规则保留现场。

### 6. 恢复本次 stash

仅当步骤 4 创建了本次 stash 且拉取成功时执行；本次未创建 stash 则跳过本节。

1. `git stash apply <本次条目 SHA>`；apply 不删除条目，失败时可直接保留。
2. 成功：用 `git stash list --format='%H %gd'` 找到该 SHA 对应的 `stash@{n}`，执行 `git stash drop 'stash@{n}'` 出栈。`git stash drop <SHA>` 不被 git 接受，必须换成索引形式。
3. 失败分两类，都保留条目、不 drop：
   - 产生未合并路径（内容冲突）：列出冲突路径，结果记「已更新，待人工处理」，等指示。
   - `already exists, no checkout` 或 `could not restore untracked files` 等未合并路径为空的失败：stash 中的未跟踪文件未恢复，列出阻塞路径，结果记「已更新，待人工处理」，等指示；不经重新 apply 确认，不得 drop。
4. 成功后核对：本次条目已从 stash 列表消失，其余条目与采集时的 stash 基线一致。

### 7. 核对

按本次结束状态选一套标准；任一项不通过 → 停止并报告差异，不自行回退。

- **已更新**：记录 `git rev-parse HEAD` 供交付；分支与拉取前一致；重新执行 `git rev-list --left-right --count '@{u}...HEAD'` 落后数为 0；若本次创建了 stash，则其条目已出栈，其余条目等同基线；`git status --porcelain --untracked-files=all` 的改动路径集合必须是 §2 采集基线的**子集**（本地改动被上游以相同结果吸收时路径会合法消失，写入备注）；若出现基线中没有的路径或存在未合并路径 → 不通过（ignored 清单不计入比较，只作交付提示）。
  提交未丢失判定（不用「领先数一致」这一错误不变量）：对 §2.6 记录的待重放领先清单逐个核对——先用 `git rev-list --parents -n1 <SHA>` 判断：父数大于 1 的是 merge 提交，适用规则 ②；否则做「元数据多重集」匹配：拉取后 `git log --format='%H|%an|%ae|%at|%s' --no-merges '@{u}..HEAD'` 中应能匹配到该提交的元数据行（作者名/邮箱/作者时间/标题），按逐行消耗的多重集比较（重复行按出现次数配平，避免简单 grep 漏判）。rebase 会保留这些字段，即使内容因上游上下文变化或用户解决冲突而改变，匹配成功即视为已重放，内容差异写入交付备注（用户若在 rebase 中改写了提交信息，可能匹配失败，按下述兜底）。匹配不到时依次兜底：① `git merge-base --is-ancestor <SHA> '@{u}'` 或 `git branch -r --contains <SHA>` 有输出（已合并或已发布）；② 该提交是 merge 提交（rebase 会压平，属已声明行为，交付注明）；③ `git cherry '@{u}' <拉取前 HEAD>` 中该 SHA 以 `-` 开头（补丁已在上游被跳过），或拉取输出提示 `skipped previously applied commit <短SHA>`。都不满足 → 异常停止，附 SHA、新旧元数据列表与原始输出（补丁已在上游但上下文变化导致 patch-id 不等时 ③ 可能不命中，按异常停止转人工，安全侧可接受）。
- **已更新，待人工处理**：HEAD 已是新上游；若本次创建了 stash，其条目仍在列表；§6.3 的冲突/阻塞路径已记录。
- **rebase 冲突中（已停止）**：rebase 仍在进行；若本次创建了 stash 则条目仍在列表，否则 stash 列表等于基线；拉取前 HEAD 可从 `ORIG_HEAD`/reflog 或采集记录找回。
- **已是最新 / 已跳过**：工作区、索引、stash、分支位置与 §2 采集基线一致（fetch 更新远端跟踪引用不算写操作）。
- **已停止**：分两种——未创建本次 stash：工作区、索引、stash、分支位置与基线一致（仅 fetch 更新远端跟踪引用）；已创建本次 stash：工作区为基线中未能收纳的残留（如嵌套仓库路径），stash 列表为基线加本次条目，分支位置不变；残留项写明本次 stash。
- **已回退**：HEAD 等于采集时记录的拉取前 HEAD（且不再是新上游 tip）；stash 列表等于基线；工作区改动路径集合与基线一致（按路径与新增/修改/删除类别比较，不比较暂存与未暂存状态）。

### 8. 汇总报告

单个仓库停止不影响其余仓库。全部处理完后按 **交付** 统一报告，等待指示的仓库单独列出。

## 冲突与异常处理

每条只作用于出问题的那一个仓库，其余仓库照常执行。

- 采集阶段命令失败（除用作条件判断的命令外）：贴原始报错，停止。
- `fetch` 失败（远端不可达、认证失败、凭据交互超时）：贴原始报错，停止；不自动重试。
- 上游已被删除或无法解析：停止，报告原上游引用名。
- 远端历史被改写：停止，报告拉取前后的上游 tip，等人工确认，不执行 rebase。
- `rebase` 冲突：若本次创建了 stash，保留条目，不 apply/pop，不 abort，不修改代码；报告冲突文件与双方改动要点，等指示。
- `rebase` 其他失败：贴原始报错，停止；已开始的 rebase 保留现场。
- `merge --ff-only` 失败：贴原始报错；涉及未跟踪文件覆盖时列出路径；停止。
- 恢复 stash 冲突/失败：条目保留，报告冲突或阻塞路径，结果「已更新，待人工处理」，等指示。
- 用户要求继续（恢复 stash 冲突）：
  - 未合并冲突：按用户指示解决冲突 → `git add` → 确认无未合并路径 → 找到并 drop 本次条目 → **7. 核对**。
  - `already exists` 等未合并路径为空的失败：先处理阻塞路径；若重新 `git stash apply` 报 `Your local changes ... would be overwritten`（首次 apply 已部分应用了已跟踪改动），先确认这些路径只含本次 apply 的部分结果、没有用户手工改动，然后对报错路径执行 `git checkout -- <路径>`（改动仍在 stash 中，不会丢失），再重新 apply；确认本次不再有失败后，才按 §6.2 找到并 drop；仍失败则保留条目、转「已更新，待人工处理」。已跟踪改动与未跟踪冲突并存的混合场景，通常应走「放弃→回退→重新 apply」路径。
- 用户要求继续（rebase 冲突）：解决冲突 → `git add` → `git rebase --continue`（可多轮）→ 完成后若有本次 stash 执行 **6. 恢复本次 stash**，然后 **7. 核对**；再次冲突则继续等指示。
- 用户要求放弃（仅限冲突/异常停止后，由用户明确指示；成功拉取不自动撤销）：
  1. rebase 仍在进行：`git rebase --abort`（同时恢复分支位置与工作区）。此情形跳过第 2、3 步，直接到第 4 步。
  2. 索引存在未合并路径：确认本次 stash（若有）的条目 SHA 仍可查到（改动未丢）后，`git reset --hard HEAD` 清除未合并状态，然后继续；不确定时转「已停止」并报告。
  3. 需要回到拉取前位置：确认工作区干净后 `git reset --keep <采集时记录的拉取前 HEAD>`（`git reset` 会改写 `ORIG_HEAD`，不要用 `ORIG_HEAD` 作回退目标），然后继续。
  4. 恢复本次 stash（若有）：`git stash apply <本次条目 SHA>`，成功后按 §6.2 出栈。
  5. 核对：HEAD 等于采集时记录的拉取前 HEAD（且不再是新上游 tip）；stash 列表等于基线；工作区改动路径集合与基线一致（按路径与新增/修改/删除类别比较，不比较暂存与未暂存状态）。
  6. 任一步无法安全执行 → 结果「已停止」，原因「放弃流程中断，需人工」，交付写明当前 HEAD 与 stash 状态，不重复尝试。

## 边界

- 不执行 `push` 与 `force`，不改写已发布历史；已发布判定以 fetch 前快照为主证据，fetch 后复查仅作补充。
- 不 drop 非本次创建的 stash 条目；本次条目按 SHA 定位，恢复成功并出栈后才消失，恢复失败时保留。
- 只拉当前分支的上游，不切换分支，不连带拉取其他分支、子模块；不主动 `--tags`，但 `git fetch` 默认会跟随指向新对象的 tag，本地 tag 可能增加。
- tag（本地或远端）不参与已发布判定：`git ls-remote` 只能取回 tag 指针、无法做祖先判断；如需覆盖 tag-only 发布，需另行做精确匹配，本技能不做。
- 在仓库内操作时不处理同级仓库；在工作区目录操作时不处理子目录以下的仓库。
- 整目录收纳未跟踪文件与目录（嵌套仓库除外）；不加 `--index`，恢复后原本已暂存的改动可能变为未暂存。
- 被 `.gitignore` 忽略的文件不在保护范围：不纳入 stash，拉取可能静默覆盖；交付时提示仓库存在 ignored 文件。
- rebase 会压平或丢弃本地 merge 提交（不加 `--rebase-merges`）并跳过已在上游的补丁：本地提交内容保留，拓扑不保证；交付中注明。
- rebase 默认会丢弃变空或原本为空的提交；出现时可能无法自动归因，按异常停止或交付注明（已知边界）。
- 首次 fetch 前 `@{u}` 不可解析时无法取证远端改写；该窗口只依赖 `--no-fork-point` 与 fetch 后复查兜底。
- 恢复 stash 不使用裸 `git stash pop`，也不使用 `git stash drop <SHA>`。
- 已有进行中的 rebase、merge、cherry-pick、revert 或未合并索引时不动手，只报告。
- 不自动重试命令、不等待交互式输入、不自动切换远端；失败原样上报。
- 命令示例中的 `@{u}`、`stash@{n}` 在 PowerShell 等 shell 中需加引号。

## 交付

逐仓库列出：路径、分支、结果、原因、残留项、备注。

- 结果取值：`已更新至 <提交>`、`已更新，待人工处理`、`已回退`、`已是最新`、`已跳过`、`已停止`。
- 分支：detached 或进行中操作导致取不到分支名时，写「detached @ <短 SHA>」，并尽量从 rebase 元数据补出被操作的分支名。
- 原因：跳过/停止/回退必填（如 detached HEAD、无上游、上游是本地分支、上游已被删除、远端历史被改写、已有进行中操作、已发布提交、fetch 失败、恢复冲突、用户要求放弃等）。
- 残留项：本次 stash 条目、进行中的 rebase、冲突文件/未合并路径、无法 stash 的路径、远端不可达等；无则写「无」。
- 备注：存在未推送提交的仓库单独说明，并注明其中是否有已发布提交；存在 ignored 文件的仓库提示「ignored 文件不受保护」；rebase 压平过 merge 提交的注明；rebase 经冲突解决、或上游上下文变化导致重放内容与原文有差异的注明（可用「元数据匹配成功但 `git show`/patch-id 不同」判定内容有差异）。
- 失败或异常项附关键原始报错或命令输出片段；成功项不必附全量输出。
- 末尾列出等待指示的仓库与仍需人工处理的事项。
- 清单为空时只报告「没有可拉取的仓库」，不逐仓库列。

## 示例

工作区 `A` 不是仓库，其下 `B`、`C` 为两个仓库。

- 在 `A` 下执行：`B` 有未跟踪临时脚本与 2 个未推送提交、落后 3 个提交——先 `git stash push -u -m pull-202506121030` 并记录 SHA，再 `git rebase --no-fork-point '@{u}'`，成功后 `git stash apply <SHA>` 并按索引 drop；`C` 工作区干净、落后 3 个提交——`git merge --ff-only '@{u}'`。报告两条结果，`B` 注明尚有 2 个未推送提交。
- 在 `B` 下执行：只处理 `B`，`A` 与 `C` 不做任何操作。
- 边界之一：`B` 的领先提交已包含在 fetch 前的远端跟踪分支中 → 停止 `B` 并报告（不改写已发布历史），`C` 照常拉取。
- 边界之二：远端被 force-push 改写（拉取前上游 tip 不是新 tip 的祖先）→ 停止并等人工，不执行 rebase。
- 边界之三：`C` 已有进行中的 rebase → 入口检查即停止 `C`，`B` 照常处理。
- 边界之四：在 `A` 下若 `B`、`C` 均不是仓库，报告没有可拉取的仓库，不检索其子目录。
