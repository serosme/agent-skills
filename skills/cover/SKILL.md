# Cover

## 这是什么

编码后的单测门禁。加载后，它定义「补单测这件事做到什么程度算够」，不是一段执行脚本：用户说「补单测 / 覆盖一下 / 跑测试」时按它工作，没说就不主动跑。一轮开发里可以反复调用，每次都只针对当次改动。

- 只补测试，不改生产代码：不改实现、不抽方法、不加测试缝、不改可见性、不改依赖注入点。构建脚本与测试配置默认不改；确需加测试依赖时先确认，只做最小改动并单列。
- 结论只有两个：通过、阻断，没有「带缺口通过」。阻断项记下来，继续把能测的测完、能跑的全量跑完，最后统一报告。只有前提缺失（无单测命令、依赖装不上、意图不清、范围不清、没有可测逻辑）时才提前停。

## 什么时候开始

- 触发：编码告一段落，用户要求补单测、看覆盖、跑测试；或本次改动已定，要锁行为。
- 范围默认是 `git diff HEAD` 加未跟踪的生产文件；已提交时给提交区间或分支，也可以指定文件或目录。提交区间的终点必须是当前工作树对应的 commit（`git rev-parse HEAD`），不是就先问，否则行号与源码会错位。没有改动就问覆盖什么；历史代码的未覆盖不追。
- 同一批未提交改动里再次调用（第一次 cover 之后又改了代码）：当次改动以上一次 cover 结束时的生产文件快照为基线，用哈希比对加 diff 界定；报告里注明本次范围是增量还是累计。快照存到仓库外的临时目录，每个生产文件放一份副本，外加 `文件:哈希` 清单；下次用 `git diff --no-index -U0 <临时副本> <当前文件>` 取行级增量。用完不留在仓库里。
- 意图来源：`docs/<需求名>/<编号>.md`、接口契约或开发人员口述。要能回答应接受、应拒绝、应保持不变；答不上，就写不出有依据的断言。口述来源记下原话、人与时间。
- 单测命令：优先取 `AGENTS.md` 命令表，其次构建声明。必须明确到单测；混跑时，先问清要跑的单元测试范围或标签；集成与 E2E 不跑。
- 开跑时给覆盖范围内的生产文件做快照（`git hash-object --no-filters`），结束时重算比对。

## 守什么

### 覆盖范围

- 本次新增、修改的每一行与每一个分支，都至少被一条绿色用例执行。删除的行不要求覆盖，但要清掉对应的失效用例。
- 改动行 = diff 里新增与修改的行，按新文件行号计（`git diff -U0`）。包声明、import 等非可执行行不计；未跟踪文件按整文件的可执行行计；排除生成代码或纯样板时，要在报告里单列，并说明由哪条用例覆盖。
- 纯样板（getter、DTO、纯委托）不单独写用例，由上层用例覆盖；覆盖不了就列阻断。
- 文件内的启动装配行（进程入口、`listen`、`require.main` 判断、框架启动器、依赖装配）不承载业务判断，单列为「装配行（交由 test 覆盖）」，不计入覆盖缺口、不判阻断；每条排除行都要在报告里列出，并说明为什么不是业务判断。业务判断不能借这个口径排除：把逻辑放进装配文件的照常覆盖，覆盖不了就阻断。
- 不可达、要改生产代码才能测、实现多出来的分支：列阻断。不为凑覆盖率造业务上不可能的输入。

### 期望从哪来

- 接受、拒绝、边界、状态迁移，由业务意图或接口契约定义，不由实现分支反推。实现允许但业务禁止 → 阻断，不写绿测试固化；业务未定义 → 先问，问不到阻断。
- 与意图求差集：意图有、代码没有；代码有、意图没有；两边对不上。三类都记阻断（位置 + 差异），交开发人员处理；不写红用例、不改代码、不按现状迁就。
- 可疑行为记阻断：缺守卫、缺回滚、缺校验、缺状态迁移，吞异常，无依据的空值兜底，重复副作用。判断不了先问。
- 契约外的防御分支（非法 JSON、null、非字符串、缺字段、类型不符这类需求未定义的输入）：不写业务期望，列为「防御行」——只断言被拒或兜底，且不产生副作用、不写脏数据，不判业务正确性；报告单列，不计入阻断。兜底把非法输入当成功处理，或产生副作用，仍按可疑行为阻断。依赖异常、仓储抛错这类内部故障导致的 500 不算防御行，按异常路径做反向断言：失败，且没有半成品副作用。

### 断言

- 正向：每个应接受场景都要断言最终业务结果与副作用（返回值、状态迁移、落库对象与关键值、消息体、事件、缓存变更），不能只看返回值。
- 反向：每个应拒绝场景都要断言拒绝表现（异常类型、错误码、兜底值），并断言状态、库存、余额、消息与外部副作用不变。
- 边界两侧：边界内正向通过，边界外反向拒绝；参数空、非法各一条反向。异常路径按反向处理：超时、抛错、依赖不可用时，断言回滚、补偿或状态不变，不留半成品。
- 幂等：有显式幂等判断的方法，一正一反（业务完成 + 无重复副作用）；无幂等语义的写明不适用，不硬造。
- 不算覆盖：只断言非空、非异常、被调用、调用次数或顺序；无字段级业务值的快照；`any()` 宽松匹配；恒真；类型或实例；日志条数；断言私有字段、内部计数、中间值或日志文本；期望值由实现或同一辅助函数反推；只断言一个字段、放过其他结果。
- 一用例一行为，独立、确定、可单跑；不依赖顺序，不共享可变状态；时间、随机数、UUID 固定；测试名写业务语义；不用 `verify` 参数代替业务结果；不 mock 被测类本身与领域对象，替身只用于进程内协作者。
- 已有断言只许按意图变强，或按依据改，不许静默弱化；变更逐条列原断言、新断言与依据。

### 单测边界与外部隔离

- 单元 = 改动方法的公开入口（或一个类、一个服务）。跨单元装配、事务边界、真实 SQL、网络、消息最终一致性不在这里，归集成/E2E，或按 `sequence` 的图交给 `test` 验证；单测证明不了的列阻断。一个编排方法内部用 fake 完成全部调用，仍算单元，不算跨单元。
- 用例在进程内自给自足：断网、无 Docker、无数据库服务、无第三方账号也能跑。需要外部进程、外部端口、连接串或凭据才能通过，就是违例，判阻断。
- 按边界替换：库/ORM → 内存 fake 仓储；缓存 → 内存 map；MQ/事件 → 记录型 fake；HTTP/RPC/SDK → 进程内 fake 客户端（预设响应与异常）；时钟/随机/UUID → 固定值；文件 → 临时目录；环境变量 → 显式参数。失败路径用 fake 抛错或返回坏响应构造，不依赖真实服务的不稳定行为。
- 进程内嵌入式库（H2、SQLite 内存模式）不算外部服务，可用于仓储实现；SQL 方言差异列风险，需要真实方言才能验证的分支仍阻断。
- 不用 `@Disabled`、`skipIf`、环境探测、条件短路或排除规则装绿；不把集成/E2E 放进单测目录。

### 绿的标准与证据

- 本次相关测试 0 失败、0 跳过、0 未执行；全量相对基线 0 新增失败、0 新增跳过、0 新增未执行。
- 基线集与结束集都按「测试标识 + 状态」记录并逐项对比。新增 = 结束集中不在基线集里的项；基线项消失必须归因为删除、改写或重命名，否则按未执行判新增并阻断；归因不明也阻断。
- 与本次无关的基线失败或跳过：单列并记决定人，不修、不跳过、不阻断。覆盖本次改动行或分支、或失败原因指向本次改动的基线项，按本次相关处理，不按基线豁免。决定人拿不到按阻断。
- 覆盖率的主指标是源码级改动行与分支 100%（以改动行清单与分支普查为基准）。有工具就给工具与命令，尽量裁剪到 diff；裁剪不了就给全量数字加裁剪方法。无工具就给逐行覆盖表（改动行 → 绿色用例 `文件:行`）与分支普查（已绿变体 + 绿色用例）。覆盖率命令要连服务时不跑，按无工具处理。
- 分支普查从 diff 独立推导：`if` 2、`switch` case 数 + default、`catch` 2、循环 3、`&&`、`||` 短路组合、`try`/`finally` 2、三元 2、每个边界 2、参数空或非法各 1。未列出的源码构造按实际出现计，并写清依据。计划缺口 = 应有变体 − 计划覆盖变体 − 阻断变体。
- 补测期间生产文件哈希与开跑快照一致；测试依赖或配置如有经确认的最小改动，单独列出；测试文件之外没有未列出的改动。
- 不为覆盖率写无断言用例、加忽略标记、跳过用例，或改实现形状迁就测试；不做「临时改坏再还原」的变异抽查。

## 什么时候停下问人

- 没有测试框架，要不要引入。
- 单测命令跑不起来、依赖装不上、命令必须连库或缓存或第三方。
- 意图来源拿不到，或业务没定义某个分支的期望。
- 某行或某分支不改生产代码就没法测（不可达、需要测试缝）。
- 改动大到一次覆盖不完：按模块拆批，报已完成与未完成，未完成即阻断。
- 与本次无关的基线失败或跳过怎么处理（要决定人）。
- 已有断言要不要变强或改写（要变更依据）。

## 结果怎么给

- 第一行给结论与计数：改动方法、改动行、改动分支、行为、正/反向断言数、本次相关测试（通过/失败/跳过/未执行）、新增用例、全量用例、全量失败/跳过/未执行、新增失败/跳过/未执行、阻断项。用例数按测试运行条数计；参数化的一次运行算一条。
- 行为 → 断言映射表：行为（场景 → 期待）| 类型 | 用例名 | 断言点（业务结果）| 测试文件:行 | 期望值 | 期望来源 | 状态。
- 分支普查表（绿色态）：分支/条件 | 应有变体 | 已绿变体 | 阻断 | 缺口 | 绿色用例 | 推导依据；附 diff 构造清单与变体公式。
- 改动行覆盖表；外部依赖隔离清单；测试命令与结果；基线集与结束集的对比表（含删除、消失、改写、重命名的归因）；测试文件清单。
- 生产文件开跑与结束清单、各文件哈希与 `git diff --stat`，证明生产代码未变；测试依赖或配置改动（无，或列文件、内容、确认人）；既有断言变更（原断言、新断言、依据）。
- 意图差集与阻断项：每条有位置、现象、为什么阻断、需要什么改动或测试缝、后续由谁验证（由开发改设计，或转集成/E2E、由开发人员或 `test` 技能验证）。
- 确认记录（人 + 时间）；工作区状态（未提交、HEAD、`git status`）；部分完成时列已覆盖方法、已写用例、未覆盖项与当前判定（阻断）；环境声明（未启动外部服务、未配连接串、未监听端口，用进程内嵌入式库时注明）。
- 报告在会话里给出（开发人员指定位置时才落盘），在最后一次编辑与全量运行之后生成。

## 示例

输入：`OrderService.pay` 新增支付、重复支付拒绝、余额不足拒绝、金额 0 拒绝、金额等于余额通过、超时回滚；范围文档要求超时回滚恢复库存。

- 行为与断言：正向——支付成功 → 订单 PAID、余额 900、库存扣减 1；金额等于余额 → 通过。反向——重复支付、余额不足、金额 0/空/非法 → 分别断言错误码，且订单、余额、库存不变；超时 → fake 抛超时，断言订单回滚、库存恢复 10。
- 期望来源：支付、拒绝、边界来自接口契约与范围文档（超时回滚恢复库存），不按实现分支反推；文档未定义的上限值不造用例。
- 分支普查：3 个 `if` × 2 + 1 个 `catch` × 2 + 1 个边界 × 2 + 参数空或非法 2 = 12，已绿 12，0 缺口。
- 隔离：单元是 `pay`，仓储、账户、库存、时钟是 fake 边界；未启动数据库、容器与 mock server。
- 报告：判定通过；改动方法 1、改动行 14、改动分支 5（变体 12）、行为 8、正/反断言 2/6、本次相关 8 通过；全量 15 条中 14 通过、0 失败、1 跳过（基线已有，决定人张三 2026-11-20 确认与本次无关）、0 未执行；补测前后生产文件哈希一致；测试文件新增 `OrderServiceTest.java` 8 条；未提交、未做变异抽查。

反例：为让用例变绿而改实现、加测试缝、把可疑行为按现状写成期望，或起 MySQL 容器跑通再报通过，都是错的。改动是只能靠真实数据库验证的仓储方法时，按阻断报告，不起数据库、不改代码。
