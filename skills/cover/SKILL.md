# Cover

## 目标

这是编码之后的收尾门禁：不管代码是怎么写下来的，落下来的每个有业务逻辑的新增或修改方法，它的每个分支、变体、状态迁移与副作用都要有断言业务结果的用例；跑完给出行为覆盖与代码覆盖证据，并判定通过、带缺口通过或阻断。

有业务逻辑的行为没有用例、已知实现 bug 未被接受、未测项不在白名单、意图缺口未澄清，都判阻断。绝对要求只作用于「通过」；带缺口通过分两种：无接受人的客观缺口（无覆盖率工具、有工具但分支覆盖数据缺失、五字段齐全的未测白名单、抽查不适用）和有接受人的人为缺口（已接受的红用例或可疑行为）。

## 前置条件

### 必要输入

- 覆盖范围：默认 `git diff HEAD` 里的生产代码；已提交时给提交区间或分支；也可以指定文件或目录。没有改动时先问要覆盖什么。
- 意图来源：范围文档 `docs/<需求名>/<编号>.md`、接口契约或开发人员口述。必须能回答应接受、应拒绝、应保持不变；拿不到就停，见 **缺失处理**。
- 测试框架与命令：优先取 `AGENTS.md` 的命令表，没有就从构建声明文件里找；找不到就问。
- 覆盖率命令：同样先取命令表，没有就从构建声明文件里找；没有覆盖率工具也能做，用映射表证明行为覆盖，结论最高带缺口通过。

### 权限与工具

- 读取生产代码与测试目录，写测试文件。
- 运行仓库的测试命令；有覆盖率命令时一并运行。
- 抽查时可临时改坏生产代码，必须立即还原并核对工作区；还原不了就按阻断处理。
- 需要测试缝时先确认，按最小改动改，并补上该缝行为的用例。

### 缺失处理

- 仓库没有测试框架：先问是否引入；不引入就说明无法补可运行的单测，停下。
- 测试命令跑不起来或依赖装不上：报告并停，不换框架，不装全局工具。
- 意图来源拿不到：先问；问不到就停，报意图缺口，不按最小解释继续。
- 改动里没有可测的业务逻辑，只有配置、样式或生成代码：说明并停，不硬造用例。
- 改动大到一次覆盖不完：按模块拆，报已覆盖与未覆盖，不把没跑的算成覆盖。
- 范围、测试命令或覆盖率命令判断不了：先问，不猜。
- 没有覆盖率工具：继续做，用映射表证明行为覆盖；结论最高带缺口通过，写明「无覆盖率工具，代码覆盖未验证」。

## 执行步骤

### 步骤 1：定范围，列行为

- 操作：
  - 从 diff 取新增、修改、删除的生产代码方法，排除测试、配置、生成代码与纯样板。
  - 对每个方法列行为：正常路径、每个 `if`/`else if`/`else`/`switch` 的 case/`catch`/提前返回、循环的零/一/多、三元与 `&&`/`||` 短路、`throw`、`try`/`finally` 与异常中途、lambda 与流内部、参数空/边界/非法、状态前置与迁移、副作用（写库、发消息、改缓存、发事件）、幂等判断（去重键、重复提交，含唯一约束或注解实现的）。
  - 私有方法通过公开入口覆盖；复杂到入口覆盖不了的，报告并建议提取。建议提取不改变判定：该分支仍要映射行为，未覆盖按未测准入或阻断处理。
  - 样板方法（getter、DTO、纯委托）不单独写用例，由上层用例覆盖，在报告里列出；判断不了时按有业务逻辑处理。
  - 删除的方法或分支单列，后面处理失效用例。
  - 每条行为写成「场景 → 期待」，测试名按仓库语言习惯取这句的意思。
  - 输出分支普查表：分支/条件 | 覆盖构造数 | 应有变体 | 已映射变体 | 缺口 | 推导依据。应有变体按类型规则从 diff 独立推导，不按已映射数反填，推导依据写公式与合计；类型规则：每个 `if`/`else` 两侧、每个 `switch` case 与 default、每个 `catch` 的正常与异常两条、循环 0/1/多、每个 `&&`/`||` 短路组合、三元两侧、`try`/`finally` 两侧、每个参数空/边界/非法、每个边界两侧；报告再写 diff 构造清单（位置 + 类型）与 diff 分支/条件构造数 = 普查覆盖构造数。
  - 输出副作用与不变量清单：每个写库、消息、缓存、事件一行；每个状态迁移的允许与拒绝一行；每个跨方法不变量（调用顺序、事务边界、回滚一致性）一行，映射行为。
- 完成标志：每个有业务逻辑的改动方法都有行为清单；分支普查表逐分支给出应有变体数与推导依据，应有变体数 = 已映射变体数，缺口为 0；diff 分支/条件构造数 = 普查覆盖构造数；副作用、状态迁移与跨方法不变量都有映射；没有「正常情况」这种笼统条目。

### 步骤 2：意图对差集

- 操作：
  - 读或问意图来源，列出应接受、应拒绝、应保持不变的场景，每条记下来源（文档文件:行或口述原话）。
  - 与步骤 1 的行为清单求差集：意图有、代码没有的（缺守卫、缺回滚、缺校验、缺状态迁移）；代码有、意图没有的（多写的行为）；两边对不上的。
  - 差集逐条处理：明显是 bug 的写红用例并标「待裁决」；不确定的列「可疑」；意图本身不清的标「意图缺口」并问；问不清就停，按阻断处理。
  - 可疑行为包括：实现与意图不一致、应有而未有的守卫或回滚或校验、空值返回、吞异常、边界判断、缺状态守卫、重复副作用。
- 完成标志：差集表已给出，每条有来源与处理结论（红用例名、可疑、意图缺口）；没有默认代码即意图；没有未澄清的意图缺口。

### 步骤 3：审计已有用例

- 操作：
  - 先跑一次基线，记录已有失败与跳过，后面只对本次相关的失败负责。
  - 对清单里的每条行为找已有用例：有断言、断言在业务结果上、覆盖该分支、期望与意图一致，才算已覆盖；期望与意图不一致的列为可疑或待裁决，不算已覆盖。
  - 弱用例按 **单测** 约束补强；同一行为只留一条最清楚的，不为凑数保留重复。
  - 既有断言只许按意图变强或按依据改，不许静默弱化；改了哪条断言、原断言、新断言、依据，都要在报告里列。
  - 已有测试因本次改动失败时，按 **不改实现** 一节判断，不偷偷改期待；删除代码导致的失效用例按 **不改实现** 处理。
- 完成标志：每条行为都有「通过 / 待补 / 未测白名单 / 可疑」的结论；弱用例已补强；既有断言变更已列出。

### 步骤 4：补写用例

- 操作：
  - 按 **单测** 约束写用例；测试放在仓库惯例的目录，用既有框架与命名，没有测试目录时按仓库惯例建一个。
  - 外部依赖（时间、随机数、ID）用仓库已有做法替换；没有就选最小的依赖注入，不引框架。
  - 需要改生产代码才能测时，按 **不改实现** 一节先确认；默认不改。
  - 可疑行为按 **可疑行为** 一节处理；意图差集里的红用例按「待裁决」单列，不当成通过。
  - 删除代码导致的失效用例：按 diff 与意图依据删除或改写，记录删除、改写的用例条数，在报告里列出。
- 完成标志：清单里每条「待补」都有用例；每条行为有用例或拟按 **未测准入** 登记；红用例、失效用例与删除条数都已处理并列出。

### 步骤 5：跑全量，补空洞

- 操作：
  - 按仓库命令跑全量；命令表要求构建或 lint 时一并跑；记录基线用例数、本次新增用例数、本次删除用例数。
  - 按 **覆盖率** 约束找空洞并补齐，或按 **未测准入** 登记。
  - 抽查：每个有业务逻辑的改动方法至少抽查一条最容易弱断言的分支（边界、短路、循环零次）。临时改坏实现，必须可编译且只改变目标分支语义；确认映射表中该分支对应用例至少一条变红；立即还原并核对工作区与改动前一致。
  - 抽查失败处理：没有用例变红，补强该分支用例后重抽；重抽仍无红，判阻断（存活变异）；编译失败不算抽查，重做；变红的不是该分支映射的用例，重抽，不得事后追认为该分支证据；还原不了，一律阻断。
  - 抽查不适用只限于未测白名单里的方法（没有单测，无法抽查），写明原因与判定影响；白名单外做不了按阻断处理。
  - 测试失败时按 **不改实现** 一节判断；红用例要分清「用例错」与「实现 bug」，实现 bug 未接受就是阻断项。
  - 把拟登记的未测项、待裁决红用例、可疑行为一次性交开发人员确认决定人或接受人，记录谁、何时、什么渠道或原话；未确认的按阻断处理。
- 完成标志：每条行为都有结论；没有本次新增的跳过或未执行；改动行与改动分支都有结论；全量用例数 = 基线 + 本次新增 - 本次删除；每个有业务逻辑的方法抽查已做且已还原，或属于未测白名单的「不适用」；需要确认的项都有确认记录。

### 步骤 6：验收并给结论

- 操作：
  - 对照 **验收标准** 逐条核对，未过项按 **判定** 归类。
  - 按 **判定** 给三态结论；有阻断项就判阻断，不写成通过。
  - 按 **交付内容** 生成行为 → 用例 → 断言映射表，计数由表汇总，再在会话里报告，说明未测项、可疑行为、红用例与未验证部分，然后停。
- 完成标志：验收项全过或未过项已按判定归类；结论与判定条件一致；映射表已给出；阻断项、未测项、可疑行为都已列出；报告已给出。

## 约束

### 测试范围

- 测试范围只覆盖本次改动的方法；无关测试、配置与部署脚本保持原样；不提交。
- 历史代码的未覆盖不追，单独说明，不混进本次结论。
- 只做确定性单测；竞态与性能行为归 **未测准入** 的「只能集成测试」并附理由；方法里显式的幂等判断要测。

### 单测

- 一个用例只验证一个行为；同一行为的多个字段（金额与状态、条数与内容）可以一起断言，不同行为不混。
- 每个分支与变体都要有用例，或按 **未测准入** 登记并给证据；只测正常路径、只断言实现细节不算覆盖。
- 成立断言落到具体业务结果（返回值、状态迁移、落库对象与关键值、消息体、副作用）；同一行为的对外可观察结果要一起断言，不能只断言返回值而放过错误副作用。
- 只断言非空、非异常、被调用、调用次数或顺序、没有字段级业务值的快照或黄金文件、`any()` 宽松匹配、恒真断言、只断言类型或实例、只断言日志条数，都不算覆盖；只断言一个字段而放过其他对外结果，也不算。
- 断言实现细节（私有字段、内部计数、中间拼接值、日志文本）不算覆盖；期望值由被测实现或同一个辅助函数推导出来的同义反复断言也不算。
- 拒绝断言写条件与对外表现（异常类型、错误码、兜底值）；不断言完整文案。
- 依赖用 fake 或 mock 隔离；断言落在 fake 的内存状态或返回值上，不用 `verify` 的调用参数代替业务结果；不 mock 被测对象自己的业务判断，也不 mock 被测类本身。
- 用例之间不依赖执行顺序，不共享可变状态，数据就地造；时间、随机数、ID 可替换。
- 测试必须能独立跑，不连真实数据库、缓存、网络与第三方服务。
- 测试名写业务语义，不写实现细节；测试里允许重复，不为了复用把用例写成参数化迷宫。

### 未测准入

- 只允许三类：不可达（附位置与原因）、框架或样板胶水、只能集成测试（附为什么单测覆盖不了、试过 fake 或依赖注入仍无法隔离的原因）。
- 每条未测项写清五字段：行为或方法、类别、位置、证据、决定人。决定人是开发人员。
- 五字段缺任一即阻断；「不好测」不是类别；可疑行为不是未测类别，不能走白名单。
- 登记粒度到行为或分支，方法级登记必须逐分支列出；无分支的方法写「0 个变体」，不能一个方法级条目吞掉整组分支。
- 白名单之外的行为没有用例，一律算未覆盖，判阻断。

### 覆盖率

- 行为覆盖是主指标：状态为「通过」的行为数 / 总行为数，分子分母都来自映射表；代码覆盖只用来找空洞。未覆盖 = 总行为数 - 通过数。
- 硬性要求：本次改动新增与修改的行都要被用例跑到，新增与修改的分支与变体都要有用例或按 **未测准入** 登记；历史代码不追。
- 有覆盖率工具时给数字（改动行、改动分支、全量行与分支）；没有工具时不写代码覆盖数字，不写「全量已覆盖」，只写「无覆盖率工具，代码覆盖未验证」，用映射表证明行为覆盖。
- 有工具但取不到 diff 覆盖率时，用 `git diff` 的改动范围对照全量覆盖率报告手工取数，并说明报告来源与取数方法；分支覆盖数据缺失时结论最高带缺口通过。
- 不为覆盖率写无断言的用例、不加忽略标记、跳过用例，或改实现形状迁就测试。

### 可疑行为

- 可疑行为是实现与意图不一致，包括应有而未有的守卫、回滚、校验、状态迁移，以及空值返回、吞异常、边界判断、缺状态守卫、重复副作用。
- 只能走两条路：按意图写会红的用例并标「待裁决」，或由开发人员明确接受并记为「带缺口通过」；不能列入未测白名单。
- 待裁决与未接受的可疑行为都算阻断；接受的要列出接受人、影响与确认记录。

### 不改实现

- 默认只写测试，不改生产代码；抽查临时改坏、测试缝是仅有的两个例外，都要在报告里单列。
- 测试缝要先确认，按最小改动（注入时间、随机数、客户端，或提取纯函数）改，改完为该缝行为补用例。
- 测试失败是实现问题的，报告并停，由开发人员决定怎么改；改完再跑本技能。
- 已有测试因本次改动失败：先判断是行为有意变更还是实现坏了；有意变更要有依据（范围文档或开发人员确认），否则报告，不偷偷改期待；删除代码导致的失效用例，按同样的依据删除或改写，并列出删除、改写条数。
- 不许静默弱化既有断言；改了哪条断言、原断言、新断言、依据，都要在报告里列。

### 异常

- 能安全修正的测试问题（命名、重复、数据构造）直接修正；影响正确性的（实现 bug、框架缺失、范围不清、意图来源缺失）停止并报告。
- 测试结果里有跳过或未执行：报条数与原因；基线已存在的单列，本次新增的直接判阻断。
- 用例期待错、环境问题、依赖缺失：改用例或报告，不改实现迁就。
- 中途叫停：报已覆盖的方法、已写的用例、未完成项与当前判定。

## 输出与验收

### 判定

- 结论只有三个：通过、带缺口通过、阻断。
- 状态只有六个：通过、红-待裁决、红-用例错、未测白名单、可疑、待补。映射表与报告总数都引用同一套词；普查表只报应有变体、已映射变体、缺口与推导依据；最终报告里出现「待补」即阻断。
- 阻断：本范围内有业务逻辑的行为没有用例且不在白名单；待裁决的红用例；红-用例错未修复且未获接受；未接受的可疑行为或已知实现 bug；未测项五字段缺项；意图缺口未澄清；生产代码未经确认被改或抽查未还原；本次新增跳过或未执行；映射表缺失，或分支普查的应有变体数 ≠ 已映射变体数、diff 分支/条件构造数 ≠ 普查覆盖构造数、应有变体未按类型公式推导、副作用或不变量清单缺失、用例数对不上；删除处理无依据；存活变异或抽查无效；中途叫停或未完成。
- 带缺口通过：所有能测的行为都有用例，但有客观缺口（无覆盖率工具、有工具但分支覆盖数据缺失、白名单、抽查不适用）或人为缺口（开发人员明确接受的红用例或可疑行为）；客观缺口写明未验证内容，人为缺口逐条列接受人、影响与确认记录。
- 通过：所有行为有用例并断言业务结果；没有红用例；没有未测项与未澄清的意图缺口；映射表、分支普查、副作用与不变量清单对账一致；每个有业务逻辑的方法抽查已做且已还原，或属于未测白名单的「不适用」；覆盖率证据已取得或已手工核对；验收标准全过。
- 兜底：任一验收标准未满足，属于客观缺口条款（无覆盖率工具、有工具但分支覆盖数据缺失、白名单、抽查不适用）的判带缺口通过并逐条列出；其余一律阻断。

### 交付内容

在会话里报告。第一行给结论（通过 / 带缺口通过 / 阻断）与总数（改动方法、行为、本次新增用例、修改用例、全量用例、未覆盖、阻断项）：

- 行为 → 用例 → 断言映射表：行为（场景 → 期待）| 用例名 | 断言点（业务结果）| 测试文件:行 | 期望值 | 状态。期望值写断言里出现的业务期望值；一行有多个断言时给多个行号或「行号 + 断言摘要」。覆盖本次改动的全部有业务逻辑方法，全绿方法也保留映射，计数由表汇总。
- 分支普查表：分支/条件 | 覆盖构造数 | 应有变体 | 已映射变体 | 缺口 | 推导依据；附 diff 构造清单（位置 + 类型）与变体公式；逐分支给出公式与合计，应有变体数 = 已映射变体数，diff 分支/条件构造数 = 普查覆盖构造数；删除分支单列。
- 副作用与不变量表：副作用/状态迁移/跨方法不变量 | 映射行为 | 状态。
- 意图差集表：意图场景 | 来源 | 代码现状 | 处理；应有而未有的行为、代码多出的行为、意图缺口都列出。
- 未测项：行为或方法、类别、位置、证据、决定人；五字段缺任一项列为阻断。
- 红用例与可疑行为：用例名、位置、现象、为什么可疑、待裁决还是已接受、接受人与确认记录。
- 测试命令与结果：通过、失败、跳过、未执行条数；基线失败单列；全量用例数 = 基线 + 本次新增 - 本次删除。
- 覆盖率：工具与命令、改动行与改动分支、全量行与分支；没有工具时写「无覆盖率工具，代码覆盖未验证」，有工具但取不到 diff 覆盖时写报告来源与取数方法。
- 抽查结果：每个方法抽查了哪条分支、哪条用例变红、是否已还原；存活变异、编译失败、未测白名单不适用都写明。
- 生产代码改动：默认无；测试缝或抽查临时改动的文件、行；测试缝的确认人、抽查的还原情况；附 `git diff --stat`。
- 既有断言变更：改了哪条断言、原断言、新断言、依据。
- 删除处理：删除的方法或分支、对应失效用例、删除或改写条数、依据。
- 历史未覆盖：与本次无关的未覆盖单独一行或一节，不混进本次结论。
- 样板方法：方法名、判定依据（getter、DTO、纯委托）、覆盖它的上层用例。
- 确认记录：未测项、红用例、可疑行为的决定人或接受人，何时、什么渠道或原话。
- 部分完成：已覆盖的方法、已写的用例、未覆盖项、当前判定。
- 工作区状态：未提交；无关文件未改。
- 报告在最后一次编辑与全量运行之后生成，映射表行号与覆盖率数据以此为准。

### 验收标准

- 结论与 **判定** 条件一致：有阻断项时不是通过；带缺口通过逐条列了客观缺口或接受人、影响与确认记录。
- 行为映射表覆盖本次改动的全部有业务逻辑方法，计数与表一致；每行有测试文件:行与期望值；每个有业务逻辑方法至少抽查一行能对上测试代码。
- 分支普查表逐分支给出覆盖构造数、应有变体与推导依据，附 diff 构造清单，公式可复算，应有变体数 = 已映射变体数，diff 分支/条件构造数 = 普查覆盖构造数；每个变体有用例或白名单登记；删除分支单列。
- 副作用与不变量表覆盖每个写库、消息、缓存、事件与跨方法不变量，各有映射行为。
- 意图差集已给出，每条有来源与处理结论；应有而未有的行为有红用例或未测登记；没有未澄清的意图缺口。
- 每条行为有用例，或按 **未测准入** 登记且五字段齐全；没有「不好测」这种理由；可疑行为没有走白名单。
- 断言落在业务结果上，覆盖同一行为的全部对外可观察结果；没有非空、非异常、被调用、调用次数、无字段级业务值的快照、宽松匹配、恒真、只断言类型或日志条数这类弱断言。
- 既有断言没有静默弱化；变更逐条列出原断言、新断言与依据。
- 用例独立、确定，不连真实数据库、缓存、网络与第三方服务；时间、随机数、ID 已替换。
- 本次相关的用例都有结论：通过；或红但已分类并处理（用例错已修复或接受、实现 bug 已报告、待裁决已记录）；基线失败单列，未改实现迁就。
- 没有本次新增的跳过或未执行；全量用例数 = 基线 + 本次新增 - 本次删除。
- 改动行与改动分支都有结论；没有覆盖率工具时写「无覆盖率工具，代码覆盖未验证」并用映射表证明行为覆盖，结论不是通过；有工具但分支覆盖数据缺失时写明工具与缺失原因，结论最高带缺口通过。
- 每个有业务逻辑的方法都做了抽查并已还原，或属于未测白名单的「不适用」；没有存活变异、编译失败的假抽查，或没用未做抽查换通过。
- 没有为覆盖率写空断言、加忽略标记、跳过用例，或改实现形状迁就测试。
- 可疑行为已列出并标了待裁决或接受人；未擅自修改实现。
- 没有提交；无关测试、配置与部署脚本保持原样；生产代码改动只有确认过的测试缝或已还原的抽查。
- 删除处理有依据与条数；历史未覆盖与本次结论分开；样板方法已列出。
- 报告在会话里给出，与实际一致；未验证的部分已标明；报告生成于最后一次编辑与全量运行之后。

## 示例

输入：`git diff` 显示 `OrderService.pay` 新增支付、重复支付拒绝、余额不足拒绝、超时回滚四条分支，`OrderRepository.findPending` 加了一个查询方法。范围文档写着「超时回滚要恢复库存」。

行为清单（场景 → 期待）：`pay` 支付成功 → 订单 PAID、余额减 100；重复支付 → 拒绝、订单不变；余额不足 → 拒绝、订单不变；金额 0 → 拒绝；金额等于余额 → 通过；超时回滚 → 订单回滚；超时回滚恢复库存 → 库存恢复；`findPending` 查询待处理订单 → 返回列表。

| ------------------------------------------------- | ---------- | -------- | ---------- | ---- | -------- |
| `pay` 3 个 if/else 条件（重复、余额不足、金额 0） | 3          | 6        | 6          | 0    | 3×2      |
| `pay` 1 个 catch（超时）                          | 1          | 2        | 2          | 0    | 1×2      |
