# Test

## 这是什么

在真实环境里验证一条业务流：怎么用接口、只读库、页面自动化去跑，拿什么当证据，结果怎么判。加载后它是一套判据，不是流水线：用户说「跑测试 / 验证这个功能点 / 临时验一下」时按它做，没说就不主动跑。

- 只验证被点名的那条流程（正式验证时，就是图覆盖的流程）。图上的 alt、前提与拒绝负例、状态副作用都在流程内；方法内部的参数校验、状态机非法迁移、单接口 500 归 `cover` 的单元测试（流程主干实际出现的 5xx 按偏差归因处理）；并发、幂等重放、消息最终一致性、性能是图外专项，开发人员点名才做。
- 业务不变量与库端实测是 AND：有落库副作用的步骤，接口返回成功不能代替库里查到的结果。
- 图不自我证明：图与代码对不上，说明不了谁错，业务流程对不对由人判断；图本身画错也测不出来；所有图跑完，只说明图覆盖的正向流程不退化，不等于覆盖所有情况。

它有两种用法，随时切换，不需要等图：

- **临时验证（无图）**：开发到一半，只想验某一步或某个假设时用。给一个目标与范围（哪个接口、哪条路径、要确认什么），按下面的证据与工具要求直接跑。结论写「临时结论」，并注明不是按图验收、不能代替正式验证。门一（环境与非生产）仍要过。
- **按图验证（正式）**：有一张 `sequence` 图时，按图逐行跑，给出通过、未通过或未跑通，作为这个功能点的验收结论。

补单测、画图、验流程是三种能力，没有先后：`cover`、`sequence`、`test` 可以任意顺序、任意组合，按需使用。

## 什么时候做

- 输入：正式验证要一张 `sequence` 图，只按图验收（只有入口表与结果行的文件也算）。临时验证不需要图，由人给出功能点、目标与范围，口述也行。功能点的编号与名称按图或人给的写；缺哪个就问，不自己编，也不默认成 `01`。
- 环境：工作区根 `AGENTS.md` 的服务表（接口基地址、页面地址）与基础设施表（库名、主机/端口）；数据库连接名由开发人员给。`AGENTS.md` 缺失、关键项为空或可能过期时先问。
- 凭据：能登录的测试账号或 token；两轮比对时，准备两套账号或隔离数据。
- 通道默认走接口，不碰浏览器；开发人员要求页面时才用页面；要求两轮比对时，先接口后页面，分别报告，不落文件。
- 图上有 `stale@` 行：先说明，问这张图是否仍可作为本次依据；不能就停。

## 守什么

### 清单要覆盖整张图（按图验证）

- 入口表、时序、前提与拒绝、状态副作用都要落到清单：每一步记「做什么 → 怎么执行（方法与路径，或页面动作）→ 核对项（业务不变量与该看到的库端结果）→ 实际结果记在哪」。
- 状态副作用逐行落到对应步骤；前提与拒绝里的身份与初始状态作前置，每个「必须被拒」的动作记一行负例。
- alt 各记一行；带触发条件的 Note 各记一行，标明靠等还是靠调接口验证。
- 负例与 alt 默认用独立会话或新手机号；图语义要求沿用前序状态（如 60 秒内重复请求）时，说明沿用依据，不默认共用可能被前序污染的状态。
- 只有入口表与结果行的文件：按入口表顺序执行，结果行作核对项，不自行编顺序。
- 图外不加行。边界、异常、并发、性能要测，须由开发人员点名，并标 `（额外）`；方法内部的分支不在本技能加。

### 证据要拿得出来

- 接口一次一个请求；登录态、变量、cookie 在同一个执行上下文里保持，用完不落盘，不碰浏览器。
- 页面照用户那一步操作，读页面上看到的结果；不直接调接口绕页面；登录或前置确需接口时，先经开发人员确认。
- 每行记下实际发出的请求或页面动作、状态码与关键返回，或者页面上看到的结果。
- 有落库副作用的步骤，业务不变量与库端实测都要有具体值：查询对象、定位键、结果值（如 `会话表 count=1，手机号 138****`）。「新增一条」要给条数或关键字段值（如 `count=1`、`expire_at=…`）；「状态已变」要给旧值与新值，只给新值证明不了「变」。
- 没有库端对象的步骤，写 `不适用：原因`，并要经开发人员确认（门二）。
- 库端按上面「用什么工具」的约定做只读查询，用刚产生的标识定位（手机号、单号、时间窗）。
- 负例核对「被拒且无副作用」，只断言 400/401 不算过。
- 页面通道只写关键元素、关键数据与页面/库一致性，不展开深业务不变量。
- 结果留在会话里的清单中，不写测试记录文件；缺前置数据就问开发人员要，不造数据（不直接插用户或会话绕条件）。
- 临时验证：范围按目标定，证据标准与正式验证一致（能查库就查库，能走页面就冒烟）；结论写「临时：通过 / 有问题 / 没验成」，不复用正式三档，也不作为功能点的验收结论。

### 偏差要归对类

停在这一步，记下实际返回、页面结果与库端现状，按顺序判断：

1. **环境问题**：连接不可用、查询被拒、连错库、凭据或外部输入不可用。该行记 `未执行`，附报错原文，整份按判定汇总。
2. **图过期或契约破坏**：先看代码与图的入口、顺序、分支、副作用是否还对得上。有对外契约文档或其他消费方、且实现改坏了契约 → 契约破坏。主干返回 5xx → 业务退化，计 `未通过`。返回与图不符、开发人员确认是实现问题但没有契约依据 → 契约破坏或业务退化。只有图与代码不符、且未确认为实现问题，才是图过期；图过期按 `sequence` 的约定，只在时序图回写一行 `stale@<日期> <原因>`，不改入口与时序，该行记 `未执行`。
3. **业务退化**：接口按图走通，但业务不变量或库端副作用不对。该行记 `未通过`。

- 流程自己产生的记录，在库里查不到：先确认是同一个库、同一时间窗、同一标识；确认是本次流程产生的，按业务退化记，不归环境问题。
- `查不到` 与 `无法核对` 先记 `待确认`，确认后回填四类之一；该行不得为 `通过`。
- 未经开发人员确认，不得仅凭图或契约不符，就判实现失败。
- 判断不了就问开发人员。不自己改数据、改配置、改代码去让它过；开发人员要求继续时，跳过该步，记 `未执行` 并写原因，不算通过。

### 判定只有三档（按图验证）

- 以下三档只用于按图验证；临时验证用「临时结论」，见「证据要拿得出来」里的临时验证一条。
- 任一行 `未通过`（业务退化，或确认是实现问题的契约破坏）→ 未通过。
- 否则有 `未执行`（环境问题、图过期、非实现契约破坏、待确认、外部输入等）→ 未跑通。
- 全部行 `通过` → 通过。
- 图上入口表与主干的每一步，以及 alt、负例、Note、状态副作用，都必须有对应行；只进未覆盖、没有对应行时，不得记 `通过`，至少记 `未跑通`。
- 两轮比对分别报告，合并结论按「未通过 > 未跑通 > 通过」；阻断或部分完成时，只禁止写成 `通过`，不降级已出现的 `未通过`。

## 什么时候停下问人

- **门一（开跑前）**：先把环境报给开发人员——`AGENTS.md` 来源与扫描时间、各仓库 HEAD、接口基地址、页面地址、库名与主机/端口、数据库连接名、非生产判定、可能过期项与只读实测差异。再把流程报过去——功能点与依据图（临时验证报目标与范围）、方式、步骤数与每步一句话（含负例与 alt）、断言深度、哪几步要人给输入、负例与 alt 的独立会话或沿用依据、图外不做的部分。等他确认；改了环境或流程就更新再报，改了地址或方式就重查环境。确认前不执行；开跑后加行、改范围，同样先更新计划再确认。
- **门二（写 `不适用` 前）**：只有图上没有库端对象的步骤才可能写 `不适用`，且要经开发人员确认并写明原因；有状态副作用（含页面通道有库端对象）的步骤，只能给库端实测值。
- **门三（判实现问题、图过期、契约破坏前）**：把差异、证据与判断报给开发人员，由他确认性质；不确认就记 `待确认`，整份按判定汇总（不得为 `通过`），在报告里列为未确认项。
- 该停的其他情形：没有时序图；基地址、库名、账号、数据库连接名任一缺失，或 `AGENTS.md` 未确认、可能过期；环境连不上或服务没起来（报告，等开发人员启动后继续；不换环境、不换端口、不自行启动）；图上的入口读不到，或当前代码找不到对应实现（先确认图与代码是否同一版）。
- 外部环节（短信验证码、支付回调、人工审核）拿不到输入时，停下来要，不伪造。
- 只在非生产环境跑；判断不了或指向生产，就先问，不先探活、不先连库。

## 用什么工具

- 数据库：按 `AGENTS.md` 基础设施表给出的连接方式做只读查询，`dbx` 优先。`dbx` 不支持该库（如嵌入式 SQLite）时，用该库原生的只读方式（只读连接、只读账号或文件只读查询），并在报告里注明用了什么、为什么用它；仍拿不到结果，就记环境问题。
- 页面：`agent-browser` 技能，打开页面、操作、读取结果都按它。
- 接口：直接调，不绑定具体 HTTP 客户端；不为绕开报错而改变路径、方法或参数，改成能过的不算测试。
- 环境：优先取 `AGENTS.md`；缺失或过期时用开发人员确认的口述值，不重新扫描仓库生成环境信息。不启动、不重启、不停止服务；可能过期时做只读实测（读配置、环境变量、`git rev-parse`、端口连通性），在门一说明差异，并提示重新运行 `init`。
- 多步串联的临时脚本放临时目录，用完说明不留在仓库；不在仓库里新建测试脚本目录。
- 不写测试用例集，不引入测试框架，不改项目里的测试目录，不改图的入口与时序内容；不碰无关的服务、端口、配置与部署脚本；流程自己产生的数据默认保留，要清理由开发人员做或明确批准；不提交。

## 结果怎么给

- 只在会话里报告，不写测试记录文件。报告只有结论、方式、结果计数、关键核对或失败/未跑步骤、偏差类别与未覆盖项；不写环境、commit、基线、文件名等元数据。
- 通过：首行写 `<编号> <功能点名>（接口流程 / 页面流程，冒烟 / 接口流程，无用户端）：通过`，第二行写 `结果：通过 N / 未通过 0 / 未执行 0`，第三行写 `关键核对：` 加 1 到 4 条业务不变量与实测值（有负例或 Note 时各给一条）。不逐步列全表。
- 未通过：首行结论加一句原因，再给结果计数，然后逐条列 `第 N 步 <步骤>：核对项 <...>；实际 <...>；偏差类别 <图过期/契约破坏/业务退化/环境问题/待确认>`，最后写 `偏差` 与 `未覆盖`。
- 未跑通：首行结论加一句原因，再给结果计数，写 `已跑` 与 `未跑/阻塞`，最后写 `偏差或阻塞` 与 `未覆盖`。
- 通过数等于清单行数（状态副作用并入对应步骤行，不另计；`（额外）` 行不计入）。写 `不适用` 的步骤，要注明经开发人员确认：通过报告可附在该步关键核对后，不占 1 到 4 条；未通过或未跑通的报告，写在该步或未覆盖里。两轮比对分别标方式，并给合并结论。不写密码、完整 token 与手机号中间位（用 `<token>` 占位）。
- 中途叫停：保留会话里已跑的结果，下次重新核对清单，再过一次门一才开跑。

## 示例

功能点「01 短信验证码登录」，时序图取自当前代码。`AGENTS.md` 服务表给出基地址 `http://localhost:8080`，基础设施表给出 `chat@localhost:3306`，数据库连接名由开发人员给。门一确认环境与流程后开跑。

清单六行：取图形验证码、请求下发短信、重复请求 alt、未先取图形验证码提交登录（负例）、提交登录、验证码 60 秒未使用自行作废（Note）。负例用独立会话；重复请求 alt 与 60 秒作废 Note 依赖同一手机号的冷却状态，沿用同一手机号，门一已说明沿用依据。

未通过时的报告：

````text
01 短信验证码登录（接口流程）：未通过（业务退化）
结果：通过 4 / 未通过 1 / 未执行 1
- 第 5 步 提交登录：核对项「会话新增一条，用户进入登录态」；实际「200+token，会话表 count=0，用户没进入登录态」；偏差类别 业务退化
偏差：第 5 步业务退化，开发人员张三确认实现问题，未修。
未覆盖：第 6 步验证码 60 秒作废，因第 5 步已停未等。
````

通过时只写：

````text
01 短信验证码登录（接口流程）：通过
结果：通过 6 / 未通过 0 / 未执行 0
关键核对：验证码记录 count=1 且 60 秒失效、60 秒作废后失效、负例被拒且会话 count=0、会话 count=1 且用户进入登录态。
````

未跑通时：

````text
01 短信验证码登录（接口流程）：未跑通（环境问题）
结果：通过 0 / 未通过 0 / 未执行 6
已跑：无；未跑/阻塞：第 1-6 步，数据库连接不可用
偏差或阻塞：dbx 查询被拒，附报错原文
未覆盖：全部步骤
````

页面方式的差别只在证据：按 `agent-browser` 技能打开登录页，填手机号与验证码，点登录，读跳转结果与页面显示，再查库确认会话落库；不做接口通道那种业务不变量展开。两轮用不同手机号；接口轮第 5 步已判业务退化，页面轮对应步骤记 `未执行`；两份报告分别标方式。

边界案例：图上的系统行为靠等触发条件，例如「验证码 60 秒未使用自行作废」，等满 60 秒再查那条记录；流程因前面的失败已停时，该行记 `未执行` 并写原因，不跳过、不提。功能点没有用户端时，报告首行写 `（接口流程，无用户端）`，不硬造页面操作。
