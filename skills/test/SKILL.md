# Test

## 目标

拿一张时序图或一段口述的流程，按顺序在真实环境里跑一遍：每一步看实际结果，并在库里核对这一步该留下的记录。产物是一份测试记录，写清每一步的实际结果与结论。

两种方式：接口流程是默认，直接调 API；页面流程只在开发人员要求时做，用 agent-browser 驱动页面。两种方式都要用 dbx 核对数据库端，页面流程也不例外。

每一步该在库里看到什么，按这一步的业务判断：新建该多一条记录，更新该看出字段变化，删除该看不到那条记录，状态流转该看出状态对得上。图上不标这些，判断依据是业务本身。

只验证这一条流程，不改代码、不造测试框架、不修数据。

## 前置条件

### 必要输入

- 时序图文件，或对话里给出的一段测试流程。
- 功能点编号与名称；图里有就用图里的，没有就用 `01`。
- 被测环境：接口基地址，页面方式再加页面地址。从 `AGENTS.md` 的服务表取，取不到就问。
- 数据库：DBX 连接名与库名，由开发人员给，或从 `AGENTS.md` 的基础设施表取。
- 凭据：能登录的测试账号，或现成的 token。

### 选择方式

- 默认接口流程，不碰浏览器。
- 开发人员明确要求页面流程时用 agent-browser；要求两者都比对时跑两轮，先接口后页面，各出一份记录，文件名末尾分别加 `-接口` 与 `-页面`。
- 功能点没有用户端，例如定时任务、回调、清理任务，接口流程直接调触发接口或按触发条件等；页面方式不适用，在记录里写不适用，不硬造页面操作。

### 输出位置

- 默认与时序图同目录，名字 `<编号>-<功能点名>-测试.md`。
- 开发人员指定位置时按指定的写。

### 缺失处理

- 基地址、账号、连接名任一缺失就先问，不猜，也不拿生产库凑合。
- 环境连不上或服务没起来时报告并停，不自行换环境、换端口。
- 流程里需要短信验证码、支付回调、人工审核这类外部环节时，停下来向开发人员要输入，不伪造。

## 执行步骤

### 步骤 1：读图出清单

- 操作：
  - 按图从上到下逐步列：这一步做什么 → 怎么执行（请求方法与路径，或页面动作）→ 期待看到什么 → 这一步之后该在库里看到什么。
  - 图的性质是计划时，先确认这块已经落地；没落地就停，报给开发人员，不拿计划当现状测。
  - 图上的 alt 各列一行；带触发条件的 Note 也列一行，标明靠等还是靠调接口验证。
  - 图外不加行：边界、异常、并发、性能要测，得由开发人员点名。
  - 图上没写清期待结果的，问开发人员补一句，写进清单，不自己编。
  - 报给开发人员确认四件事：环境、方式、清单、哪几步需要他给输入。
- 完成标志：清单每行都能在图上对上，或与开发人员确认过的口述清单对上；开发人员已确认清单、环境与方式。

### 步骤 2：核对环境与连接

- 操作：
  - 确认基地址可达；页面方式再确认页面能打开。
  - 用 `dbx doctor --json` 与 `dbx connections list --json` 确认连接可用，再用 `dbx schema list <连接名> --json` 确认连的是要测的库，一个连接下多个库时带 `--database <库名>`。
  - 按地址、库名与开发人员的说明确认这不是生产环境；任一项指向生产就停，问一句。
- 完成标志：地址可达，连接与库已核对，环境已确认非生产。

### 步骤 3：按清单执行并逐步落盘

- 操作：
  - 接口流程用 `curl -sS -i` 一次一个请求，登录态与变量落在同一个 shell 会话里，cookie 用临时 cookie jar。
  - 页面流程先读 `agent-browser skills get core`，打开页面，照着用户那一步操作，读页面上看到的结果。
  - 每步记下实际发出的请求或页面动作、状态码与关键返回，或者页面上看到的结果。
  - 执行完立刻按这一步的业务判断该在库里看到什么，用 dbx 只读查；定位用刚产生的标识，例如手机号、单号、时间窗。
  - 这一步业务上不在库里留记录，库端核对写 `无可查`；不确定该看哪张表时先用 `dbx schema list` 与 `dbx schema describe` 看清结构，或问开发人员，不为了凑一行去查无关表。
  - 每步落一行，不攒到最后一起写。
- 完成标志：清单上每行都有一行记录，没跑的行也已标明。

### 步骤 4：失败与偏差处理

- 操作：
  - 与期待不一致时停在这一步，把实际返回、页面上看到的结果与库端现状写进这一行与 **偏差**，再判断是环境问题、图过期还是实现问题。
  - 库端核对与期待对不上时同样停在这一步，查不到写 `查不到`、查不了写 `无法核对` 并附原因，不拿 `通过` 盖过去。
  - 判断不了就问开发人员，不自己改数据、改配置、改代码去让它过。
  - 开发人员要求继续时跳过该步往下走，该行结论写 `未执行` 并写原因，同时写进 **未覆盖**，不算通过。
  - 图与实现不一致按实际记，写成偏差；不按图硬凑结果，也不回头改图。
- 完成标志：每个失败或偏差都有实际证据，且已由开发人员确认性质。

### 步骤 5：验收并结束

- 操作：
  - 写记录文件，对照 **验收标准** 逐条核对，修正后重查；两者都比对时两份都写、都核对。
  - 报告文件路径、通过、未通过、未执行的条数与偏差清单，然后停。
- 完成标志：验收项全过，输出停在报告处。

## 约束

### 测试范围

- 只跑这一个功能点的这一条流程；alt 与带触发条件的系统行为算流程内，逐个走。
- 边界、异常、并发、性能不在本技能内；开发人员点名的才加行，并在步骤名后标 `（额外）`。
- 只验证，不顺手修 bug：发现实现问题只记录，改不改、谁来改由开发人员定。
- 不写测试用例集，不引测试框架，不改项目里的测试目录。

### 环境与数据

- 只在非生产环境跑；开跑前确认，任一项指向生产就停。
- 不启动、重启、停止服务，不改端口与配置，不重装依赖；服务没起来就报告。
- 流程自己产生的数据默认保留，不删、不重置；要清理由开发人员自己做或明确批准。
- 不造前置数据绕过条件，例如直接插入用户或会话；缺前置数据就问开发人员要。

### 数据库核对

- 只用只读查询，不加 `--allow-writes` 与 `--allow-dangerous-sql`；被拒绝时报告，不换客户端绕过。
- 查什么按业务判断：新建要有新行，更新要字段变，删除要行不在，状态流转要状态对得上；读不准表与字段就先看清结构，再问开发人员。
- 查询加 `--limit 50 --timeout 10s --json`；只查核对需要的那张表那几行。
- 查不到记录时先确认是不是同一个库、同一时间窗、同一条标识，再判该步未通过或无法核对，不猜。
- 结果里的密码、完整 token 与手机号中间位不进记录文件。

### 凭据

- 账号、密码、token 由开发人员提供；不猜、不爆破、不绕过登录。
- 记录文件里用 `<token>` 占位，不贴完整值。

### 执行方式

- 接口流程不变更请求路径、方法或参数去适配报错，改成能过的不算测试。
- 需要多步串联时可以在临时目录放一次性脚本，用完说明它不留在仓库里；不在仓库里新建测试脚本目录。
- 页面流程只操作这条流程涉及的页面，不点无关入口，不改账号设置，不做批量或删除类操作。
- 截图需要保留时放在记录文件旁边，名字是 `<记录文件名去扩展名>-第几步.png`，不另写说明。

### 异常处理

- 网络超时、连接中断时重试一次；仍失败就记录并停在该步，不换环境。
- dbx 连不上或查询被拒时先按它返回的错误处理，仍不可用就把该步的库端核对写 `无法核对` 并问开发人员，不拿别的客户端直连库。
- 外部输入等不到时把该步标 `未执行`，继续问清再决定是否停下。
- 中途叫停时已落盘的行留着，下次从步骤 1 重新核对清单。

## 输出与验收

### 记录文件格式

````markdown
# <编号> <功能点名> 测试

方式：<接口流程或页面流程>，依据 `<编号>-<功能点名>-时序.md`
环境：<接口基地址，页面方式再加页面地址>，<库名>，DBX 连接 `<连接名>`
时间：<开始> 至 <结束>

结论：<通过、几步未通过、没跑通，一句话>

| #   | 步骤 | 操作 | 期待 | 实际 | 库端核对 | 结论 |
| --- | ---- | ---- | ---- | ---- | -------- | ---- |
| 1   |      |      |      |      |          | 通过 |

## 偏差

- <第几步>：<期待与实际差在哪、已确认的性质>

## 未覆盖

- <哪一步或什么情况>：<为什么没跑>
```

操作写请求方法与路径，或页面动作，例如 `点击登录`。实际写状态码与关键返回，页面方式写页面上看到的结果；没跑的行写 `未执行` 与原因。库端核对写查到的业务结果：新行、字段变化、行不在了、状态已变；业务上不留记录写 `无可查`，查不到或查不了写 `查不到` 或 `无法核对` 并附原因，没跑写 `未查`。结论只有 `通过` `未通过` `未执行` 三个值。开发人员点名加的行，步骤名后标 `（额外）`。没有时序图时，依据写 `口述流程`；页面方式不适用时，方式行写 `页面不适用`。整节没有内容时删掉该节，不留空表。

完整示例见 `assets/test-example.md`，落盘前对照一次。

### 交付内容

- 文件路径，两份时都报。
- 通过、未通过、未执行的条数。
- 偏差清单，只写事实。

### 验收标准

- 文件在预定位置，名字是 `<编号>-<功能点名>-测试.md`；两者都比对时两份，文件名带 `-接口` 与 `-页面`。
- 除标 `（额外）` 的行外，清单每行都能在图上对上，或与确认过的口述清单对上；图上的 alt 与带触发条件的 Note 都有对应行，或已在 **未覆盖** 里写明原因。
- 每行都有实际结果，没有空着的行；没跑的结论是 `未执行`、库端核对是 `未查` 并写了原因，也进了 **未覆盖**。
- 每一步都按业务判断做过库端核对，或有 `查不到`、`无法核对` 与查过的连接、库、时间窗；业务上不留记录的写的是 `无可查`。
- 结论只用三个值，与各行一致，开头那句与表格一致。
- 开头写了方式与环境，环境已确认非生产；接口流程里没有浏览器操作，页面流程里页面对照与库端核对都有，也没有点无关入口或做删除类操作。
- 没有图外新增的边界、并发、性能测试，开发人员点名加的行已标 `（额外）`。
- 没有写数据库、没有启动或重启服务、没有改配置、代码与项目里的测试目录，没有装依赖。
- 文件里没有密码与完整 token；临时脚本与日志没有留在仓库里，保留的截图按记录文件名加步骤编号命名。
- 失败步骤停在原处如实记录，没有被改数据或跳过后算成通过。

## 示例

功能点「01 短信验证码登录」，时序图来源现状。开发人员说测接口流程，给了基地址、测试账号与 DBX 连接名。清单五行：取图形验证码、请求下发短信、重复请求、提交登录、用过期验证码再登录。

执行：curl 依次取图形验证码、请求下发短信，向开发人员要手机收到的验证码，再提交登录；每步后按业务该留下的记录查库，下发后看验证码记录，登录后看会话记录。第三步按图是 alt，重复请求一遍确认没有新增记录。第四步返回 200 却查不到新的会话记录，停在原处，把请求与库端现状记下来问开发人员；确认是实现问题后记成 `未通过`，未修。第五步要先用过期验证码登录，得等验证码过期，且第 4 步已停，记成 `未执行`。报路径、条数与偏差，然后停。

页面方式的差别只在步骤 3：先读 `agent-browser skills get core`，打开登录页、填手机号与验证码、点登录，读跳转结果，再照常查库。方式行改写页面流程，文件名带 `-页面`，其余不变。

成品长什么样，见 `assets/test-example.md`。

边界案例：图上的系统行为靠等触发条件，例如「验证码 60 秒未使用自行作废」，等满 60 秒再查那条记录，能等到就记一行，等不到就写 `未执行` 并说明原因，不跳过不提。
