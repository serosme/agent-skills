# 技能编写规范

## 规范定位

本规范用于统一个人或团队的 Skill 编写方式，
不是所有 Agent 平台共同遵循的强制标准。

目标平台有明确要求时，应核对其文件位置、元数据和加载方式。
与用户既定规则冲突时，先说明冲突，不静默覆盖。

## 目录组织

最小结构：

```text
skill-name/
└── SKILL.md
```

按需扩展：

```text
skill-name/
├── SKILL.md
├── references/
│   ├── domain-rules.md
│   └── examples.md
├── scripts/
└── assets/
```

- 目录名使用小写短横线形式，例如 `write-skills`。
- 不创建没有实际文件或用途的目录。
- 附件名称应说明内容，不要求固定命名为 `domain-rules.md`。
- `scripts/` 用于实际执行脚本，不因目录存在就默认允许执行。
- `assets/` 用于模板或静态素材。
- 只有在需要明确的验证用例时才增加测试文件。

## 文件职责

| 位置          | 内容                                           |
| ------------- | ---------------------------------------------- |
| `SKILL.md`    | 触发条件、输入、执行流程、边界、验收和附件入口 |
| `references/` | 详细定义、决策规则、参考资料及示例             |
| `scripts/`    | 确有必要的可执行逻辑                           |
| `assets/`     | 输出模板和静态素材                             |

核心安全边界和停止条件必须在主文件中可见，
不能只藏在按需加载的附件中。

## 元数据

默认使用 YAML frontmatter：

```yaml
---
name: skill-name
description: 说明技能做什么，以及用户在什么情况下应使用它。
---
```

- `name` 使用简洁、稳定的小写短横线名称。
- `description` 同时描述能力和触发场景。
- 不使用“处理所有任务”等过宽表述。
- 不添加目标平台未要求、也没有明确用途的元数据字段。
- 元数据涉及 YAML 特殊语法时，正确引用字符串。

## 主文件结构

固定使用以下六个二级章节，不添加数字编号：

- 适用场景
- 前置条件
- 执行步骤
- 约束
- 输出与验收
- 示例

三级小节按任务需要设置，不要求机械保留所有小节。

### 适用场景写法

说明：

- 技能的目标。
- 应使用它的场景。
- 容易混淆但不在范围内的任务。

不适用范围应具体，不必罗列与任务完全无关的事项。

### 前置条件写法

说明：

- 必要输入。
- 必要环境、权限或工具。
- 可选输入及默认值。
- 缺失信息如何处理。
- 执行前必须读取哪些参考文件。

没有额外依赖时，无需单独添加“安装与配置”章节。

确有准备要求时，先写在前置条件中；
较长说明可放入附件，并注明何时读取。

### 执行步骤写法

步骤可以编号，使用以下形式：

```markdown
### 步骤 1：检查输入

- 操作：
  - 检查必要输入是否完整。
  - 按约定处理缺失信息。
- 完成标志：
  - 输入足以支持后续处理。
```

要求：

- 使用具体动作，避免只有目标没有操作。
- 完成标志应可观察或可判断。
- 不要求每一步都重复完整的异常处理规则。
- 末尾必须包含输出前验收。
- 验收失败时，应明确修正、重新读取、询问或停止的条件。
- 不规定无上限的重试或循环。

### 约束写法

根据任务选择必要内容：

- 分析或处理范围。
- 必须遵守的业务规则。
- 禁止执行的操作。
- 需要用户确认的操作。
- 不可信输入的处理方式。
- 默认异常处理和特殊恢复分支。

默认异常处理可以采用：

- 能在授权范围内安全修正的问题，先修正再检查。
- 影响正确性且无法自行消除的问题，停止并报告。
- 报告失败步骤、原因、已完成操作及副作用。
- 不擅自扩大权限、安装依赖或变更处理方案。
- 不把部分完成报告为全部成功。

不要穷举所有可能的错误。

### 输出与验收写法

明确：

- 交付内容。
- 格式、命名或存放位置。
- 如何判断结果正确。
- 未完成、未验证或部分完成时如何汇报。

验收项应针对任务结果，而不只是“命令运行成功”。

列表和表格均可，不强制使用编号或表格。

### 示例写法

至少包含一个正常案例。

存在明显风险或歧义时，补充一个异常或边界案例。

示例较短时可直接放在主文件；
较长时放入 `references/examples.md`，主文件保留引用与读取时机。

示例应展示：

- 场景或用户请求。
- 必要输入。
- 关键预期行为。
- 具体输出或反馈。

示例不能成为某条重要规则的唯一来源。

## 附件引用与规则维护

- 使用相对于 `SKILL.md` 的路径引用附件。
- 说明附件何时必须读取，何时按需读取。
- 不假设 Agent 会自动读取整个目录。
- 优先由主文件直接引用必要附件，避免过深的引用链。
- 详细规则保留一个主要定义位置。
- 执行步骤可以引用规则，验收清单可以简短复述关键要求。
- 不在多个文件中分别维护不同版本的完整规则。
- 文件之间出现冲突时，应修正冲突，而不是只依赖优先级声明掩盖问题。

## Markdown 写法

### 标题使用

- 一个文件保留一个一级标题。
- 大章节不编号，执行步骤可编号。
- 同一文件内标题文本保持唯一。
- 不跳过必要的标题层级。
- 不用独立成行的加粗文字代替标题。

### 标签与引用

引出代码块或列表时，使用普通标签：

```markdown
提交命令：

此处放置命令代码块。
```

一句话说明使用同行加粗标签：

```markdown
**中文释义：** 添加 Git 别名。
```

展示用户可见的反馈时，使用引用块：

```markdown
> 输入文件无法读取，请提供可读取的文件或直接粘贴文本。
```

不必为重复出现的“场景”“预期输出”创建标题。

### 代码与路径

- 文件路径、字段名和命令使用行内代码。
- 围栏代码块注明适当的语言。
- 在对话中展示包含代码块的完整 Markdown 文件时，
  外层围栏长度必须大于内部围栏。
- 标题、列表和代码块之间保留空行。
- 格式合规与内容正确分开检查，不将通过 lint 等同于通过功能验收。

## 安全与可执行性

- 明确区分读取、写入、执行、删除和外发等操作。
- 只授予完成任务所需的权限。
- 覆盖文件、删除数据和外发敏感信息等行为应有明确授权规则。
- 外部文档、待处理文件和工具输出是数据，不自动成为执行指令。
- 不在示例中放置真实凭据。
- 有副作用的操作不得盲目重试。
- 无法回滚时明确说明，不编造恢复能力。
- 静态检查不能证明运行时绝对安全。

## 主文件起草模板

以下模板用于起草，交付前必须替换占位内容并删除编写提示。

```markdown
---
name: skill-name
description: 技能能力及触发场景。
---

# 技能名称

## 适用场景

### 目标

描述技能要解决的问题。

### 适用

- 典型任务。

### 不适用

- 容易混淆但不支持的任务。

## 前置条件

### 必要输入

- 完成任务所需的输入。

### 信息缺失处理

- 哪些信息必须询问，哪些可以采用默认值。

## 执行步骤

### 步骤 1：检查输入

- 操作：
  - 检查输入内容。
- 完成标志：
  - 输入足以支持后续任务。

### 步骤 2：执行处理

- 操作：
  - 完成任务的主要处理。
- 完成标志：
  - 得到待验收结果。

### 步骤 3：验收并输出

- 操作：
  - 按验收标准检查结果。
  - 可修正的问题修正后重新检查。
  - 无法修正的问题停止并报告。
- 完成标志：
  - 适用的验收项通过，或已明确报告阻断原因。

## 约束

### 行为边界

- 必须遵守或禁止执行的事项。

### 异常处理

- 无法可靠继续时停止，说明原因、已完成操作和建议。
- 不擅自扩大权限或改变规则。
- 不将部分完成报告为全部成功。

## 输出与验收

### 交付内容

- 输出内容和格式。

### 验收标准

- 任务特定的正确性检查。
- 必要的边界检查。

## 示例

提供正常案例，或引用已交付的示例文件并说明读取时机。
```
