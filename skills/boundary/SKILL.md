# Boundary

## 目标

接收一个功能点，划清它内部的边界：这个功能点里哪些行为做、哪些不做。产物是一份短文件，只写短句。

分析围绕四件事转：这一块怎么走完一个闭环、边界上各种情况怎么表现、哪里不合理、有没有更小更笨的做法。

## 前置条件

- 必要输入：开发人员指定的一个功能点，通常是 `breakdown` 拆解出来的，也可以直接给出。
- 可读：功能点所在目录的 `index.md`，以及它点到的代码与文档。
- 输出位置：功能点所在目录下 `<编号>-<功能点名>.md`；单独给出的功能点用 `01`。
- 缺失处理：功能点只有一句话、看不出要碰什么时，先问一句范围，不自行补全。没有 `index.md` 时只写块文件，不改状态。改换另一块时，从步骤 1 重新开始。

## 执行步骤

### 步骤 1：先读

- 操作：
  - 读功能点、它在 `index.md` 里那一行及状态、它依赖的功能点，以及点到的代码与文档。
  - 状态已是 `边界已定` 时，先问开发人员怎么处理，包括是否换一块，不自作主张。
  - 把已知和未知分开列，未知的整理成 **待问清单**。清单只在对话里维护，不写进文件；每条标上它属于哪个角度。
  - 每定一条，就在清单里把它划成已定结论，不要直接删。
- 完成标志：能复述这个功能点的输入、输出与出现场合。待问清单已成形，四个角度各至少有一条；提不出问题的角度，说明为何不适用并记成已定结论。有 `index.md` 时状态已确认为 `边界未定`。

### 步骤 2：逐轮提问并落盘（循环）

- 操作：
  - 每轮开头先说一句「待问清单还剩 N 条」，从清单里取 2 到 3 条出题，按 **提问格式** 写。
  - 回复一到，把没提到的按推荐、提了不做或不同意见的按开发人员的说法，一起按 **文件格式** 落盘。
  - 把已答的划成已定结论并写清结论，再把这一答带出的新问题补进清单。
  - 回到本步开头。
- 完成标志：待问清单里没有未答项，且四个角度下的问题都问完了；文件与本轮回答一致。没走完就不离开本步；中途因补齐而新增过 `做` 行的，回到步骤 3 再补一圈。

### 步骤 3：补齐「不做」行

- 操作：
  - 清单走完后必走这一步，不靠临场想起。
  - 逐条拿 `做` 行追问「紧挨着它外面的是什么，我们做不做」。候选包括同一件事的相邻能力、同一链路的上下游、常见的外围功能。
  - 问到的写成 `不做` 行，没问到的不记。追问出「这条也要做」的，先加进待问清单再回到步骤 2。
  - 这条只管功能点内部，不上推到其他功能点。
- 完成标志：每条 `做` 行都问过外面是什么，`不做` 行不少于 3 条；凑不到 3 条时说明边上为什么没有更近的能力，按实际条数放行。

### 步骤 4：提交核对

- 操作：
  - 把文件内容原样贴给开发人员，不另写摘要。
  - 不问「够了吗」，而是问「还缺什么、哪条不对」。
  - 属于不做的补充直接写进表格；属于要做或要改的，加进待问清单并回到步骤 2 继续问。
  - 改完再贴一次，直至开发人员确认。
- 完成标志：文件内容已原样贴出，开发人员已确认，中间没有未处理的补充。

### 步骤 5：结束并停

- 操作：
  - 对照 **结束判据** 与 **验收标准** 逐条核对，修正后重查。
  - 核对通过之前不改 `index.md`；通过后，有 `index.md` 时把这一行状态改为 `边界已定`。
  - 报告文件路径与状态变更，然后停。
- 完成标志：判据与验收全过且核对已确认；有 `index.md` 时状态已回填。输出停在报告处。

## 约束

### 提问规则

- 一轮 2 到 3 问，一问一块，问题一行，推荐与理由逐行写成子项。
- 默认按推荐执行：开发人员只说不做或不同意见，其余视为接受，不必逐条回「是」。
- 说了不做的写成 `不做` 行；回「不做」指的是不做这件事，不是不要这条推荐。
- 说了推荐有问题的，按开发人员的说法改，不辩护；只说不行、没说改成什么时，问一句要改成什么，不自行推演。
- 每个回答都要往下追一层：这一答带出了什么新问题？追不出新问题，这一支才算走完。
- 待问清单没空不收尾，也不问「够了吗」催收尾。
- 允许回跳过或不确定，不再追问第二遍，这类回答算不做。
- 决策由开发人员定，事实自己查，不拿查得到的东西去问。

### 文件规则

- 一张表：`做` 与 `不做` 两类同表排列，每次落盘都保持 `做` 行在上；不另开 section。
- 只写短句，不写段落，不写背景说明。
- 每轮结束就更新文件，不攒到最后一次输出。

### 边界

- 不写设计、方案、技术选型、实现步骤与测试用例。
- 不开始写代码。
- 开发人员中途叫停时，已落盘的结论留在文件里。`index.md` 保持 `边界未定`，块级状态保持 `未开发`，下次从步骤 1 接着问，不把半成品当成品。
- 结束之后不接着做下一块，也不提议开始实现。

## 输出与验收

### 覆盖下限

四个角度是下限，不是上限：每个角度下的问题都问完才算过。问完了又发现新问题，就接着加进清单。某个角度对这个功能点确实不适用时，在对话里说明为什么跳过，并作为已定结论记进清单。

| 角度   | 至少要问到                                                                   |
| ------ | ---------------------------------------------------------------------------- |
| 闭环   | 输入从哪来 → 经过什么 → 到哪去 → 谁收到 → 然后呢，每一环都有答案，断点已说明 |
| 边界   | 最空、最满、重复、失败、没权限里至少三种有答案                               |
| 不合理 | 至少问过一次：哪里自相矛盾、和现有行为冲突、成本远超收益                     |
| 可优化 | 至少问过一次：有没有更小更笨的做法                                           |

### 提问格式

每轮开头先说一句还剩几条，然后一问一块，推荐写在问题下面。

```text
待问清单还剩 4 条。

1. <问题标题>
   - 推荐：<要做的做法>
   - 理由：<一句>

2. <问题标题>
   - 推荐：<要做的做法>
   - 理由：<一句>
```

### 文件格式

标题、状态行、一句话，然后一张表，表里只有 `做` 与 `不做` 两种类型。

```markdown
# 01 <功能点名>

状态：未开发

<一句话：这块做什么>

| 类型 | 行为       | 状态   |
| ---- | ---------- | ------ |
| 做   | <具体行为> | 未核验 |
| 不做 | <具体行为> | 未核验 |
```

完整示例见 `assets/block-example.md`，落盘前对照一次。

有两个层级的状态，都由开发人员回填，本技能只写初始值。

- 块级 `状态`：`未开发` → `已实现` → `已核对`。
  - 本技能填 `未开发`。
  - `做` 行都做完填 `已实现`。
  - 逐行核验完填 `已核对`。
- 行级 `状态`：`未核验` → `已核验`。
  - 本技能全部填 `未核验`。
  - 开发完逐行对照代码：`做` 行确认真的做了，`不做` 行确认真的没做，再改成 `已核验`。
- 块级到 `已核对` 时，表里每一行都应是 `已核验`。

行级状态与 `index.md` 的状态列也不是一回事：那边记边界走到哪，这边记这一条行为核验过没有。

### 结束判据

五条同时成立才算完：

1. 待问清单里没有未答项，四个角度下的问题都问完了。
2. `做` 行每条都具体到核验时能判断做没做。
3. `做` 行合起来能兑现 `index.md` 里这一句「做完能看到什么」。
4. `不做` 行不少于 3 条，且每条都是真有人会想做的；凑不到 3 条时，说明边上为什么没有更近的能力，按实际条数放行。
5. 文件内容已原样贴给开发人员，并得到确认；中间没有未处理的补充。

### 交付内容

- 文件路径。
- 块级状态为 `未开发`，行级状态为 `未核验`。
- 有 `index.md` 时，对应行的状态已改为 `边界已定`。

### 验收标准

- 文件在功能点所在目录，名字是 `<编号>-<功能点名>.md`。
- 状态是在核对确认之后才回填的，之前没动 `index.md`。
- 待问清单里没有未答项，四个角度都有结论，没有停在第一轮。
- 文件里只有一张表，类型列只有 `做` 与 `不做` 两个值，状态列全为 `未核验`，没有多出 section、设计或实现内容。
- `做` 行能兑现 `index.md` 里的「做完能看到什么」。
- 每条都是短句，扫一眼能全看懂。
- `不做` 行数达标，覆盖了紧挨着这块外面、最容易被人顺手做掉的那几项；条数不够时已有说得过去的理由。
- 结论是按轮落盘的，没有攒到最后一次性输出。
- 文件里的块级状态是 `未开发`，行级状态全是 `未核验`，两个状态都不由本技能往下推进。
- `index.md` 里这一行的状态已改为 `边界已定`，其他行未动；没有 `index.md` 时只写了块文件。
- 只处理了这一个功能点。

## 示例

功能点：「03 接真模型」，做完能看到「发一句，收到基于 7 天记录的模型回复」。

待问清单还剩 5 条：一次性还流式、7 天按什么时间算、失败怎么表现、单次带多少条、连发怎么处理。

第一轮：

```text
待问清单还剩 5 条。

1. 模型回复是一次性返回还是流式输出？
   - 推荐：一次性
   - 理由：页面已有占位回复，先不接流式

2. 7 天窗口按消息时间算，还是按对话开始时间算？
   - 推荐：按消息时间
   - 理由：与「带最近 7 天记录」的说法一致

3. 调模型失败时怎么表现？
   - 推荐：占位回复改成失败提示，可重试，不入库
   - 理由：库里不留半截对话
```

开发人员回「3 不做，其余按推荐」。落盘后把三条划成已定结论，「一次性」这一答又带出两条新问题：单次带多少条、超出怎么裁。清单剩 4 条。

第二轮：

```text
待问清单还剩 4 条。

1. 7 天内的消息全带，还是截断？
   - 推荐：全带，超过 200 条只留最近 200 条
   - 理由：控制单次请求体积

2. 上一句还没回复就又发一句，怎么处理？
   - 推荐：等上一条回来再发，期间输入框不可用
   - 理由：避免回复错位

3. 提示词放哪？
   - 推荐：后端配置文件，不入库
   - 理由：不入手的配置不占表
```

开发人员回「2 改成直接拒绝并提示，其余按推荐」。清单只剩「可优化」这一支。
第三轮问：失败重试的次数要不要可配？推荐：不可配，固定不重试。
四个角度的问题都问完后，补 `不做` 行：流式输出、失败重试、模型切换、提示词界面配置。

把文件内容贴给开发人员核对。他补了一条「不做多轮上下文压缩」，直接进表；又说「单次请求要能配超时」，这条属于要做，加进待问清单，问清后落盘。
再贴一次，确认无误。然后块级状态写 `未开发`、每行行级状态写 `未核验`，`index.md` 里这一行改为 `边界已定`，报告路径与状态变更，然后停。

成品长什么样，见以 05 安卓壳为例的 `assets/block-example.md`。

边界案例：功能点很小、凑不出 3 条 `不做` 行时，说明边上为什么没有更近的能力，按实际条数放行，不硬凑。
